LEARN · PHASE 12 · LESSON 85

When NOT to Parallelize

Parallelise when the work divides at a boundary you can verify on its own.

Type
Learn
Prerequisites
Lesson 84 (The Decision Framework)
Time
~35 minutes

Learning Objectives

  • Run six tests on a task and reject it, with a reason, before writing any orchestration
  • Estimate the coordination cost as a number you can compare to the work
  • Name a merge step before the work starts, or say why there isn't one
  • Explain why a parallel run multiplies a bug rather than averaging it out

The Problem

Two incidents from this repo, and both are the same mistake in different clothes.

The first: a workflow script grew a --phases flag to narrow a run to one phase. It accepted the flag, filtered a list with it, and then passed every phase to the authoring step anyway. The flag was decoration. The run fanned out over all nineteen phases when the user had asked for one.

The cost of that bug was not the bug. It was nineteen times whatever the bug would have cost sequentially.

The second: three agents were dispatched, each into its own worktree, each asked for a piece of finished work. All three produced exactly what they were asked for. None of them ran git commit. All three branches pointed at the same commit as main. There was nothing to merge. Perfect work, isolated properly, gone.

And a third, from the same afternoon, which is the one that teaches attribution: after a parallel authoring run the test suite came back red. The obvious reading was that the agents had broken something. The actual cause was a wrong glob in package.json — the runner, not the work. Many workers, one red result, and the evidence pointed the wrong way.

None of these is an argument against parallelism. All three are arguments against starting it before you have answered a short list of questions.

The Concept

Parallelism is an amplifier. It multiplies throughput and it multiplies whatever the loop was already doing — including its bugs, its ambiguity, and its unfinished decisions.

So the first question is never "how many workers". It is "is the thing they will each execute correct?"

Six tests, in order

Run them in this order. The first two reject most tasks.

1. Is the single-threaded version correct?

Run it once, serially, and look at the output. If it is wrong, the parallel run is wrong N times, faster, and more expensive. This is the --phases incident: the fan-out was fine and the thing it fanned out was not.

2. Does the work divide at a boundary you can verify on its own?

Take one piece, in isolation, and ask whether you can say it is right without the other pieces. If you cannot, you do not have pieces — you have a task you have sliced into un-checkable fragments, and you will be checking the whole thing at the end anyway.

This is the real discriminator. It rules out "have five agents each improve this module" and it permits "have five agents each rewrite one file to a stated format".

3. Is anything load-bearing sequential?

If step B needs step A's output, they are one worker's job. You can still run two independent chains in parallel; you cannot parallelise a chain.

The test is concrete: write down what each worker's input is. If any input is "the result of another worker", that pair is sequential.

4. Is there a shared mutable resource?

Worktrees give each worker its own copy of the files. They do not give each worker its own database, its own deployment target, its own message queue, or its own row in a table. Two workers writing to one of those collide exactly as two people would, and a worktree will not help.

Count the shared things before you dispatch: one file, one branch, one service, one account. Each one is either partitioned or serialised.

5. Can you attribute a failure to a worker?

If the aggregate result is wrong, can you say which worker did it? For the red-suite incident the answer was "no", and the wrong party got the blame. If a result is a single artifact assembled from N contributions with no per-contribution evidence, you have traded one slow debug for N fast mismatches.

6. Is the task bigger than the coordination?

The coordination cost is real and it is countable:

N workers × (setup + briefing + isolation)
+ N commits
+ N−1 merges
+ the review you now owe each piece
+ the re-run when one fails

If that number is larger than the task, do it yourself. It often is. A four-line change does not need five worktrees, and the merge conflict between two workers who both touched the same helper will take longer than the change.

The commit rule

If your parallel plan does not end in a commit per worker and a stated merge, it does not end. Isolation without a commit is not a backup. That is the second incident above, and it is the most expensive failure in this repo's history because it looked finished.

So the merge step is not step seven. It is part of the plan, decided before the first worker starts:

  • Which branch does each worker commit to?
  • Who merges, in what order, and what does "merged" mean?
  • What if two workers changed the same file?

If you cannot answer the third question, test 4 already failed.

The honest summary

Parallelism buysParallelism costs
Wall clock, when the boundary is cleanCoordination: setup, briefs, isolation, merges
Scale, when the step is uniformTokens: N times the work, plus each worker's context
Independence, when workers cannot collideAttribution: harder to say who broke what
Throughput on I/O-heavy workCompounding: a wrong instruction, N times

None of these is a reason to avoid it. They are the reasons it is a decision.

The reframe: parallelise when the work divides at a boundary you can verify

on its own — because if you cannot check a piece by itself, the merge is the

work, and you have made the work bigger rather than faster.

Build It

1. Take a task you were about to parallelise

Pick one you have already thought about — ideally something you were confident about when you opened this lesson.

✅ You pass when you can write the task in one sentence and name the output in another.

2. Run the six tests and write a verdict per test

Pass, fail, or "not sure". not sure is a fail for the purposes of this exercise; it usually means test 2.

✅ You pass when every test has a written verdict and at least one is not "pass".

3. Compute the coordination cost

Fill in the formula above with real numbers: minutes per setup, minutes per merge, minutes for the review. Then write down what the task would take you alone.

✅ You pass when the two numbers are comparable — same units, same level of optimism — and you can say which is larger.

4. Write the merge step, or write why there isn't one

Branch names, commit rule, merge order, and what happens if two workers touched one file.

✅ You pass when the third clause has a real answer, and it is not "they won't".

5. Reproduce incident one at the smallest scale

Take a decision that is not pinned down — an ambiguous instruction you have not finished specifying — and fan it out over three workers. Deliberately.

✅ You pass when all three outputs are wrong in different ways, and you can say what the single-threaded run would have told you for a third of the cost.

6. Now serialise the same task and measure both

Run it once, yourself, start to finish, and time it. Then run the parallel version and time that, including the merges and the review.

✅ You pass when you can state the crossover: at what N would the parallel version have been worth it.

7. Find the verification boundary

For a task that failed test 2, try again to find a boundary where each piece is independently checkable — even if that means the pieces are smaller than you first imagined.

✅ You pass when you can name a boundary, or explain why none exists for this task.

8. Read the failure mode in this repo's own script

scripts/lib/workflow-lib.mjs opens by explaining what the old done-check got wrong: a single git grep for one scaffold marker, which was wrong in both directions. That is a verification boundary problem, written down by someone who hit it.

✅ You pass when you can state the two directions it was wrong in, and connect each to a test above.

Nothing here is version-gated — this is arithmetic and judgement. The repo scars

are dated in the commit log. If you want the mechanism details behind any test,

the pages linked in Lessons 77–84 are the sources.

Exercises

  1. Write the one-line rejection you would give for each of these: a 40-line bug fix across five worktrees; five agents improving one module; three agents processing a queue that writes to one table. ✅ You pass when each rejection names a test rather than a preference, and at least one offers the narrower task that would pass.
  1. Time a serial run of a task you would normally parallelise. Then parallelise it and time the whole thing, merges included. ✅ You pass when you have both numbers and a stated N at which the parallel version wins.
  1. Design a parallel plan for a task where two workers must touch the same file. Do not say "they won't". ✅ You pass when the plan names the conflict-handling step and says who resolves it.
  1. A red test suite after a parallel run is evidence of what, exactly? Answer before checking. ✅ You pass when your answer names the possibility that the runner is at fault, not only the workers.

What this lesson skipped

Dependency structure as a formal thing. "Which steps need which" as a graph, and the notion of a critical path, is Phase 15. This lesson uses the plain version of the same idea: if B needs A's output, that pair is sequential.

Measuring an agent's real cost. Attribution and cost both get instruments in Phase 14. Test 5 here is the design question; Phase 14 is the measurement.

Merge strategy in depth. Branch naming, ordering, and conflict resolution for agent branches is Phase 16, Lesson 109.

Failure propagation across a graph. What happens when one of N workers dies, and how the rest of the plan should react, is Phase 15, Lesson 104. This lesson only insists that you be able to tell which one died.

The case for parallelism. This is the counterweight lesson, and it is easy to read as a prohibition. It is not. Every test above has a version that passes, and when the boundary is clean and the merge is cheap, doing it serially is the mistake.

The one scar deliberately left out. The startup-cache trap — where a session started before git init cannot use worktree tools even though git rev-parse says otherwise — is real, and it is Phase 16, Lesson 108, because it is a bug you reproduce rather than a judgement you make.

Check yourself

6 questions. Answer before you reveal — recognising the right option is not the same as being able to produce it.

  1. A single-threaded script has a bug: it ignores a filter flag and processes every item. You now fan the same script out across nineteen workers. What is the result?

    1. Nineteen wrong results and nineteen times the tokens — parallelism multiplies whatever the loop already does
    2. One wrong result, because the workers deduplicate identical outcomes
    3. The bug is usually masked, since independent workers rarely agree on a wrong output
    4. The wrong results, but at the same total cost, since the work is the same either way
    Show answer

    A. Nineteen wrong results and nineteen times the tokens — parallelism multiplies whatever the loop already does

    Parallelism is an amplifier: it multiplies throughput and the loop's existing defects together, which is exactly the --phases incident this repo hit. The deduplication answer invents a safety net — workers running the same deterministic bug produce the same wrong answer N times, not zero times. Cost grows with the number of workers, not with the size of the output.

  2. Step B needs step A's output before it can start. You want both to happen faster. What is the disciplined move?

    1. Keep A and B in one worker, and look for a second independent chain to run alongside
    2. Run A and B in separate worktrees so they cannot interfere, then merge
    3. Put A and B in a pipeline() so the runtime schedules them
    4. Run them in parallel and discard whichever output arrives second
    Show answer

    A. Keep A and B in one worker, and look for a second independent chain to run alongside

    A dependency means the pair is one unit of work; the parallelism has to come from somewhere else — a second independent chain. Worktrees solve file collisions, not ordering, so they do nothing for a B-needs-A dependency. A pipeline() iterates one job over a list rather than sequencing two different jobs, and discarding the second result is a description of a race condition rather than a plan.

  3. Three workers will each consume from a queue and write results into one shared database table. Each has its own worktree. Is that safe?

    1. No — worktrees isolate files, not the database. The table is a shared mutable resource and needs partitioning or serialising
    2. Yes — a separate worktree per worker means the workers cannot see each other's writes
    3. Yes — the database handles concurrent writes on its own, so no coordination is needed
    4. Only if the three workers run in the same session rather than in separate ones
    Show answer

    A. No — worktrees isolate files, not the database. The table is a shared mutable resource and needs partitioning or serialising

    Worktrees give each worker its own copy of the checkout; they say nothing about a database, a deployment target, or an account. The shared-each-other's-writes answer confuses files with state: the worktrees are genuinely isolated and the table is still one table. Sensible as concurrency handling often is, it does not tell you the results are correct, and session grouping has no bearing on either.

  4. Three agents each finish their piece perfectly in their own worktree. Afterwards, all three branches point at the same commit as main. What went wrong?

    1. Nobody committed, so the isolation bought nothing durable and there is nothing to merge
    2. The branches should have been pushed to a remote, which would have preserved the work
    3. Worktrees cannot be committed to, so a different isolation mechanism was needed
    4. The agents should have shared one worktree instead of three
    Show answer

    A. Nobody committed, so the isolation bought nothing durable and there is nothing to merge

    This is this repo's most expensive scar: isolation without a commit is not a backup. The push answer is the reflexive fix and it is not the mechanism — the commits have to exist locally before a push could carry anything. Worktrees are ordinary git checkouts and commit normally, so the third option invents a limitation, and one shared worktree would have reintroduced exactly the collisions the isolation was for.

  5. A test suite comes back red after a parallel run. What is the correct first move?

    1. Check the runner before the workers — the failure's evidence is not automatically attached to the agents' work
    2. Revert every worker's branch, then re-run the fan-out to see if it happens again
    3. Assume the worker whose files changed most broke it and inspect that branch first
    4. Re-run the suite without parallel workers, since parallelism is the likely cause
    Show answer

    A. Check the runner before the workers — the failure's evidence is not automatically attached to the agents' work

    Ours was a wrong glob in package.json — the runner, not the work — and the parallel shape made the misattribution feel obvious. The revert-and-rerun answer spends the most time on the least informative experiment, because a red suite after any change is ambiguous. Guessing the busiest branch is a heuristic with no evidence behind it, and dropping parallelism removes the wrong variable: the question is whether the result can be traced to a worker at all.

  6. Which of these tasks is the best fit for parallel workers, by the six tests?

    1. Rewriting 60 independent data files into a stated format, where each file can be checked on its own and each worker commits its own file
    2. Having five agents each improve the same API module until it is better
    3. Three agents consuming one queue and writing into one shared table
    4. Two agents where the second needs the first's output before it can begin
    Show answer

    A. Rewriting 60 independent data files into a stated format, where each file can be checked on its own and each worker commits its own file

    The first task passes every test: the transformation is understood, each file is an independently verifiable unit, there is no shared mutable state, and the merge is trivial because each worker owns its file. The improve-this-module task fails the verification-boundary test — 'better' has no per-piece check and the pieces overlap. The shared-table task fails the shared-resource test, and the B-needs-A pair fails the sequential test.
