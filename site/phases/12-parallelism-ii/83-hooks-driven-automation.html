BUILD · PHASE 12 · LESSON 83

Hooks-Driven Automation — Events as Control Flow

The same exit-code contract that fences a tool call can push work back into the

Type
Build
Prerequisites
Phase 08 (Lessons 55–60), Lesson 82 (Loops)
Time
~45 minutes

Learning Objectives

  • Attach a hook to an event that pushes the loop forward, not just one that refuses a tool
  • Make "done" a checkable fact with a Stop hook instead of a sentence an agent wrote
  • Use SubagentStop, PostToolBatch, and TeammateIdle to keep orchestration moving
  • Post a message into your own session from a hook or Bash command, using the socket the session exports
  • Decide when a handler must be a command and when spending a model call is justified

The Problem

A loop was babysitting a release branch, once every twenty minutes. On the fourth iteration it reported that everything was green and quiet.

CI had been red for twenty minutes.

Nobody lied. The agent ran the check, read a truncated log, and summarised what it saw. The claim "everything is green" was the agent's sentence, not the check's output — and a sentence is not a fact you can enforce.

That is the gap this lesson closes, and it is not closed by a better prompt. It is closed by moving the decision somewhere that produces an exit code.

A hook is the only part of Claude Code that runs because an event happened rather than because the model chose to. Phase 08 taught it as a fence: this tool call is refused, this write is impossible. The same mechanism points the other way. The loop is a sequence of events — a turn is about to end, a subagent just stopped, a batch of tool calls just completed, a teammate just went idle — and your code gets to speak at every one of them.

The Concept

The loop is a machine with seams in it. A hook attaches to a seam.

The events that push, not just block

Phase 08's event table has a "can block?" column. Read it again with the orchestration question in mind: what would blocking here push forward?

EventBlocking meansWhat it is for
StopRefuse to end the turnThe turn is not finished, whatever the model said
SubagentStopSend the subagent more workA worker stopped early; the review says so
PostToolBatchStop the loop before the next model turnA batch of results changed the plan; stop and look
TeammateIdleKeep the teammate workingAn agent-team peer went idle with the shared task list unfinished
TaskCreated / TaskCompletedRefuse creation / reject completionA task does not meet the bar to exist, or to be called done
SessionStartRefuse startupLoad-time policy, not orchestration
PreCompactBlock the compactionRarely right. It is a seam, not a tool

WorktreeCreate and WorktreeRemove are not blocking, and they are the other half of orchestration: they fire on the lifecycle of a worker's checkout, which is where logging and cleanup belong.

And there is MessageDisplay, which carries a message's id, its delta, and whether it is final. It cannot block. It observes what a session shows.

"Done" is an event, and you get to define it

The single most useful hook in this phase is a Stop hook. The agent says it has finished; Stop fires; your script looks at the world and either allows the turn to end or refuses with a reason.

That is the release-branch incident fixed. Not "remember to check CI" — a script that checks, and a turn that cannot end until it agrees.

One guard you must have: Stop carries stop_hook_active, which tells you a stop hook has already fired. Without it, a hook that refuses for the wrong reason refuses forever. Phase 08's exit-2-versus-exit-1 distinction applies here exactly as it does to a fence — Lesson 58 if you need the reminder.

Where this meets workflows and loops

Two limits from the last four lessons point at hooks.

A workflow run takes no input mid-flight. It pauses only for agent permission prompts and a usage-limit wait. The seams that are available to you are the agent-lifecycle events: SubagentStart, SubagentStop, and the task events. A SubagentStop hook is how a stopping subagent gets handed one more sentence of work inside a run, without editing the script.

A loop cannot be trusted to report its own state. Lesson 82's loop fires between turns and summarises. A Stop hook is what converts that summary into a verifiable claim, and it fires whether the loop was Claude's idea or yours.

The other exit: post into your own session

Phase 08 taught the return path as exit code plus stdout JSON. There is a second one, and it is the one that makes hooks a channel rather than a decision.

Every session with messaging available binds a socket and exports its path and a per-session token to hooks and Bash commands as CLAUDE_CODE_MESSAGING_SOCKET and CLAUDE_CODE_MESSAGING_TOKEN. A hook or a command can open that socket and post a line back into its own session:

#!/bin/sh
# Emit a line into this session's own conversation.
{
  printf '%s\n' "{\"type\":\"auth\",\"token\":\"$CLAUDE_CODE_MESSAGING_TOKEN\"}"
  printf '%s\n' "build finished: 3 failures, see /tmp/build.log"
} > "$CLAUDE_CODE_MESSAGING_SOCKET"

One connection carrying both lines, because the auth line has to be the first line of its connection.

This is the same wire Lesson 77 described, addressed to yourself. Two traps carry over: on native Windows the auth line is required, and a connection that has not sent a complete line within 30 seconds is dropped — so capture slow output before you open it.

Cost decides the handler type

Phase 08's five handler types are not interchangeable, and orchestration is where the bill shows up. A command handler is milliseconds. An agent handler is a full subagent: slow, and a model call.

A hook on Stop fires once per turn. A hook on PreToolUse fires on every tool call. Put a model call on the second one and you have doubled the cost of your session to enforce a rule a grep could have enforced.

The rule: command until a script has demonstrably failed you. Then agent, on the narrowest event you can find.

The reframe: a hook is not only a fence around a tool call — the same

exit-code contract can push work back into the loop, so an event handler is

where "this step is finished" gets decided instead of described.

Build It

1. Turn a claim into a check

Pick a turn that has a checkable finish line. This repo works well: the lesson body is finished when the validator passes.

Write .claude/hooks/stop-requires-validator.sh:

#!/bin/sh
input=$(cat)
active=$(printf '%s' "$input" | jq -r '.stop_hook_active // false')

# Never refuse twice in a row; that is how a hook traps a session.
[ "$active" = "true" ] && exit 0

if [ -f package.json ] && ! node scripts/validate-lessons.mjs 12-parallelism-ii >/tmp/validate.log 2>&1; then
  head -20 /tmp/validate.log >&2
  exit 2
fi

exit 0

Wire it to Stop in .claude/settings.json, then ask the agent to finish something it has not actually finished.

✅ You pass when the turn refuses to end, the reason on your screen is the validator's first lines, and a second attempt can still end normally.

2. Prove the guard is load-bearing

Remove the stop_hook_active check and repeat. Make the validator fail in a way the agent cannot fix — a malformed quiz.json, say.

✅ You pass when you can describe what happens instead of a clean stop, and you can say which field would have prevented it.

3. Push work to a subagent at the moment it stops

SubagentStop fires when a subagent finishes, and blocking there sends it more work. Use the incident from Phase 06: a subagent that triages a report file. Have it stop after writing the line, with its SubagentStop hook asking a follow-up question the first pass did not answer.

✅ You pass when the same subagent does more work after its first stop, and you can point at the field that told your hook it was safe to block.

4. Stop the loop between batches

PostToolBatch fires after a batch of tool calls, with the calls in tool_calls[], and blocking there stops the loop before the next model turn. Write a hook that refuses the batch when a single batch wrote more than twenty files.

✅ You pass when the loop stops before the next model turn, and you can say which event you would have used if the rule were about one tool rather than a batch.

5. Keep a teammate from going idle

If you have agent teams enabled (Phase 11, Lesson 73), this is the orchestration event with no substitute. TeammateIdle carries teammate_name; blocking keeps the teammate working. Give a teammate a task and have the hook check the shared task list before letting it idle.

✅ You pass when the teammate keeps working with tasks outstanding, and you can say what the hook reads to decide.

6. Post instead of return

Rewrite the hook in step 1 so that, instead of refusing, it reports — into the session's own conversation, over the socket.

✅ You pass when the line appears in your session without a tool call producing it, and you can say which of the two return paths is a decision and which is a message.

7. Watch the cost

Run /hooks and count how many handler groups are attached to tool events versus turn events. If any tool-event handler uses an agent handler, replace it with a command handler and see whether the behaviour survived.

✅ You pass when the rule still holds and you can state, in milliseconds versus model calls, what you saved per session.

Exercises

  1. Take a rule you currently enforce with prose — in a skill, a CLAUDE.md, or a prompt — and re-express it as a Stop hook. Run it for an afternoon. ✅ You pass when you can name a case where the prose version passed and the hook version refused, and a case where both passed.
  1. Write a hook that posts a line into your own session from a background Bash command, not from a hook event. Compare it with returning JSON from a hook. ✅ You pass when the line arrives both ways and you can say which path the model sees as a tool result and which it sees as a message.
  1. A hook that fires on PostToolUse and classifies each result with an agent handler costs one model call per tool call. Compute what that does to a 200-tool-call session. ✅ You pass when your number is derived from a run you measured, not from an estimate you wrote down.
  1. Explain why a WorktreeCreate hook cannot stop a worktree from being created, and what you would use instead. ✅ You pass when your answer names a different event and says what it does before the worktree exists.

What this lesson skipped

The hook contract itself. Exit codes, stdin JSON, hookSpecificOutput shapes, matchers, and the if field are Phase 08, Lessons 55–60. This lesson builds on them and does not restate them.

The full JSON shape for each of these events. Each event's decision object has its own fields and its own nesting. Copy from the hooks page for the event you are writing — Lesson 57 says the same thing for the three you write by hand.

Channels. Pushing an event in from outside — CI, chat, monitoring — is an MCP server with a channel contract, and it is Phase 17. The distinction that matters here is direction: a hook reacts to something that happened inside a session; a channel injects something from outside.

Guardrails versus instructions as a design stance. This lesson is about where a decision lives. Lesson 96 is about what that decision can and cannot buy you, and which of the two an unattended run depends on.

Async hooks and timeouts. A background hook cannot block — the harness stops waiting — and a timeout on PreToolUse normally lets the call through. Both are Lesson 60, and both are silently wrong the first time you hit them.

Check yourself

6 questions. Answer before you reveal — recognising the right option is not the same as being able to produce it.

  1. You want a turn to be impossible to end until a generated file exists. Which event, and why?

    1. Stop — it fires as the turn ends and blocking there sends the agent back to work
    2. PostToolUse — it fires after every write, so it can check the file each time
    3. PreToolUse — it fires before the write and can hold the tool call until the file exists
    4. SessionEnd — it fires when the work is over and can reopen the turn
    Show answer

    A. Stop — it fires as the turn ends and blocking there sends the agent back to work

    The turn ending is the thing you want to refuse, and Stop is the event at that seam; blocking sends the agent back to work. PostToolUse is the tempting choice because the file check happens there naturally — but that event cannot block, so it can add a note to a turn that then ends anyway. PreToolUse runs too early, before the file could exist. SessionEnd cannot block and is about the session, not a turn.

  2. Your Stop hook refuses to end the turn, and the session now cannot stop. What is the missing piece?

    1. A check on stop_hook_active, so the hook never refuses twice in a row
    2. "async": true, so the hook does not hold the turn open
    3. Exit code 1 instead of 2, which is the non-blocking form of a refusal
    4. A PreCompact handler to clear the hook's state between turns
    Show answer

    A. A check on stop_hook_active, so the hook never refuses twice in a row

    Stop carries stop_hook_active, which tells your hook a stop hook has already fired — the documented way to avoid trapping a session. The async answer is a trap because a background hook cannot block at all, which is the opposite of what you want here. Exit 1 is genuinely the non-blocking code, but it is not a refusal that lets the session proceed; it simply means "no opinion", so it would not fix a hook that is already refusing. PreCompact has no bearing on a stop decision.

  3. A subagent stops before it answered your follow-up question. You want to hand it one more task without editing the workflow script that spawned it. What do you do?

    1. Attach a blocking hook to SubagentStop, which sends the subagent more work
    2. Attach a hook to SubagentStart, which can add the follow-up to its context
    3. Attach a hook to TaskCompleted, which rejects the task and reruns it
    4. Nothing — a subagent that has stopped cannot be given more work
    Show answer

    A. Attach a blocking hook to SubagentStop, which sends the subagent more work

    SubagentStop fires when the subagent stops and blocking there sends it more work. SubagentStart is the plausible neighbour and does something different: it can inject context before work begins, not after. TaskCompleted is about task records rather than subagents, so rejecting a task does not resume the agent that produced it. The do-nothing answer misses the event entirely — this is one of the seams that makes orchestration work inside a run that takes no mid-run input.

  4. You attach an agent handler to PreToolUse to classify every tool result. What is the cost problem?

    1. It is a full subagent, so it costs a model call on every tool call and multiplies the session's spend
    2. None — agent handlers run on a small model, so they are nearly free
    3. agent handlers are not allowed on tool events, so the hook is silently skipped
    4. The handler runs once per turn, so the cost is bounded by the number of turns
    Show answer

    A. It is a full subagent, so it costs a model call on every tool call and multiplies the session's spend

    An agent handler is a full subagent with your instructions and possibly tools — slow and expensive — and PreToolUse fires on every tool call, so the multiplication is the problem. The small-model answer belongs to the deprecated prompt handler, which is exactly why the two get confused. Agent handlers are not restricted by event, and the per-turn answer inverts the frequency: turn events fire once a turn, tool events fire constantly.

  5. A hook opens its session's socket, then runs a command that takes 90 seconds, then writes the message. On any platform, what happens?

    1. The connection is dropped, because it did not send a complete line within 30 seconds
    2. The message arrives after 90 seconds, since the socket buffers partial output
    3. The message arrives immediately and the command's output follows it later
    4. The session refuses the message because the sender did not identify itself
    Show answer

    A. The connection is dropped, because it did not send a complete line within 30 seconds

    A connection that has not sent a complete line within 30 seconds is closed, so the fix is to capture the slow output first and open the connection only when the message is ready. The buffering answer is the natural expectation from ordinary sockets and is the trap. Nothing is delivered early, and the identity question is a different requirement — an auth line is mandatory on native Windows, but that is about the first line, not about timing.

  6. A PostToolBatch hook blocks. Where exactly does the loop stop?

    1. At the batch boundary, before the next model turn
    2. Immediately, cancelling the tool calls still running in the current batch
    3. After the turn ends, before the next prompt
    4. It does not stop anything; only PreToolUse can block
    Show answer

    A. At the batch boundary, before the next model turn

    PostToolBatch sits between batches, and blocking there stops the loop before the next model turn — a checkpoint on the batch, not a kill switch inside it. The cancel-the-batch answer is the tempting one, because it is the kind of thing you wish a batch hook could do; the event fires after the calls, so there is nothing left to cancel. Turn end is Stop, and the last option contradicts the event table.
