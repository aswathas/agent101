LEARN · PHASE 12 · LESSON 80

The Completion-Order Gotcha

A fan-out hands back results in the order you asked for them. It tells you

Type
Learn
Prerequisites
Lesson 79 (`parallel()` vs `pipeline()`)
Time
~40 minutes

Learning Objectives

  • Name the two orders in a fan-out and say which one the returned array uses
  • Spot the side channels that silently record arrival order instead
  • Keep a failed agent's slot aligned with its input instead of filtering it away
  • Predict which agents rerun after a stop, and what reordering a script does to a relaunch

The Problem

This repo ran a parallel authoring pass: one agent per phase, each in its own worktree, merged in catalog order. Then the test suite came back red.

The obvious reading was that the agents had broken something. Three agents had written into three separate checkouts, so a red suite looked like three workers each failing in the same way — which is a strange-enough coincidence that it reads as a real signal about the work.

It wasn't. The suite was red because of a wrong glob in package.json. The runner was misconfigured. The work was fine.

Here is the part worth the lesson. Nothing about the failure was caused by running things in parallel. But parallelism was what made the misattribution feel obvious — many workers, one red result, so a worker must have done it. The evidence arrived in one order; the cause lived somewhere else.

The completion-order gotcha is the same shape, one level down. You get a set of results back, and the array does not carry the thing you assume it carries. Read the wrong field as the identity of a result and every downstream conclusion is attached to the wrong piece of work — plausibly, and with good evidence.

The Concept

A fan-out has two orders, and only one of them is data.

Declared order is the order you wrote the tasks in. It is what the returned array follows.

Finish order is when each agent actually stopped. It is real, and you can watch it happen in /workflows — one agent's row goes green while three others are still running. It is not attached to any result you receive.

That gap is fine as long as nothing else in your run records order. The moment something does, you have two orderings and one of them is a lie.

The side channels that record arrival order

Every one of these is a thing you will reach for naturally, and every one of them is finish order:

  • An array you .push() to from inside the job instead of writing to a slot
  • A log line, or a counter you increment as each result lands
  • A file each agent appends a line to
  • Your own reading of /workflows while the run is going
  • A sort() you apply because the results "looked jumbled"

None of them is wrong. They are simply a different axis from the one the return value uses. If you have both, you now have to join them, and the join is the whole problem.

The slot is the only identity

A fan-out result has one nameable property: its position. That is why null sits in the slot rather than being dropped — a lost agent leaves a hole where it was, so the file at index 41 is still reported at index 41.

The positional rule is documented directly for pipeline(), whose results array keeps each null in place. For parallel(), both that it runs a set of tasks at once and that it waits for all of them are documented; the array's exact ordering is the part worth confirming in your own build rather than taking on faith. What does not depend on the reading: what you are handed is not completion order, and a hole must not be closed.

Which means this line is destructive:

return audits.filter(Boolean)

The docs' own example ends that way, and for a run that has no failures it is harmless. After one null, everything after it shifts down by one. Slot 41 no longer belongs to file 41. Nothing errors. The list is shorter and every label in it is now wrong for at least one later entry.

The safe forms are the boring ones:

// Keep the slot, keep the meaning.
return list.map((file, i) => ({ file, verdict: audits[i] ?? null }))

// Drop the holes, but bind them first.
return list
  .map((file, i) => ({ file, verdict: audits[i] ?? null }))
  .filter((row) => row.verdict !== null)

Both keep the file name attached to the verdict. That is the whole difference.

Absence is not emptiness

null means lost — stopped, stalled out past every attempt, or an unrecoverable error. An empty result means the agent ran and found nothing.

If your workflow can legitimately produce nothing, you need both to survive, or "no findings" becomes indistinguishable from "no answer". A schema on the agent() call is how you make the empty case well-formed; checking for null is how you detect the missing case.

Then there is resume, where order is load-bearing in a second way

A run is not a set of agents. It is a sequence of agent calls, and a relaunch compares that sequence against the last one:

  • An agent whose call matches the previous run returns its saved result
  • The first agent whose prompt differs runs again — and so does every agent after it, including ones that had completed
  • An agent that was still running when you stopped the run starts over
  • A failed agent runs again, and everything after it runs again too

Read the second bullet again. A failure in the middle of a fan-out reruns work that already finished. If a script started A, B, C, D and B failed, a relaunch returns A from the saved results and runs B, C, and D again.

And the sequence — not the individual prompt — is what is compared. If you edit the script so it starts A, C, B, D, then the second call is now C where it used to be B. The first divergence is at position 1, so A comes back saved and C, B, and D all run again.

The reframe: a fan-out returns results in the order you asked, never in

the order they arrived — so anything you build that keys a result by when it

came back has renamed every result, and resume keys a run by where each call

sits in the sequence.

Build It

This is the shape the phase's practice module asks for. Build it here first.

1. Write a propose → verify workflow

Five proposals for one problem, and one independent verifier per proposal. The point of the pattern is that the verifier does not share the proposer's context, so a weak idea does not get a friendly review.

Give each proposal a marker that a verifier can echo:

use a workflow to propose five different approaches to rate-limiting our API,
then have an independent verifier critique each proposal. Each proposal must
carry a unique marker like PROPOSAL-3, and each verifier must return which
marker it verified.

✅ You pass when the script contains one fan-out for the proposals and a second fan-out for the verifiers, and you can point at the line that passes a proposal into its verifier.

2. Join the two badly, on purpose

Make the join use arrival order. Do it the way it actually happens: filter, then zip.

const proposals = await pipeline(promptList, p => agent(p, { label: p }))
const verdicts  = await pipeline(
  proposals.filter(Boolean),
  p => agent(`Critique this approach: ${p}`, { label: 'verify' }),
)

return verdicts.map((v, i) => `${proposals[i]} → ${v}`)

There is a real defect in there and it is not the filter alone. proposals[i] is being used as the identity of verdicts[i] while verdicts was built from a shortened list.

✅ You pass when you can say, without running it, exactly what happens to the pairing after the first null.

3. Make it fail for real

Run it, then stop one of the middle verifiers in /workflows by selecting it and pressing x. Let the run finish.

If nothing was lost, stop a proposer instead and re-run. Keep going until the output contains a null somewhere in the middle of a fan-out.

✅ You pass when you have printed at least one line where the proposal name and the verdict disagree — a verdict about PROPOSAL-4 printed next to PROPOSAL-2 — and you can point at the array index where the misalignment began.

4. Fix it by binding before you drop

Rewrite the join so the file name is attached before anything is filtered:

const rows = proposalList.map((p, i) => ({ proposal: p, result: proposals[i] ?? null }))
const verified = await pipeline(rows, ({ proposal, result }) =>
  result === null
    ? null
    : agent(`Critique this approach: ${result}`, { label: proposal }),
)
return rows.map((r, i) => `${r.proposal} → ${verified[i] ?? 'MISSING'}`)

Rerun, stop a middle agent again, and read the output.

✅ You pass when every printed verdict names the proposal it actually critiqued, or prints MISSING against the one that was lost — with no line pairing a verdict with the wrong proposal.

5. Prove absence is not emptiness

Add a proposal that is deliberately vacuous — "take no action" — and a verifier instructed to return an empty finding when a proposal is unobjectionable.

✅ You pass when your output distinguishes three states: a verdict, an empty verdict, and MISSING, and you can say which one a null slot means.

6. Feel resume, in the sequence

This is the experiment that makes the last section of the Concept land. You need a fan-out long enough that it does not finish instantly.

  1. Run the workflow. Let the middle fan-out run, then stop the whole run.
  2. Ask Claude to relaunch it with the same script. Watch which agents return instantly and which start again. Write down what you saw.
  3. Open the script and swap two adjacent entries in the list you iterate over. Relaunch.
  4. Write down how many agents returned a saved result the second time.

✅ You pass when you can name the first position at which the two sequences diverged, and say how many agents reran because of a one-line reorder.

Do not trust the narrative here over your own observation. The replay rules are

documented behaviour and they are version-gated; you just falsified or confirmed

them on your machine. Verified against

the workflows page on 2026-10-15,

and Lesson 81 covers the retries and stall windows that decide when an agent

gets re-run at all.

Exercises

  1. Take a workflow you already wrote and find every place a result is ordered by anything other than its position in the input list. ✅ You pass when you can name each one and say what would print if a result in the middle were lost.
  1. Write the same join twice — once with a marker echoed by the verifier, once by index. Break both with a stopped agent. ✅ You pass when you can say which one failed silently and which failed visibly, and which you would rather debug at 2am.
  1. A fan-out starts A, B, C, D. B fails. You relaunch. Write down which agents reuse a saved result before you run it. Then run it and compare. ✅ You pass when your prediction matches, or your note explains exactly which rule you had backwards.
  1. Find a claim in this lesson you have not personally verified, and design the smallest experiment that would settle it. ✅ You pass when the experiment has an observable outcome you could write down, rather than a feeling about whether it worked.

Key Terms

TermWhat people sayWhat it actually means

finish order"the order it finished"When each agent stopped. Visible in /workflows; attached to no result you receive
slot"an entry"A position in the returned array. The only identity a result has without a label
null in a slot"it failed"A lost agent. Stopped, stalled past every attempt, or unrecoverable. Kept in place

first divergence"the change"The earliest position where the new run's sequence of calls differs. Everything from there reruns

What this lesson skipped

The runtime's numbers. How many agents run at once, how many a call may hold, how many stall restarts an agent gets before it is declared lost. All of that decides when a slot becomes null, and all of it is Lesson 81.

Prompt caching between fan-out members. Agents sharing a prefix read each other's cache, which is why the runtime staggers a fan-out's first requests by up to five seconds by default. It is a cost mechanism, not an ordering one, and it matters when a run is expensive rather than when it is wrong.

Deterministic replay in detail. Why Date.now() and Math.random() throw inside a script, and what args is for, is Lesson 78's rule and this lesson's consequence.

Joins that span runs. Nothing here covers merging results from two separate runs. If you need it, the second run's sequence starts from zero and the first divergence rule applies from the top — try it on a small list before you trust a big one.

Check yourself

6 questions. Answer before you reveal — recognising the right option is not the same as being able to produce it.

  1. A pipeline() over a list of 412 file paths returns 412 entries, and 16 of them are null. The verdict for the file at input index 41 is at which position?

    1. Index 41 — a lost agent leaves its slot in place, so positions still line up with the input list
    2. Index 25 — 16 entries ahead of it were lost, so the real results shift forward
    3. Wherever it finished relative to the other results
    4. It cannot be determined from the array alone
    Show answer

    A. Index 41 — a lost agent leaves its slot in place, so positions still line up with the input list

    The runtime substitutes null in place of the agent's result, so the array keeps one entry per input and the index still identifies the file. The shifted-index answer is the tempting one because it describes what a filtered array looks like — and that is precisely the bug this lesson is about. Finishing order is not attached to the array at all, and the mapping is determinable; assuming it is not is what forces people into a costly re-run.

  2. results.filter(Boolean) is used, then zipped positionally with the input list. One agent in the middle was lost. What goes wrong?

    1. Nothing throws, and every entry after the dropped one is paired with the wrong input
    2. The runtime raises an error, because the two arrays now have different lengths
    3. The zip throws, but only if more than one entry was dropped
    4. Nothing goes wrong positionally, though legitimate empty results also get dropped
    Show answer

    A. Nothing throws, and every entry after the dropped one is paired with the wrong input

    filter removes the hole and closes the gap, so the result list is now one shorter than the input list from that point on — and every later pairing is off by one or more, silently. The 'empty results also get dropped' answer is half right and therefore the most dangerous: yes, empty strings are removed too, but the pairing absolutely does break, which is the part that matters. JavaScript's zip has no length check here, so nothing throws, and a single dropped entry is enough to misalign everything after it.

  3. One verifier's slot is null. Another verifier returned "" because the proposal had no issues. What is the difference?

    1. null means the agent was lost and never returned; "" means it ran and found nothing
    2. Both mean the same thing — no verdict was produced
    3. null means the verifier disagreed; "" means it timed out
    4. null is an empty result the runtime normalised; "" is an agent that was stopped
    Show answer

    A. null means the agent was lost and never returned; "" means it ran and found nothing

    A null slot is the runtime's placeholder for an agent that was stopped, stalled past every attempt, or hit an unrecoverable error — the work was not done. An empty result is a verdict with nothing in it: the work was done and the answer is nothing. Collapsing the two is the failure mode from the opening story, because 'no findings' and 'no answer' then look identical in the report. The remaining options swap the two meanings or invent a normalisation the runtime does not perform.

  4. A workflow's script starts agents A, B, C, D in that order. On the last run, B failed and C and D completed. You relaunch with the unchanged script. What runs again?

    1. B, C and D — the first divergence is at B, and everything after it reruns
    2. Only B, since C and D have saved results
    3. All four, because any failure invalidates the run
    4. Nothing — the runtime resumes from the failure point and only B is retried
    Show answer

    A. B, C and D — the first divergence is at B, and everything after it reruns

    A relaunch returns saved results up to the first agent whose call differs from the previous run, then runs everything from there on. A failed agent counts as that divergence, so the completed work after it is thrown away and repeated. The 'only B' answer is the intuition almost everyone has — that a retry is local — and the docs are explicit that it is not. 'Nothing' inverts the rule, and 'all four' overstates it: A came back from the saved results, so the divergence was not at the start.

  5. Six agent calls all completed on the last run. You append a seventh call at the end of the script and relaunch. What happens?

    1. The first six return saved results and only the new seventh runs
    2. All seven run again, because the script changed
    3. The runtime refuses the relaunch, since the script no longer matches the saved run
    4. The seventh runs first, then the six replay in their original order
    Show answer

    A. The first six return saved results and only the new seventh runs

    Replay compares the sequence of calls and stops matching at the first position where it differs — and appending at the end means the first six positions are unchanged. Contrast that with inserting a call in the middle or reordering the list: the divergence moves earlier, and every agent from there on reruns even though it had completed. The reject answer is the tempting wrong one because there is a real refusal nearby — a relaunch fails with a 'nothing to resume' error when the saved results cannot be found at all — but a changed script is not that case.

  6. While a pipeline() fan-out runs, /workflows shows B finishing first, then C, then A. When the run finishes, which order does its results array use?

    1. The order the tasks were written in — the progress view's completion order is not the array's order
    2. B, C, A — the same order the view showed them finishing
    3. Sorted by duration, longest first
    4. The runtime does not define an order, so it can vary between runs
    Show answer

    A. The order the tasks were written in — the progress view's completion order is not the array's order

    A pipeline() returns one entry per item in the order of the list you passed, and completion order exists only in the view. The B, C, A answer is exactly the mistake this lesson is named for, and it is a reasonable inference from watching the run — which is why the view is a trap rather than a tool here. There is no duration sort, and the order is not undefined: it is the input list's order.
