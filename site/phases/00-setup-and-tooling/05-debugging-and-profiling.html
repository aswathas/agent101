LEARN · PHASE 00 · LESSON 5

Debugging and Profiling

When the agent goes wrong, the agent is rarely the cause. The environment is.

Type
Learn
Prerequisites
Lesson 1 (Dev Environment)
Time
~30 minutes

Learning Objectives

By the end of this lesson you can:

  • Name three categories of "agent problem" that turn out to be environment problems
  • Read a slow run to find the actual hot step, instead of guessing where it spends time
  • Isolate a failure to one variable by changing one thing at a time
  • Distinguish "the model was wrong" from "the model was given wrong inputs"

The Problem

You ask the agent to do a task. It does it badly. You ask again. It does it badly in a different way. After the third try you conclude: "the agent is bad at this."

Most of the time, no. The model did what the inputs told it to do. The failure was upstream: a wrong folder, a stale dependency, a missing env var, a slow script you never measured. The agent inherited a broken environment and produced a broken result. Calling that "an agent problem" is the most expensive mistake in this course.

Three habits close most of that gap. This lesson teaches them.

The Concept

The reframe: Most agent problems are not agent problems. They are environment problems. Reading errors, profiling a slow run, and isolating a failure to one variable are the skills that turn an hour of guessing into a minute of looking.

The rest of this lesson is those three skills. They are not agent-specific. They are the same skills you would use debugging any program. The reason they matter here is that with an agent, the temptation to skip them is strong — you can always say "try again" and let the model iterate. Sometimes that works. Often it loops on the same upstream cause and burns your time and tokens.

The three categories of "not the agent"

When a session goes wrong, place the cause in one of three boxes. Most sessions end with the cause in box 1.

Box 1: environment. The folder is wrong. The API key is missing. A cached build is stale. A dependency is one version off. These never fix themselves by retrying the prompt.

Box 2: inputs. The prompt is vague. The context the agent sees is out of date. The spec is ambiguous. These fix themselves by writing a better prompt, not by asking the model to try harder.

Box 3: the model. Rarely. The model genuinely does not have the capability. When it is box 3, no amount of prompt rewriting will help; you need a different model or a different task.

The skill is moving the cause down the funnel. Most of your time is in box 1.

Build It

The work is three short exercises against your own dev environment. Do them in order. Each takes a few minutes.

Exercise 1: Prove the folder before blaming the agent

Open a fresh session. Ask the agent to list files in the current directory. It will print a list. Now run pwd from your terminal yourself. Compare.

If the two folders disagree, every subsequent thing the agent says is suspect. The fix is not "retry the prompt." The fix is cd to the right place, restart the session, and try again.

Pass: in one sentence, you can say whether the agent's working folder matched yours, and what you would do if they did not match.

Exercise 2: Read a slow run

Pick any task that took longer than you expected — a build, a test suite, a model call, an install. Have it run while you watch the timestamps.

Three readings:

  1. Total wall time. How long it actually took. Round number, not a guess.
  2. Per-step time. Which step took the most. Often a single step accounts for most of the wall.
  3. What you assumed vs what happened. Did the slow step match what you thought would be slow? Usually no.

If the slow step is a model call, count the calls. A loop of 30 model calls at 3 seconds each is a 90-second session that you thought was one task.

Pass: you can name the slowest step and how long it took, in seconds.

Exercise 3: Isolate one variable

Take a task that "sometimes works." Reproduce it twice. Each time, change exactly one thing. Examples of "one thing": a different folder, a different env var value, a different file content, a different prompt. If the result changes between run 1 and run 2, the thing you changed is in the causal path. If it does not, it is not — keep it out of the picture.

Two-run isolation beats five-run guessing. After two runs you know the cause is or is not in the variable you changed.

Pass: for a flaky behavior, you can name one variable whose change flipped the result, and one variable whose change did not.

Exercises

  1. Classify a real failure. Take any past session that ended badly — your own, or one you remember. Classify it into box 1, 2, or 3. Be honest. Pass: you can defend the classification in two sentences, naming the specific evidence that placed it.
  1. Profile a real run. Run any agent task end-to-end while watching timestamps. Record the wall time and the slowest step's time. Pass: in a single sentence you can say "total time was X, the slow step was Y at Z seconds."
  1. Two-run isolation. Find something flaky. Run it twice, changing exactly one variable. State which variable was in the causal path. Pass: you can name the one variable whose change correlated with the outcome change, and at least one variable whose change did not.
  1. Catch yourself guessing. Next time the agent fails, before re-prompting, write down what you believe the cause is. Then read the actual evidence — error text, folder, version, file content. Was your guess right? Pass: at least one of your guesses was wrong, and you can name what the evidence actually said.

Key Terms

What people sayWhat it actually means
"The agent is bad at this."Almost never true on the first failure. The agent inherited an environment and ran in it. The misconception is that bad output implies a bad model. It usually implies bad inputs or a bad environment.
"Just retry the prompt."A retry changes one random thing. If the cause is in the environment, retry changes nothing and burns tokens. Isolate one variable instead.
"It's slow."Unmeasured. Until you time a step, "slow" is a feeling, not a fact. Profile once. Then you know which step is the hot one.
"The model hallucinated."Sometimes. Often the model used a stale or wrong input and produced a coherent-looking wrong answer. Plausible-wrong is an input problem.
"It worked yesterday."Something changed. Find it. Two-run isolation finds changes; guessing does not.
"Reproducible."Means: same inputs, same outputs. To prove it, change one variable and see if the output changes. If yes, the variable is in the causal path.

What this lesson skipped

No debugger attach. No flame graphs. No language-specific profilers. No agent-specific tracing tools. The lesson stayed at the level of "read the error, time the step, change one thing." Those three habits cover most of what goes wrong in a session and require no special tooling.

We also skipped the question "when is the model actually the problem?" That is real and rare; the lesson's claim is that it is rare, not that it never happens. When three retries and a clean environment still fail, the model may be the cause. Change the model, or change the task.

Skipped: how to write a good failure report for a human reviewer. That is its own lesson.

Check yourself

3 questions. Answer before you reveal — recognising the right option is not the same as being able to produce it.

  1. After four agents edit four files in parallel, the suite is red. You have never seen it green. What should you check first?

    1. Revert all four agents' work — four simultaneous edits is always wrong
    2. Whether the test runner is itself correct: path globs, working directory, config, and whether tests actually ran
    3. Which agent has the most commits and start from there
    4. Run the suite with more verbose output
    Show answer

    B. Whether the test runner is itself correct: path globs, working directory, config, and whether tests actually ran

    A red suite caused by a wrong glob looks exactly like failing code — this repo lost an afternoon to precisely that. Before concluding anything about the agents' work, confirm the runner matches real test files and actually ran tests. Verbose output is a good second step, not the first.

  2. An agent "fixed" a failing test. The error message text changed completely, but the test still fails. What has most likely happened?

    1. The fix was correct; the message just got clearer
    2. The failure was moved, not fixed — the fix needs to be proven with the identical command run before and after
    3. The test cache is stale and needs clearing
    4. The agent changed the test itself, which always counts as fixing
    Show answer

    B. The failure was moved, not fixed — the fix needs to be proven with the identical command run before and after

    A real fix changes observable behaviour, so the identical command produces a different result. Only the wording changing is the classic signature of a failure relocated rather than removed — and it will resurface somewhere less convenient.

  3. You must hand an agent a failing build. Which message gets the closest fix on the first attempt?

    1. "The build is broken on the API layer, please fix it"
    2. "Run npm run build. It exits 1. Verbatim output: [30 lines]. The error mentions undefined parseHeaders in src/api/client.ts:88"
    3. "Everything worked yesterday. It doesn't work now."
    4. "Fix the bug in the API code"
    Show answer

    B. "Run npm run build. It exits 1. Verbatim output: [30 lines]. The error mentions undefined parseHeaders in src/api/client.ts:88"

    An agent can only debug from evidence, and evidence is the command plus its verbatim output — which already names the file, the line and the symbol. The other three are descriptions of your feeling about the problem; the agent must reverse-engineer the facts from them, and each round trip costs a full cycle.
