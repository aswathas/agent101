LEARN · PHASE 01 · LESSON 11

Latency, Cost, and Rate Limits

You can predict whether a session will be slow or expensive *before* you start

Type
Learn
Prerequisites
Lesson 10, What "Agentic" Means
Time
~30 minutes

Learning Objectives

  • Predict whether a task will be expensive before starting it, from its shape
  • Read /usage and say what the three numbers mean, including cache reads
  • Explain why a repeated request can cost less the second time
  • Tell a rate limit, a slow command, and a cold cache apart from each other

The Problem

An agent was left running on a broad task. Twenty minutes later it came back with a diff. It was wrong — it had searched the entire tree twice and edited files nobody asked about. Twenty minutes and real tokens, gone.

Then a second run, narrower, came back in ninety seconds with the right answer.

The difference was not the model. It was the number of requests: a broad task triggers dozens of tool round trips, and each one waits on the network. Latency and cost are the same quantity viewed twice — requests × tokens per request.

Nobody had budgeted for either, because nothing on screen said what the task would cost before starting it. And when something did stall, the three possible causes looked identical from the outside: slow model, rate limit, or your own code hanging.

The Concept

Three separate things, often confused.

Latency is how long a turn takes. It stacks: every tool round trip is a network wait, and the model's own generation time is on top. A turn with ten round trips is ten waits.

Cost is tokens × price. Inputs and outputs are priced differently, and repeated context is the dominant input cost — that is Lessons 7 and 8, not a new idea here. What is new: cost is predictable from the shape of the task.

Rate limits are the provider's ceiling. You hit one and requests are refused or queued, regardless of how much you would like them to succeed.

Cost is a function of task shape, not task size

Task shapeRound tripsRelative cost
One question about a file you name1–2Low
Search a directory, report paths3–6Medium
Search a whole monorepo, read candidates, verify15+High
Any task repeated across many sessionsN × sessionsCompounding

The expensive one is not the task that does the most. It is the one that re-reads. Ten requests each carrying a full context costs ten contexts. This is why "let it figure it out" on a large repo is a budget decision.

Caching changes the arithmetic

Repeated content does not cost full price each time. Claude Code uses prompt caching so that content it has already processed is served at a reduced rate, and the cache expires on a TTL — an hour on a typical subscription, shorter in some configurations. When it expires, the next request pays full price again.

You will see this in /usage: a session with a high proportion of cache reads is a session that is working efficiently. A run of misses usually means something large changed, or you came back after a break. Not a bug — but a signal.

Three stalls, three different fixes

What you seeWhat it isWhat to do
Error naming a usage or rate limitThe provider refusedWait, or reduce concurrency
Slow, but the same every timeLikely your own command or test suiteLook at what the tool is running
Slow on the first request of a session, fast afterCold cacheExpected; it settles
Fast on first try, then stallsOutput length or thinking budgetNarrow the ask

The fourth row is worth internalising: a longer answer can be the slow part, not the reasoning.

The reframe: latency and cost are the same bill seen twice — a function of

how many round trips your task shape forces — so the way to make a task cheap

is fewer round trips carrying less, not a faster model.

Prices, TTLs, cache behaviour, and command output all move. Read the costs page and the commands reference for current values; claude --version for yours.

Build It

1. Read your own numbers

/usage

Look at three things: total cost, how much of the input came from cache, and which model did the work. Write them down. Every later judgement in this lesson is relative to these three numbers.

✅ You pass when you have all three numbers, not just the total.

2. Predict before you run

Write down, before running anything: how many round trips you expect for "explain how this repo validates lessons", and how many for "compare the branch logic in two named files".

Then run both, with /usage between them, and check your predictions.

✅ You pass when your predicted gap between the two matches the measured gap in direction and roughly in size.

3. Demonstrate the repeat-cost

Run one narrow request. Record the cost. Run it again in the same session. Record that cost too.

The second should be cheaper, because the context is cached.

✅ You pass when the second run cost measurably less, and you can say why in one sentence.

4. Watch the cache go cold

In one session run a request. Wait several minutes. Run the same request again.

Compare the two. Somewhere in between, the cached prefix expired and the second request paid full price.

✅ You pass when the second cost is higher than the first, and you can attribute the difference to the cache rather than to the task.

5. Tell a rate limit from a bug

In a session, note the exact text of any error mentioning usage or limits. Compare it with any error that was a real failure.

They look nothing alike, once you have seen both.

✅ You pass when you can quote a limit message and say what it asked you to do, without guessing.

6. Find the expensive shape in a real session

Look at /usage after a real task. Which shape dominates: many small requests, or few large ones? Say which, and what you would change about how you asked.

✅ You pass when you can name the dominant shape and one concrete change to your asking that would reduce it.

Use It

Command / conceptWhen you reach for it
/usageBefore blaming the bill; after anything expensive

Exercises

  1. Run three tasks of deliberately different shapes in one session, recording /usage between each. Sort them cheapest-first. ✅ You pass when your ordering matches the measured costs, and you can name the shape that produced the outlier.
  1. Reproduce a cache miss. Get a warm-cache number and a cold-cache number for the same request, and write down the gap. ✅ You pass when you have both numbers and can explain the difference without invoking anything you did not observe.
  1. Write down a budget for one real task — number of round trips, rough tokens — before starting it. Run the task. Compare. ✅ You pass when you have the prediction written down before the run, and the comparison, and you can say which estimate was worse and why.

Key Terms

TermWhat people sayWhat it actually means
latency"the model is slow"Wall time per turn: many network round trips plus generation. Usually round trips, not thinking.
round trip"a step"One request to the model and back. Each one re-sends context. Cost and latency both scale with the count.
rate limit"quota"The provider's ceiling. Requests are refused or queued; nothing you write changes it.
prompt cache"it remembered"Previously-processed content served at a reduced rate. Expires on a TTL, then costs full price again.
cache read"free"Reduced-rate reuse. High proportions mean efficient work; misses mean something invalidated.
tokens per million"the price"Unit pricing for input and output. Changes — read it live, never from memory.
/usage"the bill"Session cost, plan limits, and a usage breakdown. Estimated from token counts, not an invoice.

What this lesson skipped

Choosing a model to trade cost against capability. The single biggest cost lever, and it is Phase 03. This lesson gives you the arithmetic; that phase gives you the decision.

Reducing spend structurally. Hooks that filter large outputs, moving instructions out of always-loaded files, delegating large reads. All real, all dependent on concepts this phase has not established yet.

Batch and async APIs. Lower cost per token, worse latency. Irrelevant to interactive work, and not on the path this course takes.

Concurrency and throttling. How many agents can run at once before you hit limits. It arrives with parallelism in Phase 11, where you will have the arithmetic to reason about it.

Enterprise cost controls. Spend limits, workspaces, org reporting. Only relevant if you are deploying for a team, which this course does not do.

Check yourself

3 questions. Answer before you reveal — recognising the right option is not the same as being able to produce it.

  1. The same request costs less when repeated in a warm session than the first time. What is the mechanism?

    1. The second request is shorter because the model remembers and compresses your earlier wording
    2. Previously processed context is served from the prompt cache at a reduced rate, and the cache expires on a TTL
    3. Subscriptions discount the second identical request as a loyalty repeat
    4. The agent reuses the earlier tool results instead of re-running the tools
    Show answer

    B. Previously processed context is served from the prompt cache at a reduced rate, and the cache expires on a TTL

    The prompt cache is what makes a re-send cheaper: content already processed is reused at a reduced rate, until a TTL expires and the next request pays full price again. Option A describes a memory behaviour the model does not have — it re-sends the same bytes every time. Option D confuses the model-side cache with the tool layer; tool results are still re-sent either way.

  2. You have a small change to make in a 200,000-token repo. Which ask is most likely to be both fast and cheap?

    1. Investigate the repo to understand how this area works before making the change
    2. Change the named constant on the line named, then run the named test
    3. Refactor the surrounding module so the change fits the existing conventions
    4. Search for every usage of the constant across the repo, read each match's context, and update them consistently
    Show answer

    B. Change the named constant on the line named, then run the named test

    Cost and latency both scale with round trips, and each round trip re-sends the whole context. Naming the file and the test collapses the task to one or two round trips. Option A spends a full investigation on a change you could have described precisely. Option D is genuinely thorough, which is exactly why it is the most expensive — and for a single constant it is wasted effort.

  3. An agent call has been running four minutes with no output. You open the terminal and find nothing obviously stuck. What is the most useful next move?

    1. Restart the session — a stall this long always means a dead agent
    2. Classify the stall: did it stop at a usage-limit message, at your own long-running command, or at the model's first token
    3. Switch to a smaller model to get past the stall
    4. Add more detail to the prompt so the model has more to work with
    Show answer

    B. Classify the stall: did it stop at a usage-limit message, at your own long-running command, or at the model's first token

    The three stalls have different signatures and different fixes, and only one is yours to fix — a limit message, your own hanging test suite, or a genuinely slow first token are distinguishable in the transcript. Option A destroys the work for a problem that may be a five-second wait. Option C changes capability, which is not what latency is. Option D adds context to a request that has not started responding, so it changes nothing.
