LEARN · PHASE 11 · LESSON 73

Agent Teams — Mailbox, Task List, Documented Limits

You can read a team's on-disk state, name what it buys you over subagents, and

Type
Learn
Prerequisites
Lesson 72 (Subagents as Isolation); Phase 04 Lesson 31 (The Agentic Loop); Phase 06 Lesson 45 (Subagent Markdown Format)
Time
~35 minutes

Learning Objectives

  • Enable agent teams and tell whether you actually got a team or three subagents
  • Read a teammate's state from the shared task list and the mailbox, not from the panel alone
  • Say why teams add coordination but no file isolation, and what to do about it
  • List the documented limits that will bite a real run, and which one bites first

The Problem

You asked for three teammates to land a refactor across nine files. The panel filled with three names. It felt coordinated.

Then two of them edited the same file. Agent teams do not put teammates in separate checkouts — they share the repository, the way parallel subagents do. The shared task list told each teammate what to do; nothing told them which directory to do it in. One teammate's change overwrote another's, and the overwrite was invisible until the diff.

The other trap came later. You resumed the session the next morning and asked the lead to check on the researcher. The researcher no longer existed. /resume does not bring in-process teammates back.

Neither failure is a bug. Both are documented limits, and both come from reading "team" as "safety" instead of "coordination."

The Concept

An agent team is four parts, not one.

PartWhat it is
Team leadThe one session you talk to. It plans, assigns, and synthesizes. Fixed for the team's life.
TeammatesSeparate Claude Code sessions, each with its own context window.
Task listA shared list of work items: pending, in progress, completed, with dependencies.
MailboxA per-agent inbox for messages between agents.

Two of those parts live as files you can read. A team is named session- plus the first eight characters of the session ID:

~/.claude/teams/{team-name}/config.json          runtime state (don't hand-edit)
~/.claude/teams/{team-name}/inboxes/{name}.json  each agent's mailbox
~/.claude/tasks/{team-name}/                     the shared task list

The task list is the coordination. A teammate that finishes a task picks up the next unblocked one on its own, or the lead assigns it. Claiming uses file locking so two teammates can't grab the same task — but the lock is on the task, not on the file the task edits.

Note what the diagram does not contain: any boundary between the files A and B write. That boundary is your job to draw before you spawn.

Teams versus subagents

Both give each worker its own context. They differ in who coordinates:

SubagentsAgent teams
CoordinatorClaude, turn by turn, inside one sessionA lead session, over a shared task list
Workers talk to each otherOnly if Claude named themYes, directly, by name
File isolationShared dir by default; isolation: worktree availableNone. Partition the files yourself.
Best forFocused tasks where you want the resultWork that needs discussion and self-assignment
CostLowerHigher — each teammate is a full session

Turning it on changes ordinary delegation

Teams are experimental and off by default. Enable them with an environment variable in settings.json:

{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}

While enabled, a subagent that Claude names launches as a teammate. Claude names subagents on its own for later messaging, so a team can form during delegation you never framed as team work. If you wanted a plain subagent, that is a surprise worth knowing before it happens.

Spawning teammates also needs an interactive session. With claude -p or the Agent SDK, Claude doesn't spawn teammates and a named subagent stays a subagent.

The limits that bite, in the order they bite

  1. No worktree isolation. Partition files between teammates. This is the one that corrupts work.
  2. Task status can lag. A teammate finishes but doesn't mark the task done, so dependents stay blocked. Nudge the lead.
  3. No session resumption with in-process teammates. After /resume, tell the lead to spawn new teammates. Messages to the old ones go nowhere.
  4. One team per session, and no nested teams. Only the lead manages the team; teammates can't spawn teammates.
  5. No background subagents from in-process teammates. A teammate's background work can't outlive the lead's process.
  6. Shutdown is slow. A teammate finishes its current call first.
  7. Split panes need tmux or iTerm2. The default in-process mode works anywhere.

The reframe: an agent team is a shared task list plus a mailbox — it buys

coordination, not isolation, so the files it touches still need partitioning.

Agent teams are experimental and the limit list moves. Read Orchestrate teams before relying on a specific limitation; the version-gated notes on that page change fastest.

Build It

1. Turn teams on and confirm they're on

Add the env block above to .claude/settings.json, restart, and ask for two teammates on a small, read-only task. Run /tasks and open the task list with Ctrl+T.

✅ You pass when the task list shows tasks with owners, not just a chat log.

2. Read the on-disk state

Before you close the session, find the team directory:

ls ~/.claude/teams/ ~/.claude/tasks/

Open a mailbox file and the config. Then change nothing — the config is runtime state and your edits get overwritten.

✅ You pass when you can point at the mailbox for one teammate and name the file that holds the task list.

3. Prove the file-sharing limit

Give two teammates overlapping file lists on purpose. Watch what lands. Then give them disjoint lists.

✅ You pass when you can show the overlap producing a lost or merged change, and the disjoint split producing none — and explain that the difference was partitioning, not the task list.

4. Hit the resumption limit

Finish a run with an in-process teammate, exit, and --resume. Ask the lead to message that teammate.

✅ You pass when you can report what happens to a message sent to a teammate that resumption did not restore.

Use It

SituationMove
Work needs discussion and self-assignmentAgent team.
Work is independent and you just want resultsSubagents. Cheaper, no coordination overhead.
Two teammates might touch one fileGive them disjoint paths. Teams won't isolate them.
A dependent task is stuckThe status lagged. Tell the lead to nudge or update it.
You need to define a reusable teammate roleA subagent definition, referenced as the agent type.
You want to reach one teammate directlySelect it in the panel (in-process) or click its pane (split).
You need to pass findings between your own sessionsCross-session messaging. Phase 12, Lesson 77.
Quality gates on a teammate's workHooks: TeammateIdle, TaskCreated, TaskCompleted. Phase 08.

Exercises

  1. Spawn a three-teammate team on a read-only research task and one on an implementation task. For each, write the file boundaries you'd need before spawning. ✅ You pass when the research task needs none and the implementation task has an explicit per-teammate path list.
  1. Deliberately let two teammates share a file. Record the diff and identify whose change was lost. ✅ You pass when you can name the lost change and the mechanism that would have prevented it (worktrees, per Lesson 74).
  1. Resume a session that had in-process teammates and try to message one. ✅ You pass when you can state the documented behavior from your own run, not from this page.

Key Terms

TermWhat people sayWhat it actually means
agent team"parallel agents that cooperate"A lead session plus peer sessions sharing a task list and a mailbox. Coordination, not isolation.
team lead"the main agent"The one session you talk to. Fixed for the team's life; can't be transferred.
task list"the plan"Shared work items with states and dependencies, under ~/.claude/tasks/. Claiming is lock-protected; the files aren't.
mailbox"the chat"A per-agent inbox JSON under ~/.claude/teams/. How teammates message each other by name.
self-claim"picking up work"A teammate grabbing the next unblocked task without the lead assigning it.
idle notification"it told me it's done"The message a teammate sends the lead when it stops, including its result.
task status lag"it's stuck"A finished task marked not-done, blocking its dependents.
named subagent"a teammate"With teams on, a subagent Claude names launches as a teammate. The cause of teams forming unasked.

What this lesson skipped

Worktrees. The fix for the file-collision limit. That is Lesson 74.

Workflows. When the plan itself should be a script instead of a lead's turn-by-turn judgment. All of Phase 12.

Cross-session messaging. Talking between sessions you run yourself, outside any team. Phase 12, Lesson 77.

Hooks for teams. TeammateIdle, TaskCreated, and TaskCompleted are hook events; the hook model is Phase 08, and team hooks are a Phase 12 topic.

Cost. Teams use significantly more tokens than a single session. Phase 03, Lesson 11 owns the budget.

Check yourself

4 questions. Answer before you reveal — recognising the right option is not the same as being able to produce it.

  1. Two teammates finish their assigned tasks, then each claims the next unblocked item on the shared list without being told. Two other teammates are editing unrelated files. What is the single thing you must have set up to keep their edits from colliding?

    1. Nothing — the shared task list's file locking prevents two agents editing one file
    2. Disjoint file ownership, because teams isolate tasks but not files
    3. A bigger model for the lead, so it notices overlaps
    4. Turning off self-claim, so only the lead assigns work
    Show answer

    B. Disjoint file ownership, because teams isolate tasks but not files

    The lock protects the task, not the file the task edits, so two agents can hold different tasks that both write one path. Teams give no file isolation, so you partition ownership. A stronger lead still can't guarantee disjoint writes. Disabling self-claim changes who assigns work, not where they write.

  2. You enable agent teams for a project and then ask Claude to do a small side task. Without your asking for a team, a worker is launched as a teammate with a name. Why?

    1. Enabling teams makes every tool call spawn a teammate
    2. Claude names subagents on its own, and with teams on a named subagent launches as a teammate
    3. The teammate is actually a forked subagent that inherited your conversation
    4. CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS forces the general-purpose agent to be a teammate
    Show answer

    B. Claude names subagents on its own, and with teams on a named subagent launches as a teammate

    Claude names subagents to message them later; while teams are enabled, a named subagent becomes a teammate, so teams can form during ordinary delegation. Not every tool call spawns a teammate. A fork inherits your conversation; this worker is a teammate, which does not. The env var enables teams; it doesn't rewrite the general-purpose agent's type.

  3. You resume a session the next day. The lead says it messaged the researcher teammate to confirm a finding, and no reply arrived. Nothing errored. What is happening?

    1. The mailbox file was corrupted, so the message was dropped
    2. In-process teammates are not restored on resume, so the lead messaged one that no longer exists
    3. The researcher is idle and hiding; send it another message to wake it
    4. The lead's permission mode blocked outbound messages
    Show answer

    B. In-process teammates are not restored on resume, so the lead messaged one that no longer exists

    Session resumption does not bring back in-process teammates, and the lead may still try to message them — the documented fix is to have the lead spawn new teammates. Hidden-idle rows apply within a live session, not after a resume. Mailbox corruption reports errors, and permission mode governs tool approvals, not peer messages.

  4. A five-teammate team is running a broad code review, and one dependency task sits in 'in progress' although the work is visibly done. What should you do first?

    1. Delete the stuck task, since its dependents are unreachable anyway
    2. Assume the teammate crashed and spawn a replacement
    3. Update the task status or ask the lead to nudge the teammate, because task status can lag
    4. Switch the team to split-pane mode so you can watch that teammate
    Show answer

    C. Update the task status or ask the lead to nudge the teammate, because task status can lag

    Task status lagging is a documented limitation: a teammate sometimes fails to mark a task complete, which blocks its dependents. Check the work is done, then fix the status or nudge the lead. Deleting the task discards the dependency structure. Spawning a replacement is a bigger move than the lag warrants. Display mode has nothing to do with task status.
