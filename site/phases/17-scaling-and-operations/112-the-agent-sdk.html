LEARN · PHASE 17 · LESSON 112

The Claude Agent SDK

You can put the same agent loop inside your own program — and say which of

Type
Learn
Prerequisites
Lesson 111, Headless / Non-Interactive Mode
Time
~35 minutes

Learning Objectives

  • Say what the Agent SDK is, using the loop you already know as the anchor
  • Recognise when a claude -p subprocess is enough and when you need the library
  • Write and run a minimal SDK agent that completes one task
  • Get validated structured output instead of parsing prose
  • Decide tool approval in code, not by hand
  • Name the things the terminal did for you that the SDK makes you own

The Problem

You built a small product feature on claude -p. It shelled out, parsed the text it got back, and displayed it. It worked for a month.

Then the model changed a sentence and your parser broke. There was no error — just a blank panel in your UI because a regular expression missed. You wanted the agent inside your program, and instead you had a stringly-typed pipe to a terminal tool that happens to be a program.

The pain: the CLI is an interface for a person. Your application is an interface for a program. Scraping the first to serve the second works until the text it relies on moves.

The Concept

The Agent SDK is Claude Code as a library. Same agent loop, same built-in tools, same permissions, sessions, hooks, subagents, and MCP — driven from Python or TypeScript instead of a prompt.

Read the middle box carefully. The SDK runs Claude Code's binary in a subprocess. It is not a re-implementation of the loop in a language runtime; it is a control surface over the same engine, which is why the capabilities below match the tool you already use.

What you get for free

CapabilityWhat it doesWhere it comes from
Built-in toolsRead, write, edit files, run commands, search the webThe tools you met in Phase 04
PermissionsWhich tools run, which need approvalThe permission system, now with a callback
SessionsKeep context; resume or fork laterSession persistence you met in Phase 04
HooksRun your code at lifecycle pointsPhase 08, wired from your app
SubagentsIsolated, specialised helpersPhase 06
MCPExternal tools and dataPhase 07
Skills, commands, memoryLoad from .claude/ and ~/.claude/Phases 05 and 10
PluginsPackage the above and load by pathPhase 09

What becomes yours to build

The terminal did several jobs for you. In the SDK, they move into your code:

  • Approvals. In the terminal, a prompt appears and a person answers. In the SDK, you supply a canUseTool callback — or a permission mode — and the decision is code.
  • Hosting. The SDK starts a subprocess. Who supervises it, restarts it, and isolates tenants is your deployment problem.
  • Session storage. Resuming needs somewhere to keep the transcript.
  • Auth. Third-party products built on the SDK use an API key, not a claude.ai login. Anthropic does not permit offering claude.ai login or rate limits to your own users without prior approval.
  • Output shape. If you need typed data, ask for it. The SDK supports structured outputs via a schema, and custom tools via an in-process MCP server, so you stop scraping.

When the SDK is overkill

The SDK is one of two ways to run the loop from code, and often the plainest one wins:

You want toReach for
Run a task and read a result inside a script or CI jobclaude -p --output-format json (Lesson 111)
A typed, in-process agent with callbacks and structured outputThe Agent SDK (this lesson)
Call the Claude API directly and write the tool loop yourselfThe Client SDK — different product, more control
Let Anthropic host the agent and its sandboxManaged Agents — different product, less to run

The reframe: the Agent SDK does not give you a new agent — it hands you

the loop and takes away the terminal, so everything the terminal quietly did

for you (approvals, session storage, isolation, auth) becomes something you

build.

A note on versions. The SDK is the fastest-moving surface in this course. Package names, option shapes, and entry points change often. Learn the capabilities from this lesson and take the exact signatures from the Agent SDK docs and the quickstart rather than memorising them here.

Build It

Install the SDK for your language, set an API key, and build the smallest agent that does real work on a real file.

  1. Install and authenticate.

```bash # TypeScript npm install @anthropic-ai/claude-agent-sdk # Python pip install claude-agent-sdk

export ANTHROPIC_API_KEY="sk-ant-..." ```

  1. Ask for one task in one file. The query function streams messages as the agent works. (Treat this shape as illustrative; confirm it against the current quickstart.)

```ts import { query } from "@anthropic-ai/claude-agent-sdk";

for await (const message of query({ prompt: "Find the bug in auth and fix it. Explain the fix in one line.", options: { allowedTools: ["Read", "Edit", "Bash"] }, })) { console.log(message); } ```

You should see assistant messages, a tool call, a tool result, and a final message — the loop you learned in Phase 04, streaming to your console.

  1. Get validated output. Pass a schema and read structured_output instead of matching on text.
  1. Decide approval in code. Give the session a canUseTool callback (or set a permission mode) so your program decides what runs — the terminal prompt, moved into your application.
  1. Add a tool of your own. Define an in-process MCP server so the agent can call a function in your codebase. This is how you extend the loop without a separate server process.
  1. Keep the session. Capture the session id and resume it on the next call, so a multi-step workflow survives past one process.

Use It

ThingWhen you reach for it

Exercises

  1. Convert a scrape to a contract. Take one claude -p task you parse with a string operation. Reimplement it with the SDK and structured output. ✅ You pass when your program reads a typed field and never matches on the model's prose.
  1. Move the approval into code. Add a canUseTool (or permission-mode) decision for one dangerous tool — say, anything that writes files. ✅ You pass when the agent's attempt at that action is decided by your code and you can point at the log line showing it.
  1. Reproduce the terminal's job. Name three things the CLI did for you (a prompt, a saved session, an auth login) and, for each, write the one line of your design that now does it. ✅ You pass when each of the three has a named owner in your program, not "the SDK handles it."
  1. Choose the cheaper tool. Take a task you automated with the SDK and reimplement it as claude -p --output-format json. ✅ You pass when you can state, in one sentence, which version you would ship and why — and it is allowed to be the subprocess.

What this lesson skipped

Hosting at scale. Session persistence across hosts, multi-tenant isolation, restarts, and observability are a whole guide. See Hosting the Agent SDK. This lesson is orientation, not a deployment plan.

The full option surface. Models, effort, environment, limits, streaming input vs single message, and per-feature options each have their own page. The configuration and streaming input pages are the next stop.

Auth beyond an API key. Bedrock, Google Cloud, Microsoft Foundry, and gateway routing are provider setup, out of scope here.

Where the SDK sits in this course's mission. The mission is parallel Claude Code work, and the SDK is adjacent to it — useful to recognise, not required to run a fleet. If you never build a product on it, Lesson 113's surfaces are the better next step.

Check yourself

3 questions. Answer before you reveal — recognising the right option is not the same as being able to produce it.

  1. You are building a feature inside a TypeScript app. It must return a validated object, and your code — not a person — must approve or deny each file write. Which tool fits?

    1. claude -p --output-format json, because JSON output is validated
    2. The Agent SDK, because it gives you structured output and a tool-approval callback in-process
    3. The Client SDK, because it gives you the tools and the loop
    4. A scheduled task, because approvals can be answered later
    Show answer

    B. The Agent SDK, because it gives you structured output and a tool-approval callback in-process

    The Agent SDK is Claude Code's loop as a library: it supports schema-validated structured output and a canUseTool callback, so the approval decision lives in your program — exactly the two requirements. A is tempting because json sounds validated, but --output-format json wraps free-form text in an envelope; without --json-schema the payload is still prose, and there is no in-process approval callback at all. C describes the Client SDK, which talks to the Claude API directly: you get no built-in tools and no loop — you would write both. D answers approval with a delay, which is not a control your app can rely on.

  2. A parser that reads an agent's text output broke silently when the wording changed. What is the structural fix, rather than a patch to the pattern?

    1. Pin the model so the wording can't change
    2. Ask for a schema-validated structured result and read that field
    3. Add a fallback regex for the new phrasing and keep the old one
    4. Log the raw output so you can notice breakage sooner
    Show answer

    B. Ask for a schema-validated structured result and read that field

    Structured output replaces an implicit contract (the wording) with an explicit one (a schema): the response carries a validated field, so your code reads data instead of guessing at prose. A is tempting because pinning feels like control, but model aliases move and the phrasing depends on inputs too, so pinning narrows the surface without removing it. C is the patch the question rules out: more regexes cover more phrasings, and the next wording still wins. D improves observability, which is good, but it only tells you the parser broke sooner — it doesn't stop it breaking.

  3. You are turning an SDK agent into a service several teams call. What must you now provide that the interactive terminal used to handle?

    1. A larger context window, so long sessions fit
    2. Process supervision and isolation, session persistence, and app-level authentication
    3. A second model to review the first one's answers
    4. Nothing extra — the SDK is a drop-in replacement for the terminal
    Show answer

    B. Process supervision and isolation, session persistence, and app-level authentication

    The SDK launches the Claude Code binary as a subprocess. In a terminal, a person supervises the process, the session store keeps the transcript, and you log in once. As a service, all three move into your architecture: who restarts the subprocess, where transcripts persist for resume, how callers authenticate, and how tenants stay isolated. A confuses a model budget with a deployment concern. C is optional and orthogonal. D is the misconception this lesson exists to kill: you gain a typed control surface and lose a set of jobs the terminal was quietly doing.
