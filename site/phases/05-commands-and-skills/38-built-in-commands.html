LEARN · PHASE 05 · LESSON 38

Built-in Commands

You can read the `/` menu, tell which entries run fixed code and which hand

Type
Learn
Prerequisites
Phase 04, Lesson 37, Troubleshooting — Reading Errors Properly
Time
~30 minutes

Learning Objectives

  • Open the / menu and find the command you wanted without asking
  • Sort any menu entry into "fixed logic" or "prompt-based" and act differently on each
  • Reach for /help, /status, /skills, and /context at the right moments
  • Confirm a command exists on your install instead of assuming it does

The Problem

You type /review. Nothing. You try /code-review, /review-changes, /review-changes main, /pr-review. Three of those don't exist. Then you give up and paste the review instructions you wanted anyway — a paragraph of prompt text you now retype every single review, which is exactly the job a command is for.

Nothing warned you. The / menu was right there, autocompleting on every character, and you never opened it.

The cost isn't the four typos. It's the paragraph. You have retyped the same instructions more times than you've run them by hand. The tool already ships two dozen saved entry points; most people discover three.

The Concept

Type / at the start of a message and Claude Code shows you the menu. Everything on it is invoked the same way — a slash and a name — but two different mechanisms sit behind that one surface.

The docs put it plainly: most built-in commands execute fixed logic directly, while bundled skills are prompt-based — they hand Claude detailed instructions and let it do the work with its tools.

So /compact always does the same thing. /code-review is Claude reading a checklist, and a bad review is its fault, not a bug in your install.

Reading the menu

You wantDo this
Find a name that existsType / and read the list — autocompletion is the search
Know what an entry isHover/select it; the hint line tells you if it takes arguments
Know for sureRun /help

/help is the honest answer to "does this exist". Every guess you make instead of opening the menu is a guess the menu already answered.

The handful worth knowing cold

CommandJob
/helpThe full list, on your install
/contextWhere the window's tokens went
/costWhat this session has spent (alias of /usage)
/statusWhat session is loaded, what model, what directory
/permissionsWhat the agent may do without asking
/skillsWhich skills are installed — Lesson 40 territory
/doctorHealth check, and it estimates skill-listing cost
/rewindUndo a turn or restore a file

Learn those eight. The rest you look up.

Fixed vs prompt-based changes how you debug

Fixed logicPrompt-based
Deterministic?YesNo
Can you change it?No — you can only avoid it or script around itYes — that's the next lesson
When it goes wrongCheck the harnessRe-read the instructions you're feeding it
Tool to inspect/help, --debugThe skill's own file

The reframe: the slash menu is one list but two mechanisms — knowing

whether an entry runs fixed code or hands the model a prompt tells you

whether "it went wrong" is a bug or a bad conversation.

Verified against the commands reference and the skills page on 2026-10-15. Both lists move as Claude Code ships. Run /help for yours.

Build It

1. Open the menu and count

In any session, type / on an empty line.

✅ You pass when you can name at least eight entries and say which two you had never used before this lesson.

2. Sort five entries by mechanism

Take five entries you recognise. For each, write down: fixed logic or prompt-based? Check /help or the docs page for any you're unsure of.

✅ You pass when all five are sorted and you can name the page you checked against.

3. Find the honest names

You want to review a diff. Before typing anything, open the menu and find the entry that does it. Write down its exact name and any alias.

✅ You pass when you have the exact name plus its alias, or confirmation that the name you assumed doesn't exist.

4. Baseline the window

Run /context now, before adding any custom skills to this project. Save the grid.

✅ You pass when you have a saved "before" grid with the Skills row noted, including if the row is absent.

5. Ask what the menu actually costs

Run /doctor and look for the skill-listing estimate.

✅ You pass when you can say in one sentence what the listing is charging you today, even if the answer is "nothing, because no skills are installed".

Use It

CommandWhen you reach for it
/ (bare)Any time you half-remember a command name
/help"Does this exist?" — before you retype the prompt by hand
/contextWindow filling; also baseline before adding skills
/costEnd of a long session, before starting another
/statusSession feels wrong; confirm which conversation is loaded
/permissionsBefore a run that touches a lot of files
/skillsAfter installing anything in Lesson 43

Exercises

  1. Build yourself a cheat sheet of the eight commands above, with one line each saying what it answers. Keep it where you'll see it. ✅ You pass when you can blank out the "when" column and re-derive it from memory within a minute.
  1. Invent three plausible command names for tasks you'd want one-liners for. Open the menu and mark each one real or fictional. ✅ You pass when you have three verdicts and at least one you were wrong about — a wrong guess is the evidence the exercise was worth doing.
  1. Run /help and write down the count of commands listed on your install. Run it again next week and compare. ✅ You pass when you have two numbers with dates and a one-line note on what changed.

Key Terms

TermWhat people sayWhat it actually means
slash command"a shortcut"Any entry invoked by typing /name. One surface, two mechanisms.
built-in command"a command"Fixed logic the harness runs. Same input, same result.
bundled skill"a command"Prompt-based: instructions the model follows using its tools.
invocation"running the command"Putting the slash-name at the start of a message. Mid-sentence is not invocation.
alias"the other name"A second name for one entry, e.g. /review for /code-review.
"it doesn't exist""it's broken"Usually it was never a name. Open the menu and read.

What this lesson skipped

Custom commands and skills. The whole point of / beyond reading it is that you can add your own entries. That is Lessons 39–44.

Arguments. /deploy staging, /code-review 42 — most entries take arguments and the hint line shows them. Covered where it matters, in Lesson 41's arguments field.

Hook-driven commands and scheduled tasks. Both can invoke things on a schedule or an event. Phase 08 and Phase 12, in that order.

Aliases beyond the ones listed. Alias behaviour is documented per-entry and drifts. Check /help.

Check yourself

3 questions. Answer before you reveal — recognising the right option is not the same as being able to produce it.

  1. A command you ran in every repo for a year has suddenly started producing a different, worse result on a task it used to nail. Which distinction tells you where to look?

    1. It is a prompt-based entry, so the variation comes from the model reading the instructions in a different context — re-read and sharpen them
    2. It is a fixed built-in, so the output should be identical every time — check the harness version and the --debug log
    3. It is fixed logic either way, so the cause is your conversation history being too long
    4. It depends on nothing — commands that behave differently across projects are always a bug in the skill listing budget
    Show answer

    B. It is a fixed built-in, so the output should be identical every time — check the harness version and the --debug log

    Fixed built-in commands run the same harness code on the same input, so variation across repos means something environmental changed — a version, a setting, or a permission boundary — and --debug is where that shows up. Option A swaps the categories: it is exactly the prompt-based failure mode, and those entries vary because the model varies. Option C assumes history leaks into a deterministic code path, which it cannot. Option D invents a mechanism — the listing budget decides whether a skill is described to the model, not whether a command's output varies.

  2. You want a one-liner that opens a pull request, and you are fairly sure the name is /pr. What is the right first move?

    1. Type /pr and read the error, which lists the closest valid names
    2. Type /pr and if it fails try /pull-request, /open-pr, /pr-open until one works
    3. Open the slash menu and check whether any entry does it, then run /help to confirm the exact name and alias
    4. Skip the built-in one and write your own — the built-ins never cover a workflow as small as this
    Show answer

    C. Open the slash menu and check whether any entry does it, then run /help to confirm the exact name and alias

    The menu autocompletes on every character, so it answers 'does this exist' in one keystroke, and /help confirms the exact name and its alias. Option A bets on an error message listing near-misses; that is not something the CLI guarantees. Option B is the guessing loop from the lesson's opening problem — four wrong guesses and a paragraph retyped by hand. Option C's error is the last one: reaching for a custom command before checking what ships is how the retyped paragraph happened in the first place.

  3. Before adding your own skills to this project, what is the most useful thing to run and why?

    1. /clear, so the baseline is measured on an empty window
    2. /doctor, to confirm no skill is currently installed and charging you for its listing
    3. /context, so you have a before-grid you can compare against once the listing has a cost
    4. /compact, to keep the grid small enough to compare later
    Show answer

    C. /context, so you have a before-grid you can compare against once the listing has a cost

    A baseline needs to be comparable to a later reading, and /context is what gives you that reading — the Skills row is where a listing's cost shows up once you have skills. Option A is backwards: clearing mid-session destroys the very history you'd want to compare against, and costs you the work. Option B is close but off-target — /doctor estimates listing cost, which is useful once things exist, and it is not a stored before/after measurement. Option D is destructive for a reason unrelated to measurement.
