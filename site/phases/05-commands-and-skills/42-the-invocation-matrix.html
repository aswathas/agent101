LEARN · PHASE 05 · LESSON 42

The Invocation Matrix — Who Can Trigger It

You can place any skill in one of four cells, predict who will run it and what

Type
Learn
Prerequisites
Lesson 41, Anatomy — the Frontmatter Field Table
Time
~30 minutes

Learning Objectives

  • Place a skill in one of four cells using two independent frontmatter switches
  • Predict, before running anything, who may invoke a skill and whether its description is in your window
  • Handle a name collision and know what /apps/web:deploy means
  • Say when a skill should be neither automatically nor directly invocable

The Problem

You write a skill for a workflow you run on Fridays. On Wednesday, mid-refactor, it fires on its own. It doesn't break anything — but you didn't ask for it, you can't predict when it'll happen again, and you stop trusting the whole skill directory.

So you add a switch to stop it. Now it can't fire on its own. And then a colleague asks you to run it, and typing /friday-flow does nothing. You had one switch and two problems.

The instinct is to find the single "who can run this" field. There isn't one. There are two, they are independent, and conflating them is what produced the second failure.

The Concept

Two switches. Nothing else controls invocation.

FieldSet it whenEffect
disable-model-invocation: trueClaude must never choose itClaude can't auto-load it. You still can. Description is also removed from the model's available-skill context.
user-invocable: falseYou should never type itHidden from the / menu; typing the name does nothing. Claude still can.

Set both and it is neither. That's a real cell, not a paradox — see below.

The matrix

Celldisable-model-invocationuser-invocableYou can type itClaude can pick itIn your listing cost

Which cell each thing belongs in

ThingCellWhy
Deploy, commit, push, send mail, delete2Side effects. A surprise is worse than a keystroke.
A review checklist, a style guide1Both callers, neither is dangerous
Project conventions Claude should absorb without you typing3Reference, not a command
Reference material something else reads directly4Deliberately dormant

Cell 3 is the one people get wrong. user-invocable: false reads like "hide this" and actually means "Claude, you handle it." A skill nobody types and Claude never matches is a folder of text — useful only if a hook or another tool reads it. That is a Phase 08 concern, not a skill concern.

Cell 2 also saves you money

The docs say a disable-model-invocation: true skill has its description removed from Claude's available-skill context. So a manual-only skill costs you no listing budget. If you own twenty manual-only workflows, they are effectively free until typed.

That is the whole argument for cell 2 on anything you're not sure about: it is the reversible one.

What else can invoke it

Not just you and Claude. A disable-model-invocation: true skill is also prevented from being preloaded into subagents, and from running when a scheduled task fires with the skill's name as its prompt. Both are later phases (Subagents, Orchestration); the point here is that cell 2 is stricter than just "you, interactively."

Names, when two skills want the same one

Where the skill livesCommand name comes from
.claude/skills/deploy-staging/ or ~/.claude/skills/name field, else the directory name
Nested .claude/skills/ that clashesPath relative to the working dir, then the name: apps/web/.claude/skills/deploy/ → /apps/web:deploy
Legacy .claude/commands/deploy.mdFilename, no extension
Plugin skills/review/name, else directory name — prefixed: /my-plugin:review

name wins over the directory name, unless another command already uses that name — then the directory name still invokes it.

The reframe: there is no "who can run this" flag, there are two switches

that cross to make four cells, and the one that surprises people is that the

manual-only cell is also the one that costs you nothing.

Verified against the skills page on 2026-10-15. Name-resolution details are version-gated — check the page when the collision rules matter.

Build It

1. Fill all four cells

One skill. Copy it four times with different names — cell1 through cell4 — one per switch combination.

✅ You pass when all four exist and you have not yet tested any of them.

2. Test the user column

In a fresh session, type /cell1, /cell2, /cell3, /cell4.

✅ You pass when you can say which two respond and which two are absent from the menu, and can point at the menu itself as evidence.

3. Test the model column

With no slash anywhere, ask for each task in natural language:

I need to run the cell-N workflow now.

✅ You pass when you have four results and exactly the two cells you predicted loaded without a slash.

4. Check the listing cost

Run /context and look at the Skills row with all four installed. Then delete the frontmatter description from cell2 and cell4 and re-check.

✅ You pass when you can say which descriptions are charged for and why the manual-only ones are not, in terms of the switch rather than a guess.

5. Force a name collision

Create apps/web/.claude/skills/deploy/SKILL.md and .claude/skills/deploy/SKILL.md. Find the command that runs each.

✅ You pass when you can name both commands and say which form one of them takes.

Use It

SituationCell
It changes the outside world2 — disable-model-invocation: true
You'd rather type it than have it guessed2
Claude needs the knowledge, you never would3 — user-invocable: false
Safe either way, and useful both ways1 — the default
You genuinely want it dormant4 — both switches, deliberately
Unsure?Start at 2. It's the reversible one and it's free.

Exercises

  1. Take every skill you own and put it in a cell. Write down any that move as a result. ✅ You pass when any skill that moved has a one-line reason naming who was wrongly able to run it before.
  1. Build the cell-4 case on purpose, then deliberately break it: have Claude never mention it, never be asked for it, and see whether anything ever reads the file. ✅ You pass when you can say what, if anything, loaded the body, and what would have to exist for the skill to earn its place there.
  1. Write a rule — one sentence — that decides cell for every new skill you author. Test it against three skills you already own. ✅ You pass when the rule gives the same answer for all three, or you can say which one it gets wrong and why.

Key Terms

TermWhat people sayWhat it actually means
disable-model-invocation"don't auto-run"Claude can't pick it. You can still type it. Also drops the description from the listing.
user-invocable"hidden"You can't type it. Claude still can.
manual only"user-invocable: true"Cell 2 — the disable-model-invocation side. The default for user-invocable is true.

What this lesson skipped

Subagents as callers. A subagent can use a skill; cell 2 excludes preloading them. Phase 06, lessons 45–48.

Scheduled tasks. A scheduled task firing with a skill name as its prompt is suppressed for cell-2 skills. Phase 12, Orchestration.

Settings-level overrides. skillOverrides in settings can change listing visibility and set entries to "name-only". That is context budgeting, and it belongs to Phase 13.

Plugin namespacing. Named so /my-plugin:review isn't a surprise. Phase 09.

Check yourself

3 questions. Answer before you reveal — recognising the right option is not the same as being able to produce it.

  1. You author a skill that publishes release notes. It fired on its own once during an unrelated task. You add a switch so that cannot happen again — and now a teammate's slash command no longer does anything. Which single change fixes both?

    1. Remove the switch and rely on a stricter description instead
    2. Set user-invocable: false, which hides it from the menu and from the model
    3. Set disable-model-invocation: true and leave user-invocable at its default, so the model can't pick it but /name still works
    4. Set both switches, since the skill must be run by someone and there is no cell for that
    Show answer

    C. Set disable-model-invocation: true and leave user-invocable at its default, so the model can't pick it but /name still works

    The two failures came from treating invocation as one flag. disable-model-invocation is the switch that stops the surprise, and user-invocable defaults to true, so /name keeps working — that is cell 2, and it also removes the description from the listing you were paying for. Option B picks the switch that stops the wrong caller: it hides the skill from you and leaves Claude free. Option D produces cell 4, which is neither caller — and there is a cell for exactly what this skill wants, which is the one option A refuses to find.

  2. You own about fifteen skills you only ever type yourself, and /context shows the Skills row is now the largest fixed cost in your window. Which observation is true?

    1. The listing cost is unavoidable — every installed skill's description sits in the window regardless of how it is invoked
    2. Setting disable-model-invocation: true on the manual-only ones removes their descriptions from the model's available-skill context, so they stop costing listing budget
    3. Set user-invocable: false on them instead, since that is the switch that removes them from the listing
    4. Only /context with the skills deleted shows the real cost, so there is nothing to optimise while they are installed
    Show answer

    B. Setting disable-model-invocation: true on the manual-only ones removes their descriptions from the model's available-skill context, so they stop costing listing budget

    The docs state that a disable-model-invocation skill has its description removed from Claude's available-skill context — which is why cell 2 is also the cheap cell. Option A states the opposite of that, and it is the belief that makes people assume skills are free. Option C swaps the switches; user-invocable false keeps the skill in the listing while hiding it from you, which is exactly backwards for this goal. Option D gives up before measuring.

  3. Two skills are named deploy — one at .claude/skills/deploy/, one at apps/web/.claude/skills/deploy/. Which is the accurate picture?

    1. The second one silently loses; only the first gets a command
    2. Both get a command, and the nested one is invoked as /apps/web:deploy
    3. The nested one shadows the root one and both are invoked as /deploy
    4. The root one must be renamed, because two skills cannot share a command name
    Show answer

    B. Both get a command, and the nested one is invoked as /apps/web:deploy

    Nested skills that clash with another skill are addressed by prefixing the path relative to the working directory, then the skill's own name — which is why the colon form looks unusual and is not a typo. Option A invents a silent shadowing rule that would make monorepos unusable. Option C reverses it: the root one is the plain /deploy, not the other way round. Option D is wrong because the mechanism exists precisely so that neither has to be renamed.
