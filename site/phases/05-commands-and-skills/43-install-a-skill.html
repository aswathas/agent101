LEARN · PHASE 05 · LESSON 43

Install a Skill

You can install a skill at the right scope, prove it loaded, and recover it

Type
Learn
Prerequisites
Lesson 42, The Invocation Matrix
Time
~35 minutes

Learning Objectives

  • Install a skill at personal, project, or nested scope and say who gets it
  • Verify a skill loaded, and identify whether the problem is discovery, YAML, or the name
  • Check a skills directory for unparseable frontmatter in one command
  • Recover personal skills that were moved to .trash/

The Problem

A week ago you had eleven personal skills in ~/.claude/skills/. Today you have none. The folders are gone from where they were.

They are not gone. They are in ~/.claude/skills/.trash/, moved there silently by a file named manifest.json that you — or a tool — dropped into the skills directory. Before Claude Code v2.1.280, that filename made the harness sweep every skill folder the file listed into a timestamped trash folder. Those skills stopped loading. No error. The menu simply had fewer entries.

They stay there for 30 days by default, then a retention sweep deletes them.

Two lessons: personal skills are a directory, not a database, so the failure mode is file placement — and "it just vanished" is a real reported shape, not an exaggeration.

The Concept

Installing a skill means putting a folder in one of the documented locations. There is no install command for the local case. That is the whole of it, and that is why it can go wrong silently.

ScopeWhereWho gets it
Enterprisemanaged settings directoryEveryone, policy-managed
Personal~/.claude/skills/<name>/SKILL.mdYou, every project on this machine
Project.claude/skills/<name>/SKILL.mdAnyone who clones the repo — commit it
Nested / monorepo<subdir>/.claude/skills/<name>/SKILL.mdLoads when working under that subdir
Extra directory.claude/skills/ under an --add-dir pathWhoever granted that directory
Plugin<plugin>/skills/<name>/SKILL.mdAnyone who installs the plugin
Synced from claude.ai~/.claude/skills/synced/Downloaded, separate subfolder
Legacy command.claude/commands/<name>.mdSame as its containing scope

Personal skills load across projects on your machine but not in cloud sessions. Project skills load from the starting directory and its parents up to the repository root; skills below the starting directory load after Claude first reads or edits a file there.

Which scope

UseScope
Your own workflow, every repoPersonal
Your team's workflow, versionedProject — commit it
One package of a monorepoNested
Anything you want to hand to a colleagueProject or plugin, never personal

If a skill only works on your machine, personal is right. If someone else needs it, personal is the wrong scope by definition — they will not see it.

Verifying, in the right order

Ask these in sequence. Each rules out one failure and hands you to the next.

StepCommandTells you
1/skillsIs it discovered at all
2Ask "What skills are available?"Is the description present to the model
3/nameDoes it load and run
4claude plugin validate <dir>Do any SKILL.md files have unparseable frontmatter
5claude --debug, grep for [names]Was a name refused

Step 4 needs Claude Code v2.1.233 or later. If yours is older, skip to step 5 and read the debug log by eye — which is the situation most people are in without knowing it.

After a rename or a name: edit, restart the session unless the file sits in a directory Claude Code watches for changes. /reload-skills is in the command menu; try it, and if your build doesn't do what you expect, restart.

The trash

~/.claude/skills/.trash/ is where swept skills land, in a timestamped folder. Recovery is a move:

~/.claude/skills/.trash/2026-10-08T14-22-11/my-skill/
  → ~/.claude/skills/my-skill/

Do it before 30 days pass. After that the retention sweep takes them.

The reframe: installing a skill is placing a folder, so every failure

here is a placement failure — discovered by asking three questions in order,

not by reading a stack trace that never comes.

Verified against the skills page on 2026-10-15. The trash incident and the claude plugin validate minimum version are both version-gated; re-read the troubleshooting section before repeating either as fact.

Build It

1. Install at both scopes, on purpose

Put the same skill in ~/.claude/skills/ and in .claude/skills/ of a scratch project.

✅ You pass when you can say which one your teammates would receive and which one you would, from the scope table rather than from a guess.

2. Verify in order, not in one jump

Run /skills, then ask "What skills are available?", then /name. Stop at the first failure and record which step failed.

✅ You pass when you have a named step that failed and the command that proved it — not just "it didn't work".

3. Break the YAML and find the right command

Insert a malformed line into the frontmatter. Run /name (still works) and then a natural request (doesn't fire). Run claude plugin validate on the directory.

✅ You pass when the validator names the file and you can explain why /name still worked anyway.

4. Break the name

Rename a skill folder so its name holds a character Claude Code refuses — a zero-width space or a <. Look in the menu, then in claude --debug for [names].

✅ You pass when the debug log names the refused character and you can say why the skill vanished entirely rather than merely failing to fire.

5. Simulate the trash

Create ~/.claude/skills/.trash/2026-10-08T14-22-11/, move a skill into it, and confirm the skill is gone from the menu. Move it back and confirm it returns.

✅ You pass when you have the before and after /skills output for the move and the move-back.

6. Restart vs reload

Edit a description in place and run /reload-skills. If nothing changes, restart the session and check again.

✅ You pass when you can say which mechanism actually re-read the file on your install, and your answer is observed rather than assumed.

Use It

ThingWhen you reach for it
~/.claude/skills/Personal, machine-wide, never committed

Exercises

  1. Install one skill at project scope in a real repo, commit it, and hand the path to a colleague or a fresh clone. ✅ You pass when the clone loads it and you can state the one line of the install that makes the difference.
  1. Take every skill you own and check its scope. Move at least one to a different scope. ✅ You pass when you can say which scope was wrong and what specifically broke because of it — a teammate not seeing it, or a stale global skill.
  1. Break a skill four ways — wrong folder, bad YAML, refused name, missing directory — and record which command diagnosed each. ✅ You pass when you have a table of four failures with the command that named each one, and none of them say "restart and hope".

Key Terms

TermWhat people sayWhat it actually means
install"adding a plugin"Copying a folder to a documented path. No install step.
personal scope"global"~/.claude/skills/. This machine, this user. Not cloud.
project scope"repo".claude/skills/, committed. What teammates get.

What this lesson skipped

Marketplace installation. /plugin marketplace add and friends. The plugin is the packaging layer and Phase 09 owns it.

Synced skills from claude.ai. They land in ~/.claude/skills/synced/, are prefixed anthropic-skills:, and have their own behaviour. Real, and Phase 09 again.

Enterprise and managed-settings scope. Policy-managed, not yours to place.

Settings-level overrides (skillOverrides, "name-only" entries) and the listing budget. Phase 13.

Check yourself

3 questions. Answer before you reveal — recognising the right option is not the same as being able to produce it.

  1. You wrote a release workflow skill for yourself and left it in ~/.claude/skills/. A teammate says they don't have it and asks you to send it over. What is actually wrong?

    1. Personal skills are machine-local by definition — a teammate will never see them, and the fix is project scope, committed to the repo
    2. The install failed silently; re-copy the folder to ~/.claude/skills/ on their machine
    3. They need to run claude plugin validate before personal skills appear
    4. The skill's name is refused because it isn't lowercase
    Show answer

    A. Personal skills are machine-local by definition — a teammate will never see them, and the fix is project scope, committed to the repo

    Scope is the whole mechanism here: personal skills load on this user, this machine, and nowhere else — so a teammate not having one is correct behaviour, not a failed install. The fix is to move it to .claude/skills/ and commit it. Option B asks a teammate to copy a file into a machine-local location that will diverge immediately. Option C is unrelated — validate checks frontmatter parsing on a skills directory, not who can see it. Option D invents a naming rule; names are rejected for specific characters, not case.

  2. A skill you installed runs fine as /my-skill but never fires on a natural request. The description looks correct. What is the diagnostic order?

    1. Re-read the description out loud and rewrite it more emphatically
    2. Check /skills first to confirm discovery, then claude plugin validate the directory for unparseable frontmatter
    3. Delete and reinstall the skill
    4. Check ~/.claude/skills/.trash/ in case a sweep moved it
    Show answer

    B. Check /skills first to confirm discovery, then claude plugin validate the directory for unparseable frontmatter

    The symptom has two causes that look identical from outside — a description that doesn't match human phrasing, and frontmatter that fails to parse so the body loads with empty metadata — and only a parse check separates them. /skills first establishes that discovery is even the problem; validate then names the file. Option A tests a hypothesis you said you'd already ruled out. Option C destroys the evidence that would have told you which cause it was. Option D is a real failure mode but it removes the skill from the menu entirely, which is not the symptom described.

  3. A colleague's eleven personal skills vanished between sessions with no error, and their folders are gone from ~/.claude/skills/. Where do they actually go?

    1. They are deleted permanently the moment they stop loading
    2. They are moved into a timestamped folder under ~/.claude/skills/.trash/, recoverable until the retention sweep — historically triggered by a stray manifest.json in the skills directory
    3. They moved into ~/.claude/skills/synced/, which is where downloaded skills live
    4. They were overridden by a plugin with the same names
    Show answer

    B. They are moved into a timestamped folder under ~/.claude/skills/.trash/, recoverable until the retention sweep — historically triggered by a stray manifest.json in the skills directory

    This is a reported failure shape, not a hypothetical: a file named manifest.json in the skills directory used to make Claude Code sweep the listed skill folders into ~/.claude/skills/.trash/ under a timestamped subfolder, and those skills stopped loading — with a 30-day retention sweep afterwards. So recovery is a move, and it is time-limited. Option A is the panic response and it's wrong. Option C confuses two different things — synced skills are downloaded, not swept. Option D would change what commands exist, not remove files.
