BUILD · PHASE 05 · LESSON 44

Author a Skill From Scratch

You can write a skill someone else can use without reading your head: matching

Type
Build
Prerequisites
Lesson 43, Install a Skill
Time
~50 minutes

Learning Objectives

  • Author a SKILL.md that passes every check in the runnable script in code/
  • Write instructions as standing rules, so they survive turn fifteen
  • Pass arguments into a skill and load supporting files only when needed
  • Diagnose "it fired once and then stopped" from the three documented causes

The Problem

Your pasted review checklist worked. Then it didn't.

Turn one, Claude runs the whole thing. Turn fifteen, it's reviewing files without running the check you spent forty lines writing. Nothing broke. Nothing errored. The skill is still installed, still in the menu, still described correctly.

You have three real causes and no way to tell them apart, because all three present as "Claude quietly stopped obeying":

  • The rule was written as a one-time step, so after it ran once it was done.
  • The conversation was compacted, and only the start of the skill came back.
  • The rule must hold every time, and a prompt is a request, not enforcement.

The first is a wording bug you can fix. The third is a phase you haven't reached yet. The second is why "keep the important stuff at the top" is a real instruction and not folklore.

The Concept

A skill is a maintained prompt. Three parts, in this order of importance.

The description is a matching rule, not a label

It decides whether the skill exists for a given request. Write the words a human would type, and put the key use case first — description + when_to_use is truncated at 1,536 characters in the listing.

✓ "Run the project's full check suite. Use when the user says run the tests,

verify, check this, or before any commit."

✗ "A skill for testing. Helpful for developers."

Write standing instructions

The rendered body enters the conversation as one message and stays there. The file is not re-read on later turns. So the body describes what should be true for the whole task:

Don't writeWrite
"Run the tests.""Run the tests after every edit."
"Check the error handling.""Every error path you add must have a test that fails without it."
"Use the project's formatter.""Before reporting done, format every file you touched."

Same length. Completely different lifespan.

Keep the important part at the top

After compaction, Claude Code re-attaches the most recent invocation of each skill and keeps the first 5,000 tokens of each, with a 25,000-token combined budget, filling from most-recently-invoked — so older skills can be dropped entirely if you invoked many.

Put the rule that must not be lost at the top of the file.

Arguments

argument-hint shapes autocomplete. arguments names positions. The body substitutes them.

---
name: fix-issue
description: Fix a GitHub issue end to end.
argument-hint: "[issue-number]"
arguments: issue
disable-model-invocation: true
---

Issue to fix: $issue

1. Read the issue, reproduce the failure.
2. Fix it. Test before reporting.
3. Report the diff and the test output.

$ARGUMENTS is the whole raw argument string. Positional $1, $2 map to the arguments names in order.

Dynamic context

The difference between a frozen prompt and a live one:

Current state, fetched fresh each time:

!`git status --short`
!`git log --oneline -5`

The command runs at invoke time and its output enters the conversation. This is what a legacy command file cannot do — and the reason "the current branch is main" belongs here rather than in the text.

Supporting files

Anything else in the folder ships alongside. Point at it with a relative path and tell the model when to read it. It costs nothing until then.

.claude/skills/review/
├── SKILL.md
└── references/
    └── security-checklist.md

The three reasons it stops being followed

SymptomCauseFix
Followed turn one, not turn fifteenGuidance read as a one-time stepRewrite as standing instructions
Followed, then the conversation compactedOnly the skill's first 5,000 tokens come backStrongest rule at the top
Skipped a rule that must hold every timeA prompt is a requestA hook (Phase 08) enforces it

The third is the honest limit of this whole phase. If it must hold every time, write it down here and also plan the enforcement; do not expect prose to do it.

The reframe: a skill is a prompt you now maintain, so its quality is

judged by what it prevents — the rule at the top that survives compaction and

the standing instruction that still applies on turn fifteen, not by how

thorough the prose reads.

Verified against the skills page on 2026-10-15. Token caps, minimum versions and the validate command age; the shape does not.

Build It

There is a runnable checker in this lesson's code/ directory. Use it.

node code/check-frontmatter.mjs .claude/skills/review

1. Start from the template

Copy code/SKILL.md into a scratch project at .claude/skills/review/SKILL.md. Run the checker on it.

✅ You pass when the checker reports no problems and you can name each check it ran.

2. Write the description last, and write it wrong first

Put "A skill for reviewing code." Run it against three natural requests a reviewer would type. Then rewrite it with the words those requests use and run the same three again.

✅ You pass when at least one request changed outcome, and you can quote the words you added.

3. Convert one step into a standing rule

Take a line the body gives as a step. Rewrite it so it holds for the whole task. Invoke the skill, ask for a second file, and see whether it still applies.

✅ You pass when you can quote the second-turn behaviour and say which phrasing produced it.

4. Move your strongest rule to line one of the body

Put the must-not-be-lost rule first. Compact the session. Check what came back. Move the same rule to the bottom and repeat.

✅ You pass when you can say which position survived and why, using the cap rather than intuition.

5. Add an argument and a dynamic command

Add argument-hint, arguments, and one ` !git status --short ` line. Invoke with an argument.

✅ You pass when the argument appears in the body and the git output is current rather than the state from when you wrote the file.

6. Add a supporting file

Move the longest checklist into references/. Point at it. Confirm it isn't read on a plain invocation and is read when you ask for the security review.

✅ You pass when you can show both states, and /context shows no cost for a run where it never loaded.

7. Run the checker on a deliberately broken skill

Break four things: the opening --- not first, an unterminated block, an unknown field, a name with a < in it.

✅ You pass when the checker finds all four and names the line for each.

Use It

ThingWhen you reach for it
descriptionFirst and last thing you edit on a skill that won't fire
when_to_useTrigger phrases that would bloat description
disable-model-invocation: trueAnything with side effects
argument-hint / arguments / $nameAny skill that takes input
` !command `Anything the skill asserts about current state
references/ + relative linkLong checklists you don't want in the window
Strongest rule at the topAny skill you expect to survive compaction
code/check-frontmatter.mjsBefore you commit a skill
A hookWhen a rule must hold every time and a prompt is not enough

Exercises

  1. Author a real skill for a workflow you actually run. Under 60 lines. Share it with one person who has to use it without you explaining anything. ✅ You pass when they run it correctly with no follow-up question from you, and you can point at the lines that made that possible.
  1. Break your own skill three documented ways — one-time phrasing, weakest rule at the top, a must-hold-every-time rule. For each, record the symptom before you fix it. ✅ You pass when you have symptom-then-fix for all three and can say which one no amount of wording will fix.
  1. Take a skill you did not write. Improve only its description, measure before and after across five realistic requests, and report the numbers. ✅ You pass when you have five before/after results and at least one change in either direction — a measurement that never moves means the description was not the problem.

Key Terms

TermWhat people sayWhat it actually means
SKILL.md"the prompt file"YAML frontmatter, then markdown. One message, kept in the conversation.
standing instruction"a rule"Wording that applies for the whole task. The opposite of a step.
$ARGUMENTS"the input"The raw argument string. $1, $2 are positional.
` !cmd `"an include"Runs at invoke time. Output enters the conversation now, not when you wrote it.
supporting file"an attachment"Loads only if the body points at it. The cheapest way to hold detail.
first 5,000 tokens"it got truncated"Per-skill re-attach budget after compaction. Put the important rule first.
prompt vs hook"the skill should enforce this"A prompt asks. A hook enforces. Different phases.

Check yourself

3 questions. Answer before you reveal — recognising the right option is not the same as being able to produce it.

  1. Your skill's body says "Run the test suite." It fires, Claude runs the tests, and by turn twenty it is editing files without testing. What is the actual defect?

    1. The skill body is too long and got compacted away
    2. The instruction is written as a one-time step, and the content is never re-read on later turns — it needs to be standing guidance
    3. disable-model-invocation is unset, so Claude is choosing when to follow it
    4. The body needs an arguments field so the step re-runs on each invocation
    Show answer

    B. The instruction is written as a one-time step, and the content is never re-read on later turns — it needs to be standing guidance

    The skill's rendered content enters once and stays; the file is not re-read on later turns. So "run the test suite" reads as a task that is now complete, and "run the tests after every edit" is the phrasing that still applies on turn twenty. Option A guesses at compaction when the content was never dropped — you would see it in /context. Option C is unrelated: automatic invocation is about who triggers the skill, not whether the model keeps following what it said. Option D invents a mechanism — arguments substitute values, they don't re-trigger steps.

  2. A skill body asserts "the current branch is main and the working tree is clean." Six months later that sentence is wrong and Claude still says it confidently. Which mechanism fixes it?

    1. Add a references/ file describing the branch and point the body at it
    2. Use a dynamic context block so the git state is fetched fresh at invoke time
    3. Set disable-model-invocation: true so only you can run it
    4. Move the assertion to the top of the body, next to the strongest rule
    Show answer

    B. Use a dynamic context block so the git state is fetched fresh at invoke time

    A body is a frozen prompt — anything it asserts about the present was true when you wrote it. A dynamic context block runs the command at invoke time and its output enters the conversation then, which is the difference between a command file and a skill. Option A makes it worse: the stale sentence stays and a reference adds a second place for it to be stale. Option C changes who may trigger the skill and says nothing about the content being out of date. Option D survives compaction better while still being wrong.

  3. Your skill tells Claude to never commit directly to main. Claude follows it for a while, then commits anyway, with no error. What is the honest answer?

    1. Sharpen the description so the rule matches more requests
    2. Repeat the rule at the bottom of the body as well as the top
    3. A prompt is a request, not an enforcement mechanism — a rule that must hold every time needs a hook
    4. Add paths so the skill only activates on main
    Show answer

    C. A prompt is a request, not an enforcement mechanism — a rule that must hold every time needs a hook

    This is the documented limit of the skills layer: if a rule must hold every time, prose is the wrong tool, and a hook is the right one because it runs on the event whether or not Claude is following the skill. Option A changes how often the skill is chosen, not whether its instruction is obeyed. Option B adds repetition, which is a louder request rather than a guarantee. Option D scopes when the skill loads and has no bearing on compliance.
