LEARN · PHASE 04 · LESSON 32

What Loads Into the Window, and What Doesn't

Before the tool writes a single word, it reads a block of text. That block is

Type
Learn
Prerequisites
Lesson 31 (The Agentic Loop)
Time
~25 minutes

The Concept

The block is filled in this order, top to bottom:

  1. The system prompt. Instructions the tool was given before the conversation started.
  2. The conversation. Your messages, its messages, in order.
  3. Files it has read. Each time the tool calls a tool to read a file, that file lands here.
  4. Tool results. The output of every past tool call.
  5. Project rules. Anything the project has placed to tell the tool how to behave.

When the tool is about to act, that is the whole picture. The tool does not 'remember' anything outside this block. It does not know about the rest of your computer. It does not know about your other sessions.

Build It

For this conceptual lesson, the work is one short scenario in a Claude Code session to confirm the section landed:

  1. Open a fresh session in any project folder.
  2. Apply the idea in the section above to your project in a way that fits.
  3. Notice what happens when the condition in the section is met, and when it is not.

Pass: you can describe the difference between the two cases in one paragraph.

What's not in the block

The block does not contain:

  • Your other open sessions.
  • Files it has not been told about.
  • The internet, unless the tool is the kind that fetches.
  • Anything that was not put there this turn or a past turn.

If the tool hasn't read a file, it cannot quote from it. If you opened another terminal in another window, the tool cannot see it. If a coworker changed a file between two of your turns, the tool does not know.

The block, as a diagram

The box on the right is real. The arrows on the left are also real. They are separate things.

Learning Objectives

By the end of this lesson you can:

  • Name the five categories of content that fill the block at each turn
  • Predict what the tool does and does not know about your environment
  • Spot when a request requires the tool to read a file it has not yet read
  • Explain why the tool can forget an instruction you gave ten turns ago
  • Identify which inputs are most expensive to the block's fixed size

The Problem

You paste a long log into the tool. It reads the log, answers your question. You ask a follow-up about an earlier part of the log. The tool says it does not see that part anymore.

That is not a bug. That is the block filling up. The first half of the log got pushed out by the second half, and the tool is reading from what is left.

The block has a fixed size. Everything in it costs. Long inputs push out earlier content. The tool's behavior when 'out of room' is the budget mechanic, not a fault.

The reframe

The reframe: What the tool sees is a budget. Every tool call, every file read, every system prompt word costs against that budget. When the budget is gone, the tool forgets. It is not losing capability. It is running out of room.

This is the one sentence to remember from this lesson. Hold it.

What costs the most

Not all inputs cost the same. Rough ordering, cheapest to most expensive per item:

  • A line of your message: cheap.
  • A system prompt word: cheap.
  • A short tool result: medium.
  • A long file the tool just read: expensive.
  • A giant log dump from a failed command: very expensive.

Long, repeated reads of the same file cost twice: once for the read, again every turn the file is kept around. Tests that print megabytes of output cost every time you run them.

Why the tool 'forgets'

If you have ever had the tool ask the same question twice in a session, this is why. The earlier answer fell out of the block. The block has a fixed size. When new content comes in, old content leaves. The tool is not being rude. It can no longer see what it said twenty turns ago.

If the tool seems to forget an instruction you gave at the start, that instruction may have been pushed out by something longer that came later. The system prompt is the longest-lasting thing in the block, because it sits at the top. Your first messages are shorter-lived, because they sit below everything you have done since.

Three practical consequences

1. The tool can only act on what it can see. If it edits a file but has never read that file, it is editing blind. Have it read first.

2. Past errors stay in the block. A failed command from ten turns ago is still using space. If you are running out of room, the early failures are the first thing to trim.

3. Project rules matter. Files like a project memory file get loaded into the block at start. The longer that file is, the less room you have for everything else. Keep it tight.

Use It

What you seeWhere the cost came from
Tool is slow on the first turn after launchThe block is being assembled; system prompt + project rules + first message
Tool seems to forget your early instructionsEarlier content was pushed out by later, longer content
A long read happens early in the sessionThat read is sitting in the block for the rest of the session
Tool refuses to read a third long fileThe first two reads filled the block; the third does not fit
You can scroll back and see an old answer in the transcriptThe transcript is on disk, but the tool's block is not — the tool cannot scroll back

Exercises

  1. Run a long read and watch the block fill. Take a project with at least one source file over 200 lines. In a fresh session, ask the tool to read the file and summarize it. Then ask a question that requires looking at the first 10 lines. The tool can still see them. Now paste a 5000-line log into the same session. Ask the question again. The tool may have lost the first file. Pass: you can explain which content fell out and why, naming the size of the file you read and the size of the log you pasted.
  1. Catch the cost ordering in the wild. In a session, do three things in order: send a long message, run a command that returns a large result, ask the tool to summarize a 1000-line file. After each, ask the tool to recall a fact from earlier in the session. Note which one loses the fact first. Pass: the file read is the one that costs the most per turn, and you can name the cost ordering from cheapest to most expensive without looking at the table.
  1. Spot the hidden read. In a session, ask the tool to make a small edit. The tool reads the file first without telling you. You see no explicit 'reading' message — only the edit result. State, out loud or in writing: did the tool have to read the file? Where in the block did the read live, and for how many turns? Pass: the read happens during the act step, lives in the block for the rest of the session, and costs every turn it sits there.

Key Terms

What people sayWhat it actually means
'The tool forgot what I said.'Earlier message was pushed out of the block by later content. The tool is not losing capability; it is running out of room. The misconception is that the tool has memory of its own. It does not.
'Context window.'The fixed-size block. Until Lesson 34 we call it 'the block' or 'the budget.'
'It's hallucinating.'Usually: it is answering from a partial block where the answer to your question was not present.

What this lesson skipped

We have not named the size of the block in numbers. That is Lesson 34. We have not talked about how to clear the block on purpose. That comes after.

This lesson was only about what is in the block, and what is not.

Check yourself

4 questions. Answer before you reveal — recognising the right option is not the same as being able to produce it.

  1. You paste a long log, ask about its start, and later ask about it again — Claude Code can no longer see that part. What happened?

    1. A bug — the log should stay readable once pasted
    2. The block filled up: later content pushed the earlier part out, so the tool is reading from what is left
    3. The tool is being uncooperative
    4. The log was deleted from disk
    Show answer

    B. The block filled up: later content pushed the earlier part out, so the tool is reading from what is left

    The fixed-size block holds everything the tool sees, so new content evicts old content — it is a budget running out, not a capability failing. Option A is tempting because the words are still on your screen, but the transcript on disk is not the same as the block the tool reads. Option C assigns intent where there is only a limit. Option D mistakes the window for storage.

  2. Which input costs the most room per turn once it is sitting in the block?

    1. A line of your message
    2. A word in the system prompt
    3. A long file the tool just read
    4. A short tool result
    Show answer

    C. A long file the tool just read

    Cost rises from a line of chat to a short result to a long file read, so a file the tool read is the most expensive per turn. Option D is tempting because a tool result feels like a small detail, but a short result is medium and a long read is the heavy one. Options A and B are the cheap end of the ordering.

  3. You ask for a small edit. You never see an explicit "reading" message — only the edit result. What is true?

    1. It did not read the file; it edited blind
    2. It read the file during the act step; that read lives in the block for the rest of the session and costs every turn
    3. It read the file but discarded the read immediately
    4. File reads never enter the block
    Show answer

    B. It read the file during the act step; that read lives in the block for the rest of the session and costs every turn

    A hidden read is still a read: it happens during the act step and then sits in the block, costing room on every later turn. Option A is tempting when no reading message appears, but the edit could not have been made without the read. Option C assumes the read is transient when it is retained. Option D contradicts the whole model.

  4. Your test command prints megabytes of output, and you run it every few turns. What is the effect on the block?

    1. Only the first run costs; later runs are free
    2. Each run's output stays in the block and is re-paid every following turn, crowding out earlier content
    3. The tool compacts just that output automatically, so it is free
    4. The tool refuses to run it
    Show answer

    B. Each run's output stays in the block and is re-paid every following turn, crowding out earlier content

    A giant output dump is the most expensive kind of content, and it is re-paid on every turn it remains. Option A is tempting because the command itself ran once, but its output persists. Option C invents targeted compaction that the lesson does not describe. Option D is not the failure mode — the block fills, the tool does not decline.
