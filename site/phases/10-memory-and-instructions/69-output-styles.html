LEARN · PHASE 10 · LESSON 69

Output Styles

You can change how the agent talks and what role it plays for a whole session — without changing what it knows.

Type
Learn
Prerequisites
Lesson 68, Auto Memory and MEMORY.md
Time
~30 minutes

Learning Objectives

  • Switch between the built-in output styles and say what each one changes
  • Write a custom output style with frontmatter
  • Decide between keep-coding-instructions: true and leaving it out
  • Choose between an output style, CLAUDE.md, and a hook for a given need
  • Explain why an output style is a request the agent follows, not a guarantee

The Problem

You want short answers. So every session you type "be concise" before your first real question. Every session. Thirty times a month, the same sentence, and it wears off the moment the conversation gets long.

Or the other one: you are using Claude Code to draft documentation, not code. It keeps behaving like a software engineer — scoping changes, writing comments, verifying work — because that is the default role it was given. You want a writing assistant, not a coder with a documentation task.

Both are the same problem: you are trying to change how the agent works, one message at a time.

The Concept

An output style is a set of instructions that sets Claude's role, tone, and response format for every response in a session. You pick one, and it applies until you change it — so you stop repeating the request.

Claude Code ships four built-in styles besides its default:

StyleWhat changesUse it when
DefaultNothing extra — standard software-engineering instructionsNormal work
ProactiveStarts work immediately, assumes on routine decisions, doesn't enter plan mode unless askedYou'll correct course rather than pre-approve
ConciseLeads with the result, drops preamble and recaps, one to three sentences for a simple questionDefault answers are longer than you want
ExplanatoryAdds short Insight blocks explaining choices behind the codeYou're learning a codebase
LearningAdds Insight blocks and leaves small pieces of code for you to write (TODO(human))You want hands-on practice while the task still gets done

Switch with /output-style <name>, or /config → Output style, or the outputStyle field in a settings file. The command and the menus save the choice to .claude/settings.local.json.

The reframe: an output style changes the agent's voice, not its knowledge — and unlike a rule in CLAUDE.md, it can replace the agent's whole job, which is why the built-in coding instructions come out unless you ask for them back.

Writing a custom style

A custom output style is a markdown file: optional YAML frontmatter, then the instructions. Save it at one of three levels:

  • User: ~/.claude/output-styles — every project
  • Project: .claude/output-styles — committed, shared
  • Managed policy: .claude/output-styles inside the managed settings directory

The file name becomes the style name unless you set name in the frontmatter. The frontmatter fields:

FieldWhat it does
nameShown in the /config picker. Defaults to the file name
descriptionShown in the picker
keep-coding-instructionsSet true to keep Claude Code's built-in software-engineering instructions alongside your style
force-for-pluginPlugin styles only — apply automatically when the plugin is enabled

keep-coding-instructions is the field that bites. Leave it out and your custom style replaces the software-engineering instructions — right if Claude is now a writing assistant, wrong if you only wanted a different tone. Set it true when you are changing how Claude communicates but still want it coding the same way.

---
name: Diagrams first
description: Lead every explanation with a diagram
keep-coding-instructions: true
---

When explaining code, architecture, or data flow, start with a Mermaid diagram
showing the structure, then explain in prose.

What an output style is not

  • Not enforcement. It is an instruction the agent follows. For something that must happen every time, use a hook (Lesson 55). For what the agent should know about your project, use CLAUDE.md (Lesson 65).
  • Not for subagents. Styles apply to the main conversation and to a fork (Lesson 47). Other subagents run their own system prompt, so a style doesn't change how they respond.
  • Not a permission change. The Proactive style doesn't change your permission mode; prompts appear the same way.
  • Not instant for a new file. In the terminal, style files are read at startup. Create or edit one mid-session and you restart to pick it up. Switching between existing styles applies from your next message (Claude Code v2.1.251 or later, checked October 2026).

Build It

  1. Run /output-style concise, then ask a question with a factual answer. Note the length.

✅ You pass when the reply leads with the result and you can say what was left out compared with the default.

  1. Run /output-style explanatory, make a small code change, and look for an Insight block.

✅ You pass when you can point at the block and say it explains a choice rather than narrating the steps.

  1. Write a custom style in ~/.claude/output-styles/ with keep-coding-instructions: true. Restart Claude Code and select it with /output-style.

✅ You pass when the style is in the picker and the agent still codes with its normal care.

  1. Write a second custom style without keep-coding-instructions. Select it and ask for a code change.

✅ You pass when you can describe what the agent stopped doing, and say why the field was responsible.

  1. With a style active, ask the agent to do something destructive but reversible. Watch for the confirmation.

✅ You pass when you can explain that the style is an instruction, not a lock, and that permissions still apply.

Use It

Command / conceptWhen you reach for it
/output-style <name>Switch styles; list them with no argument
/config → Output stylePick from a menu
outputStyle in settingsSet a default, or set it per project
~/.claude/output-styles/Your styles, every project
.claude/output-styles/Team styles, committed

Concise / Explanatory / LearningBuilt-ins for shorter, teaching, and hands-on sessions

Exercises

  1. Your team wants every explanation to start with a diagram, but the agent must still work like a careful engineer. Write the style and prove both halves. ✅ You pass when explanations start with a diagram and the agent still scopes and verifies its code changes.
  1. You draft documentation in Claude Code, not code. Write a style for that job and decide, out loud, whether to keep the coding instructions. Then test a coding task under that style. ✅ You pass when you can say what the style gained you on documentation and what it cost you on the coding task.
  1. A teammate says "just put 'be concise' in CLAUDE.md." Compare the two approaches on one task and write down which is better and why. ✅ You pass when you can name a case where a rule in CLAUDE.md is right and a case where a style is right.

Key Terms

TermWhat people sayWhat it actually means
output style"a prompt preset"Instructions that set role, tone, and format for every response in a session.
keep-coding-instructions"keep the defaults"Whether your custom style keeps Claude Code's built-in software-engineering instructions. Defaults to false.
built-in styles"the four modes"Proactive, Concise, Explanatory, Learning — each adds to the default.
force-for-plugin"always on"A plugin style that applies automatically when the plugin is enabled.
style vs hook"both change behaviour"A style is an instruction the agent follows; a hook runs regardless of what it decides.
style vs CLAUDE.md"both set context"A style shapes how it responds; CLAUDE.md says what it should know.

Check yourself

4 questions. Answer before you reveal — recognising the right option is not the same as being able to produce it.

  1. You write a custom output style to change how the agent explains things. After selecting it, the agent stops scoping its code changes and stops verifying its work. What did you miss?

    1. Nothing — that is expected, and you should switch back to Default for coding
    2. keep-coding-instructions: true, which keeps the built-in software-engineering instructions alongside your style
    3. force-for-plugin: true, which prevents the coding instructions from being dropped
    4. outputStyle set in ~/.claude/settings.json rather than the project settings
    Show answer

    B. keep-coding-instructions: true, which keeps the built-in software-engineering instructions alongside your style

    A custom style replaces Claude Code's built-in software-engineering instructions unless keep-coding-instructions is true. Option 0 is tempting because the symptoms look like 'this style is for writing' — but you did not intend to change the coding behaviour, and the field is the fix.

  2. You want the agent to lead every explanation with a diagram, but only in one repository. Where do you put the style file?

    1. ~/.claude/output-styles/, so it is available everywhere
    2. .claude/output-styles/ in that repository
    3. .claude/rules/, because it is a project instruction
    4. CLAUDE.md, under a heading
    Show answer

    B. .claude/output-styles/ in that repository

    A project output style lives in .claude/output-styles/ and is committed with the repo. Option 0 is tempting because it works immediately — but a user-level style applies to every project, which is more than you asked for.

  3. Your team needs a formatter to run after every file edit, no exceptions. A teammate suggests an output style that says "always run the formatter after edits." Why is that the wrong mechanism?

    1. Output styles can't mention tools, only tone
    2. A style is an instruction the agent follows, so it can be missed; a hook runs regardless of what the agent decides
    3. Output styles only apply to the first response in a session
    4. A style would need keep-coding-instructions: true to run commands
    Show answer

    B. A style is an instruction the agent follows, so it can be missed; a hook runs regardless of what the agent decides

    Styles are guidance, not enforcement, so a guarantee needs a hook. Option 0 is tempting because styles do read like prompts — but the problem is not what they can mention; it is that they cannot guarantee an action.

  4. You create a new custom style file while a session is running, select it, and nothing changes. What is the most likely cause?

    1. The style name in the frontmatter doesn't match the file name
    2. In the terminal, style files are read at startup, so a new file needs a restart
    3. Custom styles must be set in settings.json before a session starts
    4. The style was rejected because it has no description
    Show answer

    B. In the terminal, style files are read at startup, so a new file needs a restart

    The terminal reads style files when it starts, so a file created mid-session is picked up after a restart. Option 2 is tempting because settings often need a restart — but selecting an existing style mid-session does work; it is the new file that is not read.
