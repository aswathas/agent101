LEARN · PHASE 10 · LESSON 67

Rules and Path-Scoped Rules

You can split your instructions into topic files and make each one load only when the agent touches the files it is about.

Type
Learn
Prerequisites
Lesson 65, CLAUDE.md — the 200-Line Rule
Time
~30 minutes

Learning Objectives

  • Split a long CLAUDE.md into .claude/rules/ topic files
  • Write paths: frontmatter so a rule loads only for matching files
  • Predict which rules are in the window at launch and which load on demand
  • Choose between a rule and a skill for a given instruction
  • Explain why a rule is guidance the agent follows, not enforcement

The Problem

Your API conventions live in CLAUDE.md. So does the test convention, and the React convention, and the CSS convention. The agent working on a CSS file is carrying 40 lines of API rules it will never use — every turn, in every session.

That is the 200-line problem from Lesson 65, but the fix is not to delete the rules. It is to make them load only when they are relevant. An instruction that matters for src/api/** has no business in the window while the agent edits a stylesheet.

The Concept

A rule is a markdown file in a .claude/rules/ directory. It is an instruction file like CLAUDE.md, with one addition: it can carry a paths: field that decides when it loads.

Rules live in two places:

  • Project: .claude/rules/ — committed, shared with the team.
  • User: ~/.claude/rules/ — yours, every project. Loaded before project rules, so a project rule appears later in context. Neither overrides the other; if they conflict, the agent may follow either.

All .md files under the directory are discovered recursively, so frontend/react.md and backend/api.md are both found.

Path-scoped rules

A rule without frontmatter loads at launch. A rule with a paths: field loads only when the agent works with a matching file — read, write, or edit, including a Bash command like cat or head that counts as a read.

---
paths:
  - "src/api/**/*.ts"
  - "tests/**/*.test.ts"
---

# API rules

- Every endpoint validates input with a schema
- Return shape is `{ data }` or `{ error }`

paths accepts a YAML list or a comma-separated string. Glob patterns cover extensions, directories, or both:

PatternMatches
**/*.tsAll TypeScript files, any directory
src/**/*Everything under src/
*.mdMarkdown in the project root
src/components/*.tsxReact components in one directory

Brace expansion works: "src/**/*.{ts,tsx}". One detail with teeth — paths is the only field Claude Code reads from a rule. Any other frontmatter key is ignored without an error. And if the YAML between the --- markers doesn't parse, the rule loads as if it had no paths at all, quietly becoming always-on.

Rules are not enforcement

Like CLAUDE.md, a rule is guidance the agent reads. It is not a permission and not a hook. If an instruction must happen every time, a rule is the wrong tool — that is a hook (Lesson 55). If an instruction is a procedure the agent runs on demand, that is a skill (Lesson 40).

You wantUseWhy
Always-on project knowledgeCLAUDE.md or an unconditional ruleLoads every session
Knowledge only when certain files are touchedA paths: ruleLoads on match, saves context otherwise
A procedure for one kind of taskA skillLoads on invoke
Something that must happen, every timeA hookEnforced, not requested

The reframe: a rule is not a smaller CLAUDE.md — it is a CLAUDE.md with a condition, and the condition is the whole point: it loads exactly when the files it talks about come into view.

A few sharp edges

  • Symlinks work, but a link whose target is outside your working directory is treated like an external import and needs approval once per project (Lesson 70).
  • Excluding files: claudeMdExcludes in a settings file skips specific CLAUDE.md and rules files by path or glob — useful in a monorepo where another team's rules leak in.
  • Prompt caching: loading a new rule mid-session changes what is in the window, so the cache is rebuilt. That is a small cost paid once, not every turn.

Build It

  1. Create .claude/rules/testing.md with a paths: frontmatter scoped to your test files.

✅ You pass when the file exists with valid paths: frontmatter.

  1. Start a fresh session and run /context. Look for the rule.

✅ You pass when the rule is not under the loaded memory files at launch.

  1. Ask the agent to edit a file matching the glob. Watch for a Loaded line naming the rule, then run /context again.

✅ You pass when the rule now appears, and you can say which file triggered it.

  1. Add a second rule with no frontmatter. Restart and run /context.

✅ You pass when the unconditional rule is loaded at launch and the scoped one is not.

  1. Break the YAML between the --- markers in the scoped rule (leave a field unclosed). Restart.

✅ You pass when you can explain why the rule loaded unconditionally despite the paths: you wrote.

Exercises

  1. Take one section out of a long CLAUDE.md — say, the API conventions — and move it into .claude/rules/api-design.md scoped to your API directory. Prove it stops loading in a session that never touches those files. ✅ You pass when /context shows the rule absent at launch and present after the agent reads a matching file.
  1. Write two rules that both claim to govern the same file — one user-level, one project-level — with different guidance. Open the file and observe which the agent follows. ✅ You pass when you can explain that both loaded and neither overrides the other, so the agent may follow either, and you have removed the conflict.
  1. You have an instruction that must run after every edit, not just when the agent is in a certain folder. Write it as a rule first, watch it get skipped, then convert it to the right mechanism. ✅ You pass when you can name why the rule failed and which mechanism you used instead.

Key Terms

TermWhat people sayWhat it actually means
rule"a small CLAUDE.md"An instruction file in .claude/rules/ that can be scoped with paths:.
paths:"a filter"The only frontmatter field a rule reads. Globs that decide when the rule loads.
path-scoped rule"a rule for one folder"A rule that stays out of the window until the agent touches a matching file.
load at launch"it's always on"Rules without paths:, loaded every session like .claude/CLAUDE.md.
user vs project rules"project overrides user"They concatenate; user rules load first. Conflicts are not resolved for you.
rules vs skills"both are instructions"Rules load at launch or on a file match; skills load when invoked.

Check yourself

4 questions. Answer before you reveal — recognising the right option is not the same as being able to produce it.

  1. You write .claude/rules/api-design.md with paths: ["src/api/**/*.ts"]. You start a fresh session and run /context. The rule isn't listed. Is something wrong?

    1. Yes — the frontmatter is invalid, so the rule failed to load
    2. No — a path-scoped rule loads only after the agent reads, writes, or edits a matching file
    3. Yes — rules must live in ~/.claude/rules/ to load at launch
    4. No — /context never lists rules, only CLAUDE.md files
    Show answer

    B. No — a path-scoped rule loads only after the agent reads, writes, or edits a matching file

    Path-scoped rules are deliberately absent at launch and load on the first matching file. Option 0 is tempting because 'not in /context' usually means 'didn't load' — but for a scoped rule, absence at launch is the correct behaviour.

  2. A rule you scoped to test files starts loading in every session, even when no test file is touched. You check the frontmatter and it looks right. What is the most likely cause?

    1. The paths value is a comma-separated string, which is not allowed
    2. The YAML between the --- markers doesn't parse, so the rule loads as if it had no paths
    3. Rules with paths always load at launch; only skills are scoped
    4. The rule is in a subdirectory, which disables scoping
    Show answer

    B. The YAML between the --- markers doesn't parse, so the rule loads as if it had no paths

    If the frontmatter YAML fails to parse, Claude Code ignores it and loads the rule unconditionally. Option 0 is tempting because it sounds like a syntax rule — but both a YAML list and a comma-separated string are accepted, so that is not the cause.

  3. Your team needs a formatter to run after every file edit, without exception. You put the instruction in .claude/rules/formatting.md. What will happen?

    1. It works — rules are loaded every session and the agent follows them
    2. The agent will usually follow it, but nothing guarantees it; a hook is the mechanism that runs every time
    3. The rule will be skipped because formatting is not a file path
    4. The rule will be rejected because it has no paths field
    Show answer

    B. The agent will usually follow it, but nothing guarantees it; a hook is the mechanism that runs every time

    Rules are guidance the agent reads, not enforcement, so an occasional miss is expected. Option 0 is tempting because the rule does load every session — but loading is not the same as guaranteeing the action, which is what a hook is for.

  4. You have a release procedure the agent should run only when you ask for a release. Where does it belong?

    1. An unconditional rule, so it is always in the window
    2. A path-scoped rule, scoped to release files
    3. A skill, which loads when you invoke it
    4. A user-level rule in ~/.claude/rules/
    Show answer

    C. A skill, which loads when you invoke it

    A procedure that runs on demand belongs in a skill, which loads on invoke. Option 1 is tempting because scoping sounds close to on-demand — but a path-scoped rule loads on a file match, not on your request, so the release procedure would load whenever you happened to open a matching file.
