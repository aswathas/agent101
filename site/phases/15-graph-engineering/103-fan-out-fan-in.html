LEARN · PHASE 15 · LESSON 103

Fan-Out / Fan-In Patterns

You can design a join before you launch the fan-out — deciding what "done"

Type
Learn
Prerequisites
Lesson 99 (Task Graphs); Phase 12, Lesson 79 (parallel() vs pipeline()), Lesson 80 (The Completion-Order Gotcha)
Time
~35 minutes

Learning Objectives

  • Recognise fan-out and fan-in, and tell map from broadcast
  • Choose join semantics: all-of, any-of, or quorum
  • Collect parallel results by key, not by arrival order
  • Decide, before the run, what a missing child does to the join

The Problem

A report generator fanned out eight children, one per section. Eight agents returned: seven as JSON, one as a friendly paragraph, and one returned nothing at all because it hit a token limit and stopped.

The join node took "whatever came back" and assembled a report. It succeeded. The report shipped with one section missing — and a reviewer found out a week later, because the run reported success and the missing section looked like an editorial choice.

Nothing about the fan-out was hard. Eight agents, eight sections. The bug was in the fan-in: nobody had decided what each child must return, or what the join should do when one of them returned nothing. The join was written to be convenient, and convenient turned a failure into silence.

The Concept

Fan-out is one node launching many children. Fan-in is one node consuming them. Between them is the whole design problem.

Fan-out is the easy half and it is where the attention goes, because it is where the agents are. The fan-in is where the design lives, because it is where you decide what done means.

Two contracts you must fix before launching

1. The result shape. Every child returns the same kind of thing, tagged with which node produced it. A keyed record — { node: "section-3", ok: true, output: "…" } — beats "a string" or "a paragraph" or "whatever the agent felt like". The join then works on a uniform shape and never has to guess.

2. The join semantics. "Wait for all of them" is only one choice:

JoinWaits forUse when
all-of (barrier)Every childThe output is invalid without any of them — a report with all sections.
any-ofThe first child to succeedYou want one answer from several routes — a race, a first-working mirror.
quorum (k of n)Any k childrenYou can tolerate some loss — three-of-five reviewers.

Each has a failure answer attached, and that answer is the design. For an all-of join, a missing child can either fail the join or produce a partial output carrying an explicit gap marker. Both are legitimate. The illegitimate one is the default the bug above used: silently drop the missing child and report success.

Completion order is not node order

Children finish in whatever order they finish. The one that started first may return last; the fastest may be the least important. So a join must key its results by node id, never by arrival:

// Wrong: positional — a fast child shifts every later result.
const report = results.map((r) => r.output).join('\n\n');

// Right: keyed — every child lands in its own slot, missing or not.
const byNode = new Map(results.map((r) => [r.node, r]));
const sections = expected.map((id) =>
  byNode.has(id) ? byNode.get(id).output : `[MISSING: ${id}]`,
);

This is the same trap the completion-order lesson names — a pipeline that assumes results come back in the order you sent them. Keying by node id is the fix, and it is the same fix at every join you build.

Map versus broadcast

A fan-out is one of two shapes, and the difference matters for the result shape:

  • Map: the same operation over different inputs. "Lint each of these 30 files." Every child does the same thing; the results compare.
  • Broadcast: the same input through different lenses. "Review this PR for security, performance, and tests." Every child does a different thing; the results complement.

A map's join can usually combine (concatenate, aggregate); a broadcast's join must reconcile (the three lenses may disagree). Knowing which you have tells you whether the fan-in is an assembly or an argument.

Width is a cost

Every child is a window, a claim, and a slice of budget. A fan-out of two hundred is rarely two hundred times the value. When the children are cheap and independent, go wide; when they are expensive or must be reconciled, go narrow and iterate. The join does not care how wide you went — but your budget does.

The reframe: fan-out is the easy half; the design is the fan-in — the join

is where you decide what "done" means and what happens to the child that never

came back.

parallel() versus pipeline(), and the completion-order gotcha, are Phase 12, Lessons 79 and 80. Which combinators a runner exposes is version-gated; check Run agents in parallel.

Build It

You will build an all-of fan-in that reports a missing child instead of hiding it. Run this as a plain Node script; the shape maps directly onto a workflow's fan-out.

1. Define the children and the expected set

// fanin.mjs
const expected = ['intro', 'body', 'risks', 'outro'];
const work = {
  intro: async () => ({ node: 'intro', ok: true, output: 'Introduction…' }),
  body:  async () => ({ node: 'body',  ok: true, output: 'Body…' }),
  risks: async () => { throw new Error('token limit'); },
  outro: async () => ({ node: 'outro', ok: true, output: 'Outro…' }),
};

✅ You pass when every child returns the same keyed shape, or throws.

2. Fan out with allSettled, then join by key

const settled = await Promise.allSettled(expected.map((id) => work[id]()));

const byNode = new Map();
for (const r of settled) {
  if (r.status === 'fulfilled') byNode.set(r.value.node, r.value);
}

const report = [];
for (const id of expected) {
  report.push(byNode.has(id) ? byNode.get(id).output : `[MISSING: ${id}]`);
}
console.log(report.join('\n'));
console.log(`complete: ${byNode.size}/${expected.length}`);

✅ You pass when the output contains [MISSING: risks] and the complete line reads 3/4 — the hole is visible, not swallowed.

3. Deliberately reorder the results

Change work so risks resolves slowly and outro resolves first. Keep the same join.

✅ You pass when the output is unchanged, because the join keyed by id and never trusted arrival order.

4. Switch the join to quorum

Make the join succeed when at least three of the four children arrive.

✅ You pass when the run reports success and still names which child was missing — a quorum join is allowed to proceed, not allowed to forget.

Use It

SituationMove
Output is invalid without every childAll-of (barrier), and fail the join on a miss.
Need one good answer from several routesAny-of: take the first success, cancel the rest.
Can tolerate some lossQuorum: succeed at k of n, and log the misses.
Same operation over many inputsMap. The join can usually combine.
One input through several lensesBroadcast. The join must reconcile disagreement.
Results arrive out of orderKey by node id. Never join positionally.
A child returns a different shapeFix the result contract at the fan-out, not in the join.
Hundreds of childrenCheck the budget. Fan-out width is a cost, not a target.

Exercises

  1. Build the all-of join above and make it print [MISSING: …] for a dropped child rather than a silent gap. ✅ You pass when the completeness count is shown and never rounds a miss up to success.
  1. Reorder your children's completion times and show the joined output is byte-for-byte identical. ✅ You pass when you can point at the keyed map as the reason order did not matter.
  1. Take a real fan-out of yours and write, before running it, its result shape and its join semantics in one sentence each. ✅ You pass when the sentence names the shape, the join type, and what a missing child does.

Key Terms

TermWhat people sayWhat it actually means
fan-out"spawning agents"One node launching N parallel children.
fan-in / join"collecting results"One node consuming N children. Where "done" is defined.
barrier (all-of)"wait for everyone"The join proceeds only when every child has returned.
any-of"race them"The join proceeds on the first success.
quorum (k of n)"most of them"The join proceeds when k children have returned.
keyed result"the output"A child's return tagged with its node id, so the join never trusts order.
map vs broadcast"fan out"Same operation over many inputs versus one input through many lenses.
completion order"they come back in order"False. Children finish by their own timing; key, do not index.

Check yourself

4 questions. Answer before you reveal — recognising the right option is not the same as being able to produce it.

  1. A report fans out eight section-writers and joins them by concatenating results in arrival order. One slow section and one fast section swap places in the output. What is the fix?

    1. Make every child finish at the same time
    2. Key each result by node id and place it in its own slot, so arrival order is ignored
    3. Switch from all-of to any-of so only the first result is used
    4. Add more children so the probability of reordering drops
    Show answer

    B. Key each result by node id and place it in its own slot, so arrival order is ignored

    A join must map results to slots by identity, not by the sequence they arrived in. Option A is impossible to guarantee and treats a design bug as a timing bug. Option C discards most of the work. Option D changes nothing — reordering is inherent to parallel children; the keyed join is the only real fix.

  2. Five reviewer agents examine one pull request. You need at least three verdicts to close the review, and you are fine if two are late. Which join, and what must it still do?

    1. All-of; require every reviewer before closing
    2. Quorum (three of five); it may proceed on three but must record which reviewers did not report
    3. Any-of; take the first verdict and cancel the rest
    4. A barrier of one; close on the fastest reviewer
    Show answer

    B. Quorum (three of five); it may proceed on three but must record which reviewers did not report

    You need k of n and can tolerate loss, which is exactly a quorum join — and a quorum that forgets the missing reviewers hides the fact that two never spoke. Option A is over-strict for the stated need. Option C takes a single verdict and discards the point of five reviewers. Option D is any-of wearing the wrong name.

  3. A fan-out is "review this PR for security, performance, and test coverage." The three results are meant to be complementary and may contradict each other. Is this a map or a broadcast, and what does that imply for the join?

    1. Map — the join can simply concatenate the three outputs
    2. Broadcast — the join must reconcile three different lenses, including handling disagreement
    3. Map — the join can pick whichever result is longest
    4. Broadcast — the join should drop the two disagreement points
    Show answer

    B. Broadcast — the join must reconcile three different lenses, including handling disagreement

    One input through three different lenses is a broadcast; the lenses can disagree, so the join reconciles rather than merely assembles. Option A is the tempting shortcut because the outputs look combinable, but concatenation does not resolve a security finding that contradicts a performance recommendation. Option C picks by length, which is meaningless. Option D hides exactly the information that matters.

  4. An all-of report job has one child that intermittently returns nothing. The team proposes making the join always succeed and just leaving that section blank. What has to be true for that to be acceptable?

    1. Nothing — always succeeding is more robust
    2. The join must emit an explicit gap marker (or fail loudly), so a missing child is distinguishable from a section that is intentionally empty
    3. The child should be removed from the fan-out
    4. The join should retry forever until the child returns
    Show answer

    B. The join must emit an explicit gap marker (or fail loudly), so a missing child is distinguishable from a section that is intentionally empty

    A partial join is legitimate only if the gap is observable; otherwise a failure silently reads as a choice, which is the bug in The Problem. Option A is the tempting "be resilient" reflex that caused the bug. Option C changes the deliverable instead of handling the failure. Option D risks an unbounded run, which Lesson 104 bounds with a retry policy.
