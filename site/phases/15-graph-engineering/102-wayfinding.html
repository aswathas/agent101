LEARN · PHASE 15 · LESSON 102

Wayfinding — Producing Decisions, Not Deliverables

You can put a decision on the graph as a node — with an owner, an output, and

Type
Learn
Prerequisites
Lesson 99 (Task Graphs); Phase 14, Lesson 92 (Most Agent Calls Are Decisions)
Time
~30 minutes

Learning Objectives

  • Tell a decision node from a deliverable node and from a spike
  • Put a decision on the graph with an owner, an output, and its consumers
  • Write a decision record downstream nodes can act on without re-asking
  • Spot an invisible dependency — a decision nobody assigned

The Problem

Three builders each had a node in the graph: build the settings sync, build the billing hook, build the audit log. All three needed the same answer — which auth scheme does this product use? — and that answer was not a node. It was a question in a chat that nobody owned.

The three builders each made a reasonable guess. They chose three different schemes. The fan-in produced three components that could not talk to each other, and the fix was not a merge — it was a rewrite of two of the three.

The schedule had said the graph was three parallel nodes and a join. It was actually three nodes joined by a decision that lived nowhere on the graph. That is what an unowned decision does: it blocks every consumer at once, while looking like nobody's task.

The Concept

A node produces an output. Usually that output is an artifact — code, a file, a passing test. But some nodes produce a decision: a choice, the options that were weighed, and the reason. Call it a wayfinding node, from the navigation term for the work that gets you oriented before you move.

A wayfinding node is not special machinery. It is a node like any other:

  • It has an output: a decision record (the choice and its rationale).
  • It has consumers: the nodes whose work depends on the choice.
  • It has an owner: one person or agent who makes the call.
  • It has a position on the graph, so it blocks its consumers and nothing else.

Once the decision is a node, the picture tells the truth: the three builders can run in parallel, but only after the decision — and the decision can be made once, by one owner, cheaply, instead of three times by guess.

Decision, spike, deliverable

Three kinds of node are easy to confuse. The difference is what they produce:

NodeProducesConsumers do what with it
DeliverableA shippable artifactDepend on it existing and working
Spike / experimentKnowledge: a number, a feasibility answerUse it to decide something
Wayfinding / decisionA commitment: choice + rationaleBuild against the choice, and stop re-asking

A spike reduces uncertainty by finding out. A decision record reduces uncertainty by committing. You often do a spike immediately before a decision node, and the spike's output feeds the decision's input. The decision is the node other things depend on; the spike is a helper that informs it.

Make the decision its own node, not a side effect

The failure mode is a decision that never becomes a node. It hides in a chat message, a comment, a verbal "let's just use X", or worse — it hides nowhere, and each consumer invents its own.

Putting it on the graph does three things that are invisible when the decision lives in prose:

  1. It blocks exactly its consumers. A decision everyone needs is a fan-out bottleneck and the graph now shows it. A decision only one node needs does not hold up the rest.
  2. It gets an owner and a moment. Unowned decisions drift; a node with an owner and a due position in the frontier gets made.
  3. It stops re-litigation. The rationale is recorded, so a downstream node reads the decision instead of asking again — which is the same reason a decision record beats a decision made in conversation.

Sometimes the highest-leverage first node in a project is not code at all. It is the decision that everything else was quietly waiting on. Wayfinding is choosing to do that first, on the graph, on purpose.

The reframe: some nodes produce code and some produce a decision — and a

decision you did not put on the graph blocks every node downstream of it while

looking like nobody's task.

The idea is version-independent; whether a given runner models a node as "decision" or just as a task is cosmetic. What matters is that the output and its consumers are on the graph. Mechanism pages: Run agents in parallel.

Build It

Take the graph you have been building (tasks.json from Lesson 99, edges labelled in Lesson 100).

1. Walk the nodes and ask "what does this need to know?"

For each deliverable, list the facts it cannot proceed without. Anything that is not already an artifact-producing node is a candidate decision.

settings sync  needs: which auth scheme, where tokens live
billing hook   needs: which auth scheme
audit log      needs: which auth scheme, what retention period

✅ You pass when you have a list of questions, not of tasks.

2. Promote each shared question to a node

Any question needed by more than one consumer becomes a wayfinding node. Give it id, owner, and consumers — the nodes that need it.

{
  "tasks": [
    { "id": "decide-auth", "kind": "decision", "owner": "you", "needs": [],
      "consumers": ["settings", "billing", "audit"] },
    { "id": "settings", "kind": "deliverable", "needs": ["decide-auth"] },
    { "id": "billing",  "kind": "deliverable", "needs": ["decide-auth"] },
    { "id": "audit",    "kind": "deliverable", "needs": ["decide-auth", "decide-retention"] },
    { "id": "decide-retention", "kind": "decision", "owner": "you", "needs": [], "consumers": ["audit"] }
  ]
}

✅ You pass when every shared question exists as a node and both waves.mjs and the graph agree that the builders wait on it.

3. Write one decision record

The output of a wayfinding node is a record, and it must be enough for a consumer to act without asking. Four parts, short:

# Decision: auth scheme
- Context: three components need to share a session; no SSO requirement yet.
- Options: (a) opaque session cookie, (b) signed JWT, (c) third-party IdP.
- Decision: (a) opaque cookie, server-side store. Revisit if SSO lands.
- Consequences: session store becomes a node we must deploy; tokens never
  leave the server.

✅ You pass when a reader who never saw the discussion can build against it and know what would change the decision.

4. Find an invisible one

Look for a deliverable whose blocker is not any node in the graph — a question someone answered in chat. That is an invisible dependency.

✅ You pass when you can name it and add it as a node, with a consumer list.

Use It

SituationMove
Two or more nodes need the same unresolved answerPromote it to a wayfinding node with those nodes as consumers.
One node needs an answer nobody hasStill a node — it just blocks only that one node.
The answer cannot be made without dataA spike feeds the decision; the decision is the node consumers wait on.
The decision is made but downstream nodes keep askingWrite the record. The record is the output.
A "decision" you cannot phrase as options and a choiceIt is not ready to be a node. It is still a question.
A decision everyone needs, earlyExpect a fan-out bottleneck; make it as early in the frontier as possible.
A decision only one node needsDo not gate everyone on it — scope its consumers narrowly.

Exercises

  1. Take a real project and list every answer a builder would need before starting. Mark which are shared. ✅ You pass when at least one shared answer is currently an unowned question in your notes rather than a task.
  1. Promote the highest-fan-out decision to a node and write its record. ✅ You pass when the record names options, a choice, and the condition that would reverse it.
  1. Take the graph from Lesson 99 and add a decision node. Recompute the waves. ✅ You pass when the graph shows three builders that previously looked independent now waiting on one shared node — and you can say which wave grew.

Key Terms

TermWhat people sayWhat it actually means
wayfinding node"just a task"A node whose output is a decision: a choice plus its rationale.
decision record"a note in chat"The durable output of a wayfinding node: context, options, choice, consequences.
invisible dependency"everyone knows that"A blocker that exists in conversation but not on the graph. It blocks silently.
spike"a research task"A node that produces knowledge to inform a decision. Not the decision itself.
owner"someone will figure it out"The single person or agent accountable for making the call.
re-litigation"we already decided"Downstream nodes re-asking because the rationale was never recorded.

What this lesson skipped

How agents make decisions cheaply. Decision models and confidence gating are Phase 14, Lessons 92–94.

Joining consumers of a decision. What the three builders do with the shared answer at their join is Lesson 103.

Failure of a decision node. What happens when the owner never decides is Lesson 104 — a decision node that never completes is a stranded parent.

Decision-making frameworks (pros/cons grids, weighted scoring). Useful, but they are how you decide, not where the decision lives on the graph.

Check yourself

4 questions. Answer before you reveal — recognising the right option is not the same as being able to produce it.

  1. Four builders each begin work, and each quietly picks a different date format because nobody decided one. Their outputs later fail to combine. Where was the missing node?

    1. A deliverable node for the combine step
    2. A wayfinding node whose output is the date-format decision and whose consumers are the four builders
    3. A spike that measures how long each builder wants to spend
    4. A soft edge between the builders
    Show answer

    B. A wayfinding node whose output is the date-format decision and whose consumers are the four builders

    The shared unresolved answer is a decision needed by all four, so it belongs on the graph as one node that gates them. Option A describes the fan-in, which is fine — the failure is upstream of it. Option C confuses a spike (produces knowledge) with the decision that was actually missing. Option D removes an edge the builders do not have; there was no explicit connection at all, which is the problem.

  2. A team says "we decided to use an event bus months ago" but every new component re-asks and two have since chosen different queues. What is the wayfinding failure?

    1. The decision was never made
    2. The decision was made but no record was produced, so it cannot be consumed — a decision that lives in conversation blocks invisibly and gets re-litigated
    3. The event bus should have been a spike
    4. The components needed a longer lease
    Show answer

    B. The decision was made but no record was produced, so it cannot be consumed — a decision that lives in conversation blocks invisibly and gets re-litigated

    The output of a wayfinding node is the record; without it, downstream nodes cannot read the commitment and drift. Option A is the tempting reading, but the decision was made — the failure is that its output was never written down. Option C swaps a commitment for knowledge-gathering. Option D is a claiming concept and unrelated.

  3. A single node needs to know the retention period for logs. Nobody else needs this. Should you add a separate wayfinding node that gates other work?

    1. Yes — every decision must be a top-level node
    2. No — make the decision a node that gates only that one consumer, so it does not become a bottleneck for unrelated work
    3. No — leave it out of the graph and let the builder decide
    4. Yes, and make it block the whole frontier so it is resolved first
    Show answer

    B. No — make the decision a node that gates only that one consumer, so it does not become a bottleneck for unrelated work

    A decision node should block exactly its consumers; with one consumer, scoping it narrowly keeps the decision from serialising unrelated work. Option A is the tempting rule-taken-too-far and creates bottlenecks. Option C is the invisible-dependency bug: an unassigned question the builder will guess at. Option D is over-blocking — the retention decision has one consumer and does not belong on the critical path of everything else.

  4. You cannot phase a blocker as "option A or option B, choose one, here is why" — it is really "go find out whether the vendor API supports webhooks." What kind of node is this, and what comes next?

    1. A wayfinding node; write the decision record now
    2. A spike — it produces knowledge; the decision it informs becomes its own node afterwards
    3. A deliverable; ship the support check as a feature
    4. Nothing — unknown blockers cannot be represented on a graph
    Show answer

    B. A spike — it produces knowledge; the decision it informs becomes its own node afterwards

    An open question that needs investigating is a spike: its output is a fact, which then feeds a decision node. Option A is tempting because both are "up front," but you cannot commit a choice before the fact exists. Option C ships an investigation as if it were a product. Option D is false — spikes are ordinary nodes and belong on the graph.
