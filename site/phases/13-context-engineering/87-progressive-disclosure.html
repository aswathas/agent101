LEARN · PHASE 13 · LESSON 87

Progressive Disclosure — Skills as a Loading Strategy

You can split a wall of reference text into metadata you always pay, a body

Type
Learn
Prerequisites
Lesson 86 (What Loads, What Costs), Lesson 44 (Author a Skill)
Time
~30 minutes

Learning Objectives

  • Name the three tiers a skill loads in, and when each one is paid
  • Read a skill's startup cost from /context and separate it from its body cost
  • Move a long checklist into references/ and show it does not load until asked
  • Use disable-model-invocation: true to keep a side-effecting skill at zero cost until you invoke it
  • Put the rule that must survive compaction at the top of the body, on purpose

The Problem

Your review skill works. It is 600 lines: an intro, a long security checklist, a house-style guide, and — near the bottom — the three rules that actually catch bugs.

It fires. It reviews. Everything is in the window, and it stays there for the rest of the session. Then the conversation compacts to free space, and only the first 5,000 tokens of the skill come back. The part that returns is your intro. The three rules that matter are gone, silently, and Claude keeps reviewing without them.

You wrote a document. You needed a loading strategy.

The Concept

A skill loads in three tiers, and each tier has a different price and a different time. This is what progressive disclosure means: show a little, load more only when it is needed.

Tier 1 — metadata, always paid

The skill's description (plus when_to_use) is the only part that sits in the window from startup. It is one line, so Claude knows the skill exists. The combined description + when_to_use text is truncated at 1,536 characters in the listing.

There is a switch that removes even this. A skill with disable-model-invocation: true is not in the startup listing at all. It costs nothing until you type its name. Put it on anything with side effects — committing, deploying, sending.

FrontmatterYou can invokeClaude can invokeLoaded at startup
(default)YesYesDescription only
disable-model-invocation: trueYesNot on its ownNothing
user-invocable: falseNoYesDescription only

Tier 2 — the body, paid on use

When the skill is invoked, the rendered body enters the conversation as one message and stays across later turns. The file is not re-read on later turns, which is why instructions must be written as standing rules, not one-time steps.

After auto-compaction, Claude Code re-attaches the most recent invocation of each skill, keeping the first 5,000 tokens of each, with a 25,000-token budget shared across skills and filled most-recent-first. Consequence: an old skill can be dropped entirely, and within a skill only the top survives.

Tier 3 — supporting files, paid on demand

Anything else in the folder ships alongside the skill but costs nothing until the body points at it and something reads it. A 400-line checklist in references/security.md is free until the run that needs it.

.claude/skills/review/
├── SKILL.md              tier 1 + tier 2
└── references/
    ├── security.md       tier 3, free until read
    └── house-style.md    tier 3, free until read

The reframe: a skill is a loading strategy you design, not a document you

write — every line belongs to one of three tiers, and the tier decides when you

pay for it.

Verified against the skills page and the context window page on 2026-10-15. The 1,536-character cap, the 5,000-token re-attach, and the 25,000-token budget are version-gated and will move; the three tiers will not.

Build It

Use a skill you already own that has grown past ~150 lines. If you do not have one, take the longest reference section of your CLAUDE.md and make it a skill first.

  1. Run /context in a fresh session. Find the Skill descriptions block. Note its total.

✅ You pass when you can name the startup cost of your skill listing.

  1. Open the skill. Find its longest block — the checklist or style guide. Create a references/ directory beside SKILL.md and move that block into a file there.
  1. Replace the moved block with one line that says when to read it:

``markdown For the full security checklist, read references/security.md. ``

  1. Invoke the skill on a task that does not need the checklist. Confirm the reference file was not read and cost nothing.

✅ You pass when you can show both states: a run where security.md never loaded, and a run where it did.

  1. Put the three rules that must catch bugs at the top of the body. Move them to the bottom, compact the session, and compare what came back.

✅ You pass when you can say which position survived and tie it to the 5,000-token cap rather than to intuition.

  1. Add disable-model-invocation: true to a skill with side effects. Restart and run /context.

✅ You pass when the skill no longer appears in the startup listing, yet still runs when you type its name.

Use It

Exercises

  1. Measure a listing. In a project with several skills, capture the Skill descriptions cost from /context, then add one new skill with a 20-word description. Capture again. ✅ You pass when you can state the per-skill startup cost you measured, not estimated.
  1. Relocate a checklist. Take a skill over 150 lines and move its longest section to references/. Keep a one-line pointer. ✅ You pass when a run that does not need the section never reads the file, and a run that does read it — both observed, not assumed.
  1. Design for compaction. Choose the single rule your skill must never lose. Put it first, then compact the session and confirm it came back. Move a second, less important rule below the 5,000-token line and observe it drop. ✅ You pass when you can point at which rule survived and which was cut, and say how many tokens the attached copy held.

Key Terms

TermWhat people sayWhat it actually means
progressive disclosure"lazy loading for prompts"Metadata always, body on invoke, supporting files on demand. Three tiers, three times.
the listing"the skills"Only name + description load at startup. The body is not loaded until the skill is used.
disable-model-invocation"make it manual"The skill leaves the startup listing entirely and costs zero until you type its name.
references/"extra files"Shipped with the skill, read only when the body points at them. Free until then.
5,000-token re-attach"it got truncated"After compaction, only the first 5,000 tokens of each invoked skill return. Top matters.
standing instruction"a step"Wording that applies for the whole task. The body is not re-read, so a step reads as done.

What this lesson skipped

Skills inside subagents. context: fork, agent, and what changes when the skill runs in its own window — Phase 06, lessons 45–48.

Enforcement. If a rule must hold every single time, a skill is a request. A hook is the enforcement — Phase 08.

Packaging. A skill plus hooks plus subagents as one installable unit is a plugin — Phase 09.

Listing-budget tuning. The knobs that cap or hide skill listings (skillListingBudgetFraction, skillOverrides, name-only) are a settings topic. Come back when the listing itself is one of your larger blocks.

Check yourself

4 questions. Answer before you reveal — recognising the right option is not the same as being able to produce it.

  1. A 600-line skill has its three most important rules near the bottom. The session compacts. When the skill is re-attached, which content is most likely to be there?

    1. The whole 600 lines, restored in full
    2. Nothing — invoked skills are never re-attached
    3. The first 5,000 tokens, filled from the top of the body
    4. The bottom 5,000 tokens, because they were written most recently
    Show answer

    C. The first 5,000 tokens, filled from the top of the body

    After compaction, Claude Code re-attaches the first 5,000 tokens of each invoked skill, with a 25,000-token combined budget. Option A overshoots — the cap exists because full restore is too expensive. Option B is wrong: invoked skills are re-attached; it is the skill listing that is not re-injected. Option D inverts the rule; the cap fills from the top of the file, which is why the strongest rule goes first.

  2. You want Claude to apply a set of codebase conventions automatically whenever they are relevant, but you do not want users to be able to trigger them with /name. Which frontmatter matches?

    1. disable-model-invocation: true
    2. user-invocable: false
    3. context: fork
    4. background: false
    Show answer

    B. user-invocable: false

    user-invocable: false hides the skill from the / menu and stops /name from running it, while Claude can still invoke it — exactly the background-knowledge case. Option A is the reverse: it stops Claude from invoking on its own and leaves manual invocation open. Option C runs the skill in a forked subagent, which changes where it loads, not who can trigger it. Option D is a subagent-timing field that only applies with context: fork.

  3. You move a 400-line checklist out of a skill's body into references/security.md and add a one-line pointer. You invoke the skill for a tiny change that needs none of the checklist. What did the checklist cost this run?

    1. 400 lines — files under the skill folder always ship into context
    2. Nothing — supporting files are read only when the body points at them and they are actually read
    3. Only the file's name, because the listing includes reference filenames
    4. It is impossible to know without opening the file
    Show answer

    B. Nothing — supporting files are read only when the body points at them and they are actually read

    Supporting files are tier three: they cost nothing until the body points at them and something reads them. Option A is the misconception that a skill folder is a single blob. Option C invents a listing of reference filenames; the startup listing is skill name plus description only. Option D overstates the uncertainty — /context and the transcript show whether the file was read.

  4. You run /compact in a long session that had a dozen skills listed at startup. Which of these is true afterwards?

    1. The skill descriptions reload with the rest of the startup content
    2. The skill listing is not re-injected; only skills you actually invoked are carried forward
    3. Every skill that was ever listed re-attaches in full
    4. All skills are dropped, invoked or not
    Show answer

    B. The skill listing is not re-injected; only skills you actually invoked are carried forward

    The skill descriptions are the one startup block that does not re-inject after compaction; invoked skills are re-attached (first 5,000 tokens each). Option A assumes the listing behaves like CLAUDE.md, which does reload — it does not. Option C retells the whole-listing myth in reverse. Option D is too strong: invoked skills are preserved, which is the point of putting your strongest rule at the top.
