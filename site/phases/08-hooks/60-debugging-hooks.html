LEARN · PHASE 08 · LESSON 60

Debugging Hooks

A hook that fails silently is the default failure mode, so the skill is

Type
Learn
Prerequisites
Lesson 59, Build a Guardrail Hook
Time
~30 minutes

Learning Objectives

  • Debug a silent hook in the order it actually fails: registration, matcher, payload, exit code, event
  • Tell a matcher bug from a payload bug from a wiring bug
  • Test a hook without Claude Code by piping a fabricated event into it
  • Read claude --debug for registration, matcher evaluation, skips, and crashes

The Problem

Your guardrail doesn't work. The agent ran git push and nothing happened. Or something happened — a line of text appeared, an action was refused — and it wasn't the refusal you wrote.

There are at least four places it can be wrong, and they look identical from the outside:

  1. The hook is registered but its matcher never matches.
  2. It matches and runs, but reads the wrong field and decides nothing.
  3. It decides, and you used the wrong channel — exit 1 instead of 2, stdout instead of stderr.
  4. It ran and was correct, on an event that can't block.

The debug loop that wastes an hour is checking the script. Nine times out of ten the script is fine, and the wiring is wrong — a matcher that looks like a regex and isn't, a settings file that merged with another, an event that can't block.

Learn the order. Check registration, then matching, then the payload, then the exit code, then the event's capability. In that order.

The Concept

Step 1 — is it registered?

/hooks

Lists every hook, which settings file it came from, whether it's enabled, and its matcher, type, and timeout. If it isn't here, nothing else matters.

Two reasons it won't be, and both bite:

  • Wrong settings file. .claude/settings.json vs .claude/settings.local.json vs ~/.claude/settings.json. Settings merge (Phase 04, Lesson 34), so a hook can be live from a file you forgot exists.
  • Settings changed after the session started. Restart Claude Code. This is the single most common "my hook doesn't work" and it costs people real time.

Step 2 — did the matcher match?

The matcher is not a substring filter. Three behaviours, one string decides which (Lesson 56):

  • Only letters, digits, _, -, spaces, ,, | → exact string, or alternatives split on | / ,.
  • Anything else → unanchored regex.

So "Edit" matches Edit and nothing else. "Edit.*" also matches NotebookEdit. "^Edit$" means exactly Edit.

Two more:

  • An event with no matcher support ignores the matcher and runs every time.
  • FileChanged and StopFailure use a stricter matcher syntax — a space, comma, or hyphen pushes them onto the regex path.

Step 3 — read the payload

Don't guess the field names. Print them.

#!/bin/sh
cat

Wire it to the event, trigger one occurrence, and read what actually arrives. Then log just what you need:

input=$(cat)
printf '%s\n' "$input" | jq '{event: .hook_event_name, tool: .tool_name, cmd: .tool_input.command, file: .tool_input.file_path}'

The failure this catches most often: .tool_input.command is absent on an Edit event, and bare jq -r prints the literal string null. That null then fails to match anything, so the hook decides nothing and exits 0. Use // empty or ?? ''.

Step 4 — exit codes

Lesson 58 in one line: exit 2 blocks, exit 1 and everything else non-zero fails open, and the reason comes from the first line of stderr.

If exit 2 "isn't blocking", check the event next. PostToolUse, PostToolUseFailure, SessionStart, Setup, Notification, MessageDisplay, StopFailure, PermissionDenied cannot block. A PostToolUse hook exiting 2 does not undo the tool — it sends its stderr into the model's context.

Step 5 — the debug log

claude --debug

For a persistent one:

claude --debug-file /tmp/claude-debug.log

Look for: hook registration, matcher evaluation, handler execution, whether a hook was skipped, and input/output processing errors. A hook that never ran says so there; a hook that ran and crashed says that too.

Useful when you're only checking startup:

claude --debug-file /tmp/claude-debug.log --init-only

Step 6 — test the script alone

The move that saves the most time: the script does not need Claude Code. Pipe it an event.

printf '%s\n' '{"hook_event_name":"PreToolUse","tool_name":"Bash","tool_input":{"command":"git push"}}' \
  | .claude/hooks/guardrail.sh; echo "exit=$?"

If that produces exit 2, the script is correct and the problem is wiring. If it produces 0, the problem is the script. Two minutes, no restart, no guessing.

Two things that fail with no error at all

Async hooks that decide too late. "async": true runs in the background and the harness doesn't wait. A decision printed after that arrives too late to control anything. If an async hook must ever block, use "asyncRewake": true, which wakes Claude on exit 2 and hands it the stderr. onFailure does nothing for async handlers.

Timeouts fail open. Default is 600s for command hooks, 30s on several events, 10s on MessageDisplay. A PreToolUse timeout normally lets the call through. If it must block, set "onFailure": "block" (needs v2.1.295+). And a hook that runs on every Bash call should carry a short explicit timeout: 5 — the default exists for slow work and gives you a six-minute hang when your script has a bug.

The reframe: hooks fail in a fixed order — registration, match, payload,

exit code, event capability — and checking them in that order beats reading

your script, because a correct script wired to the wrong matcher produces

exactly the same silence as a broken one.

Build It

1. Get the ground truth before touching anything

Take your guardrail from Lesson 59 and run /hooks.

✅ You pass when you can state, for each hook, which settings file supplied it and whether it's enabled.

2. Break it four ways, on purpose

In order: (a) restart-needed stale settings — add a hook and don't restart; (b) change the matcher from Edit to Edit.* and trigger NotebookEdit; (c) delete .tool_input?.file_path ?? '' from the Edit branch; (d) change exit 2 to exit 1.

Trigger each and record what you observe.

✅ You pass when you have four observations and each one matches the diagram above — including the one where nothing visibly happens at all.

3. Take the script out of the loop

Pipe a fabricated git push event into the guardrail. Then pipe an Edit event with no command field.

✅ You pass when the first gives exit=2 and the second gives exit=0 with no crash, and you can say which of your four breakages each one would have caught.

4. Find it in the debug log

claude --debug-file /tmp/claude-debug.log

Trigger one blocked action, quit, and search the log for the hook's name.

✅ You pass when you have quoted the line showing the hook registered and the line showing the matcher evaluated — and, for one deliberately-skipped hook, the line that says it was skipped.

5. Prove you can find a hook you didn't write

Add a PostToolUse hook to ~/.claude/settings.json on an event you use nothing else on. Trigger it. Then check whether removing it from the project settings changes anything.

✅ You pass when you can state which file was actually responsible and why your removal attempt did nothing.

Exercises

  1. Take a hook that isn't firing and run the six-step order above, writing down where it actually broke. ✅ You pass when you can name the step that found it and say what the previous step would have told you if you'd trusted it.
  1. Write a hook that fails open on purpose — malformed input exits 1 — then convert it to fail closed and record both observations by piping events at it. ✅ You pass when you can state what a user of your hook would experience under each, without reading the source.
  1. Find a hook in your settings or your user's settings that you did not remember adding, using /hooks, and determine which file it came from. ✅ You pass when you have the file path and one sentence on why that file exists.

Key Terms

TermWhat people sayWhat it actually means
debug log"the logs"claude --debug or --debug-file. Shows registration, matcher evaluation, skips, and crashes.
--init-only"startup check"Debug-file mode for checking that Setup / SessionStart hooks ran, without a full session.
skipped"it didn't run"The log says why. Usually the matcher, not an error.
stale settings"I edited the file"Settings load at session start. Edit and restart, or you're debugging the old copy.
async hook"a background hook"Can't block. A decision printed after the harness stopped waiting controls nothing.
asyncRewake"async that can block"Wakes Claude on exit 2 and hands it stderr. The one background mode with teeth.
fail open"it's not strict"A timeout or crash lets the action through. The default for every failure mode.

What this lesson skipped

Reading an agent or http hook's failure. These fail differently — connection failures, non-2xx responses, model timeouts — and each has its own diagnostics. Worth it only once you're using one; Lesson 56 names the types.

Hook input/output validation schemas. The harness logs schema-invalid JSON as a failure. What's valid per event is in the docs, not taught here.

InstructionsLoaded and FileChanged observability hooks. These exist for auditing what got loaded or changed, which is Phase 10's problem, not this phase's.

Multi-platform debugging. Windows shell: "powershell" vs sh, .cmd resolution, and path quoting all produce hook failures that look like logic bugs. Real; a rabbit hole if you hit it; exec form avoids most of it (Lesson 57).

stop_hook_active. Stop and SubagentStop carry it so your hook can tell whether it's re-entering after its own continuation, which prevents an infinite loop. It's a two-line guard, but it's a lesson in itself and no hook in this phase needs it.

Timeout defaults and the onFailure version floor were verified against the hooks page on 2026-10-15. Timeouts have changed before. Check https://code.claude.com/docs/llms.txt.

Check yourself

4 questions. Answer before you reveal — recognising the right option is not the same as being able to produce it.

  1. A hook that used to block force-pushes no longer does, and nothing about the script changed. Following the lesson's order, where do you look first?

    1. /hooks — is it registered, from which settings file, and did settings change since the session started?
    2. The regexes in the script — re-read every pattern line by line
    3. The transcript — search for where the agent mentioned the hook
    4. git status — check whether the working tree is clean
    Show answer

    A. /hooks — is it registered, from which settings file, and did settings change since the session started?

    The debug order is registration, then match, then payload, then exit code, then event capability. Registration first, because if the hook isn't listed — or was edited after the session started — nothing downstream matters. /hooks shows the source file and whether it is enabled. Option B is the hour-waster the order exists to prevent: nine times out of ten the script is fine and the wiring changed. Option C treats narrative as evidence. Option D is irrelevant to whether a hook fired.

  2. Your hook fires when the agent uses Edit but not when it uses NotebookEdit. Why?

    1. Edit is an exact-string matcher and does not match NotebookEdit; use ^Edit$|^NotebookEdit$, or a deliberate regex like Edit.*
    2. NotebookEdit isn't a tool, so no event fires for it
    3. Edit is a substring filter, so it should have matched — the hook must be unregistered
    4. NotebookEdit requires an entirely separate event from Edit
    Show answer

    A. Edit is an exact-string matcher and does not match NotebookEdit; use ^Edit$|^NotebookEdit$, or a deliberate regex like Edit.*

    When a matcher contains only letters, digits, _, -, spaces, commas, and |, it is an exact string or an alternation — so Edit matches only Edit, not NotebookEdit. To cover both, add the second name or shift onto the regex path consciously. Option B is false: NotebookEdit is a real tool. Option C is the opposite of how exact matching works — a substring filter is what people assume and the docs say otherwise. Option D invents event separation that doesn't exist.

  3. You add a PostToolUse hook to .claude/settings.json and immediately trigger the action in the same session. Nothing happens. Most likely cause?

    1. Settings load at session start — the new hook isn't live until you restart Claude Code
    2. The matcher string is malformed
    3. PostToolUse hooks need "async": true to run at all
    4. The settings file needs to be made executable
    Show answer

    A. Settings load at session start — the new hook isn't live until you restart Claude Code

    This is the single most common "my hook doesn't work": the file changed but the session is still running the copy it loaded at launch. Restart. Option B is possible but not the first suspect when the hook is brand new and the same file worked before. Option C is backwards — async makes a hook run in the background and it still runs; it is not required. Option D confuses a JSON config file with a script.

  4. You pipe a fabricated git push event into your guardrail script and it exits 2. But when the agent actually runs git push, nothing is blocked. Where is the problem?

    1. The script is fine — the fault is wiring: registration, the matcher, or a settings file that didn't reload
    2. The script is wrong — it must be reading the wrong field
    3. The agent is bypassing the hook on purpose
    4. Hooks cannot block git push specifically
    Show answer

    A. The script is fine — the fault is wiring: registration, the matcher, or a settings file that didn't reload

    The fabricated-event test separates the two halves of the problem: a correct exit 2 in isolation means the decision logic works, so the defect is between the harness and the script — the hook isn't registered where you think, the matcher doesn't fire, or the session is running stale settings. Option B is ruled out by the test you just ran. Option C attributes intent to a mechanism. Option D is false: the command name is irrelevant; the event and matcher decide.
