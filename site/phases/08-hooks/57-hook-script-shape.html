LEARN · PHASE 08 · LESSON 57

Hook Script Shape — stdin JSON → stdout / exit code

The script is a function of one JSON object with no arguments. Everything it

Type
Learn
Prerequisites
Lesson 56, All the Events, Matchers, Handler Types
Time
~35 minutes

Learning Objectives

  • Parse the event JSON on stdin and read the fields you need
  • Choose between exit code and JSON stdout for a given decision
  • Return a PreToolUse deny, an additionalContext, and a systemMessage from the same script shape
  • Feed a hook script a fabricated event from your shell, without Claude Code

The Problem

You write a hook. It runs. It seems to do nothing — no output, no error, no block, and the agent carries on exactly as if the hook weren't there.

The script is almost certainly fine. What you got wrong is the interface.

There is no argument list. There is no environment variable holding the command. No file is handed to you. The event arrives as one JSON object on stdin, and if your script doesn't read stdin, it is working with nothing at all — and a script that inspects nothing will usually decide nothing.

Two scripts, same file, one line different:

cat > /tmp/log.json        # reads the event — works
cat > /dev/null            # doesn't read it — you are guessing

The Concept

Three exit codes, and they mean three different things. Lesson 58 is entirely about the middle one versus the third, so treat this section as orientation.

What arrives on stdin

Every event carries these:

FieldWhat it is
hook_event_nameWhich event fired. Check this in a hook wired to several
session_idCurrent session
cwdWhere the agent is now. Not the project root — see below
transcript_pathConversation file. Written asynchronously; may be stale
permission_mode"default", "plan", "acceptEdits", … not sent to every event

Tool events add tool_name, tool_input, tool_use_id.

A real PreToolUse payload:

{
  "session_id": "abc123",
  "cwd": "/home/user/my-project",
  "hook_event_name": "PreToolUse",
  "tool_name": "Bash",
  "tool_input": {
    "command": "npm test",
    "description": "Run test suite"
  },
  "tool_use_id": "toolu_01ABC123"
}

Reading it

In shell, with jq:

#!/bin/sh
input=$(cat)
tool=$(printf '%s' "$input" | jq -r '.tool_name')
command=$(printf '%s' "$input" | jq -r '.tool_input.command // empty')

// empty matters. .tool_input.command is absent on Edit, and plain jq -r prints the literal string null — which then fails to match anything and reads as a decision you never made.

In Node, which is what this repo already uses:

#!/usr/bin/env node
let raw = '';
process.stdin.on('data', (c) => (raw += c));
process.stdin.on('end', () => {
  const event = JSON.parse(raw);
  if (event.hook_event_name === 'PreToolUse' && event.tool_name === 'Bash') {
    const cmd = event.tool_input?.command ?? '';
    if (/^git\s+push\b/.test(cmd)) {
      process.stderr.write('Blocked: no git push from this project.\n');
      process.exit(2);
    }
  }
  process.exit(0);
});

?? '' is the same guard as // empty. Pick one and keep it.

Going out: exit code, or JSON, or both

You wantDo this
Allow, silentlyexit 0, print nothing
Blockwrite the reason to stderr, exit 2
Add context for the modelexit 0 + JSON with additionalContext
Tell the user somethingexit 0 + JSON with systemMessage
Change what the model readsexit 0 + JSON with updatedInput or updatedToolOutput
Auto-format after an editJust do it on disk; exit 0

Print one JSON object and nothing else. The harness parses your stdout as JSON only when the entire output is a single valid object surrounded by whitespace. One stray echo before it and your decision is now plain text.

The three JSON shapes you will write by hand

Block a tool call — PreToolUse, top-level decision: "block" also works but the nested form is the one with a reason field:

{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "Writes under dist/ are generated. Edit src/ instead."
  }
}

Add context the model will read:

{
  "hookSpecificOutput": {
    "hookEventName": "PostToolUse",
    "additionalContext": "This file is generated. Edit src/schema.ts and run the generator."
  }
}

Stop the whole thing — continue: false beats any event-specific decision:

{
  "continue": false,
  "stopReason": "Build failed, fix errors before continuing"
}

additionalContext and systemMessage are not the same thing and get confused constantly:

FieldGoes toUse for
additionalContextThe model's contextTeaching the agent something true
systemMessageThe user's screenTelling the human something

additionalContext strings cap at 10,000 characters. Past that, the excess goes to a file and the model gets the path plus a 2,000-character preview. Don't build on that.

Two fields that bite

suppressOutput does nothing. The docs are explicit: it's accepted for schema compatibility and is inert. It does not affect the transcript or the debug log. If you were reaching for it to quiet a hook, reach for systemMessage or fix the output.

${CLAUDE_PROJECT_DIR} is not cwd. The placeholder is where the session started. In a worktree (Phase 16) it still points at the main checkout, while cwd is the worktree. If your hook needs to know where the agent is writing, read cwd from stdin. If it needs the repo's .claude/ directory and config, use the placeholder.

The reframe: a hook script has no arguments and no memory — the event is

the entire input and the exit code is the entire output, so anything you fail

to read off stdin is something you never had.

Build It

1. Build a hook you can test without Claude Code

Create .claude/hooks/inspect.sh:

#!/bin/sh
cat

Wire it to PostToolUse with matcher Bash, restart, run any command.

Then, without Claude Code at all:

printf '%s' '{"hook_event_name":"PreToolUse","tool_name":"Bash","tool_input":{"command":"git push --force"}}' \
  | .claude/hooks/inspect.sh

✅ You pass when the second command prints exactly the JSON you piped in, and you can say why that proves the interface without any Claude Code involved.

2. Read one field safely

Replace the body with a parse, and pipe it an Edit event, which has no .tool_input.command:

#!/bin/sh
input=$(cat)
tool=$(printf '%s' "$input" | jq -r '.tool_name')
command=$(printf '%s' "$input" | jq -r '.tool_input.command // empty')
printf 'tool=%s cmd=[%s]\n' "$tool" "$command"

✅ You pass when the Edit payload prints an empty cmd=[...], not cmd=[null].

3. Block, by exit code

#!/bin/sh
input=$(cat)
command=$(printf '%s' "$input" | jq -r '.tool_input.command // empty')
case "$command" in
  git\ push*)
    echo "Blocked: no git push from this project." >&2
    exit 2
    ;;
esac
exit 0

Pipe it a git push --force event and check $?. Then pipe it git status and check it is 0.

✅ You pass when the first is exit 2 with the reason on stderr and the second is exit 0.

4. Add context, by JSON

Wire a PostToolUse hook on matcher Edit|Write that emits additionalContext when the edited path is a generated file. Trigger it by editing a file under dist/.

✅ You pass when the agent's next turn references the reminder, and .claude/hooks/<your script> contains no echo before the JSON.

5. Prove the parse-by-accident failure

Add a stray echo "running" to the top of the JSON-emitting script. Re-trigger.

✅ You pass when the hook no longer affects anything, and you can explain it in terms of "the whole of stdout had to be one JSON object".

Exercises

  1. Write a hook script that refuses any Bash call whose command contains rm -rf, and prove all four of: block, allow, exit code 0 on a normal command, and no accidental block of a command that merely mentions rm. ✅ You pass when you have the two exit codes recorded and can name the case that would have false-positived under a naive substring match.
  1. Feed one fabricated event to your script per event family — tool, prompt, stop — and make the script handle all three from the same file without crashing on a missing field. ✅ You pass when all three return 0 and you can show the field your script reads that is absent in at least one of them.
  1. Take the PostToolUse formatter pattern and produce the version that also adds additionalContext explaining the format it applied. ✅ You pass when the JSON you print is exactly one object and the model mentions it on the next turn.

Key Terms

TermWhat people sayWhat it actually means
stdin"the arguments"One JSON object. There is no argument list.
stdout"the output"Shown only on a few events; parsed as JSON only if the whole thing is one object
stderr"the error log"On exit 2, the first line is the blocking reason shown to the user
additionalContext"the hook message"Goes into the model's context. Capped at 10k chars.
systemMessage"the hook output"Goes to the user's screen, not the model.
suppressOutput"keeps it quiet"Accepted and inert. Does nothing.
hookSpecificOutput"the decision object"Event-specific. Always carries hookEventName.
${CLAUDE_PROJECT_DIR}"the working directory"Where the session started. In a worktree, the main checkout — not where the agent is.

What this lesson skipped

Every event's hookSpecificOutput shape. PermissionRequest nests updatedInput inside a decision.behavior object; PermissionDenied uses retry; PostToolBatch takes an array of tool calls. Each has its own shape. Copy from the docs for the event you're writing — the hooks page is copy-pasteable and authoritative.

Async hooks. A background hook ("async": true) can't block: the harness stops waiting, so a decision printed afterwards controls nothing. If you use async, print any decision before starting the background work. Lesson 60.

Timeouts. A PreToolUse timeout normally lets the call through. There's an onFailure: "block" setting that changes it, and it needs a recent version. Lesson 60, because a silent pass-through is a debugging problem.

http and mcp_tool handlers. Same stdin contract, different return path — your decision comes back in an HTTP response body or an MCP tool result instead of an exit code. Worth knowing, not worth a lesson until Phase 07 or 09 depends on it.

Scripting languages. Everything here is POSIX sh or Node. Python works the same way; the interface doesn't care what you write it in.

The exact field set on stdin grows over time. Verified against the hooks page on 2026-10-15; check https://code.claude.com/docs/llms.txt before trusting a field name.

Check yourself

4 questions. Answer before you reveal — recognising the right option is not the same as being able to produce it.

  1. One guardrail script is declared on both Bash and Edit|Write. It blocks when the command contains rm -rf, read with jq -r '.tool_input.command'. An Edit event arrives, which carries file_path but no command. What does the script actually see?

    1. The literal string null — it doesn't match rm -rf, so the script quietly allows the edit
    2. An empty string — jq collapses a missing field to "", so the block rule is skipped
    3. An error from jq, which exits non-zero and is reported as a hook failure
    4. Nothing — the harness omits the field and withholds the whole event
    Show answer

    A. The literal string null — it doesn't match rm -rf, so the script quietly allows the edit

    jq -r on a missing field prints the literal string null, not an empty string and not an error. That null then fails to match rm -rf, so the hook decides nothing and exits 0 — the safe-looking default. The fix is jq -r '.tool_input.command // empty', or ?? '' in Node. Option B is the tempting one because "missing data" feels like an empty string, but jq's raw mode prints null. Option C misattributes a non-error as a crash; indexing a missing key is not an error. Option D is wrong because events always arrive whole — the field is simply absent.

  2. Your hook reformats a file after an edit and you want the person at the keyboard — not the model — to see that it happened. Which output carries that?

    1. systemMessage in the JSON on stdout
    2. additionalContext in the JSON on stdout
    3. permissionDecision in hookSpecificOutput
    4. The first line of stderr, with exit 0
    Show answer

    A. systemMessage in the JSON on stdout

    systemMessage goes to the user's screen; additionalContext goes into the model's window. The two are confused constantly because they are both strings in the same JSON object, but they have different readers. Option B would tell the model, not the human — the opposite of what you asked for. Option C is a decision field (allow/deny) for tool events, not a display channel. Option D is a trap: stderr is only read as a reason on exit 2; on exit 0 it is not surfaced as a message.

  3. A teammate adds a debug line — echo "hook running" — above the single JSON object their PostToolUse hook prints. The script still runs, exits 0, and prints valid JSON. What does the harness do with the decision?

    1. Ignores the JSON — stdout is parsed as JSON only when the whole output is one object, and the stray line makes it plain text
    2. Parses the JSON anyway — the harness scans stdout for the first { and reads from there
    3. Errors, because stdout must be empty when a hook exits 0
    4. Uses the JSON, but records a warning about the extra line
    Show answer

    A. Ignores the JSON — stdout is parsed as JSON only when the whole output is one object, and the stray line makes it plain text

    The whole of stdout must be a single valid JSON object surrounded by whitespace. One preceding echo and the output is no longer that, so it is treated as plain text and the decision is lost — the hook appears to do nothing while the script is perfect. Option B is the common hope; there is no scanning or extraction. Option C inverts the rule — plain text on stdout is allowed, it just isn't a decision. Option D invents a warning that doesn't happen; the failure is silent.

  4. A hook needs the path the agent is currently working in. The session is running inside a worktree, so this differs from where the session started. Which value do you read?

    1. cwd from the event JSON on stdin
    2. ${CLAUDE_PROJECT_DIR}
    3. The process's process.cwd()
    4. transcript_path from the event JSON
    Show answer

    A. cwd from the event JSON on stdin

    cwd on stdin is where the agent is now, which is exactly the question. Option B is the trap: ${CLAUDE_PROJECT_DIR} is where the session started — the main checkout even when the agent runs in a worktree — so it is right for finding the repo's .claude/ and wrong for finding current edits. Option C relies on the process's launch directory, which you don't control and can't assume. Option D is the conversation file, unrelated to the working directory.
