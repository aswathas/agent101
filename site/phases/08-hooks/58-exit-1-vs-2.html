LEARN · PHASE 08 · LESSON 58

The Exit-1-vs-2 Trap

Exit 1 is an error. Exit 2 is a decision. Everything you build in this phase

Type
Learn
Prerequisites
Lesson 57, Hook Script Shape
Time
~30 minutes

Learning Objectives

  • Say which of the three exit codes means "block" and which means "crashed"
  • Predict, from the event's name alone, whether exit 2 will stop the action
  • Choose a fail-open or fail-closed failure mode deliberately, and write it down
  • Explain why a guardrail that fails open is the more dangerous default

The Problem

Your guardrail is correct. The script reads the command, sees rm -rf, decides to block, and writes the reason:

echo "Blocked: destructive command"   # no >&2
exit 1

The command runs anyway.

exit 1 is the code every shell script uses to say "something went wrong." To the harness it means: this hook crashed, here is the first line of its stderr, carry on. The action continues. Your guardrail is a warning label on a door.

The line that would have worked is exit 2. Same script, same message, opposite outcome.

This is the single most common way a hook silently fails, because it fails open. A guardrail that lets everything through when it's broken is worse than no guardrail, because you stop looking at it.

The Concept

Three exit codes. Every other code behaves the same as 1.

CodeMeansThe action
0Success. Structured decisions, if any, were printedContinues
2Blocking error. First line of stderr is the reasonBlocked, on blocking events
anything else, incl. 1Non-blocking errorContinues

Read that flow once more. Exit 2 does nothing on a non-blocking event. PostToolUse, SessionStart, Setup, Notification, MessageDisplay, StopFailure, PermissionDenied — none of them block, whatever you exit with.

The trap, stated as a rule

If you mean "stop", you must exit 2. If you mean "something broke", exit 1 or anything else. Never let a crash produce exit 2.

That last clause is the sharp edge. A guardrail script that dies halfway — set -e plus a bad jq on unexpected input — exits non-zero. If you wrote the guard path as exit 2 and the crash path as exit 1, the crash is loud and visible. If you wrote the crash path as exit 2 because it was "the failure branch", a broken script silently becomes a total lockout.

ponytail: a guardrail that fails open is fine during development —

you want to be able to work while you debug it. It is not fine once you trust

it. Decide which failure mode you want and write it down.

Four ways to get it wrong

1. Reason on stdout instead of stderr.

echo "Blocked: no git push"      # stdout — the user sees nothing useful
echo "Blocked: no git push" >&2  # stderr — first line becomes the reason

On exit 2 the first line of stderr is the blocking reason shown to the user. On stdout it's ignored.

2. Print JSON you didn't mean to print.

Valid JSON on stdout is treated as a successful structured decision, and then the exit code is ignored. If a hook exits 3 and prints valid JSON, the JSON wins and the hook doesn't fail. This is convenient and it is how an echo debug line turns into a hook that "succeeds" while blocking nothing.

3. Assume exit 2 blocks everywhere. Covered above, and it's the one that makes a PostToolUse guardrail feel broken when the script is fine.

4. Ignore hook failures entirely.

{
  "type": "command",
  "command": "node",
  "args": ["${CLAUDE_PROJECT_DIR}/.claude/hooks/check-command.js"],
  "onFailure": "block"
}

By default a hook failure, a timeout, or invalid JSON lets the action continue. onFailure: "block" converts failures, crashes, timeouts, connection failures, and schema-invalid output into blocks. It needs Claude Code v2.1.295 or later — check your version before relying on it.

Note what it does not cover: plain-text stdout is not a failure.

Where exit 2 actually stops something

Blocking: PreToolUse, UserPromptSubmit, UserPromptExpansion, Stop, SubagentStop, TeammateIdle, TaskCreated, TaskCompleted, PostToolBatch, ConfigChange, PreCompact, PreModelSwitch, Elicitation, ElicitationResult.

Not blocking: PostToolUse, PostToolUseFailure, PermissionRequest, PermissionDenied, Notification, SessionStart, Setup, StopFailure, MessageDisplay, PostCompact, PostModelSwitch, SubagentStart.

One idiom worth knowing: on PostToolUse, exit 2 is the way to send stderr into the model's context — feedback on a tool that already ran. It doesn't block the tool; it hands the model the error. Same code, different effect, different event. That's the one place the two halves of this lesson meet.

The reframe: exit 1 is the code for "I have no opinion" and exit 2 is the

code for "no" — and a guardrail whose failure path uses the wrong one doesn't

announce that it stopped working, it just stops working.

Build It

1. See exit 1 fail open, for real

Take the blocking hook from Lesson 57, change exit 2 to exit 1, and ask the agent to run the blocked command.

✅ You pass when the command runs, and you can point to the hook-error notice in the session showing a failure that nobody intended.

2. See exit 2 block, on the same script

Change it back to exit 2. Same command.

✅ You pass when the command does not run and your stderr line appears verbatim as the reason.

3. Feed it the reason channel

Move the echo to stdout, keep exit 2.

✅ You pass when the block still happens but the reason shown to the user is missing or wrong, and you can say which stream carries it.

4. See exit 2 do nothing

Move the same script from PreToolUse to PostToolUse, matcher Edit|Write, and have it exit 2 on a path under dist/. Edit a file there.

✅ You pass when the edit lands and the hook still ran, and you can name which column of the blocking list each event sits in.

5. Decide your failure mode, and write it down

Make your guardrail crash on purpose — malformed input to jq, or a file the script reads that isn't there — and observe the code it exits with.

Then decide: fail open (stay usable while broken) or fail closed (onFailure: "block", or an explicit crash path)?

✅ You pass when you have a written line somewhere in the script saying which, and you can say what a user of your hook would observe under each.

Use It

You meanWrite
Allowexit 0, no output
Blockreason on stderr, exit 2
Block on a non-blocking eventNothing. Pick a blocking event instead
Report a crashstderr message, exit 1 (or anything non-zero)
Turn every failure into a block"onFailure": "block" in the handler
Send a tool's error to the modelPostToolUse + exit 2
Hand the model contextexit 0 + additionalContext

Exercises

  1. Write one script that handles three cases — allow, block, crash — and exercise all three by piping events at it, recording $? for each. ✅ You pass when you have three distinct codes recorded, each matching the intent you wrote in a comment beside it.
  1. Take a working guardrail and reproduce the "JSON on stdout beats the exit code" behaviour: print a valid object then exit 1. ✅ You pass when you can state, from the observed behaviour, that the exit code was ignored and the JSON decided instead.
  1. Find a hook in your own settings that would fail open on a crash, and either fix it or write down why you're choosing to leave it. ✅ You pass when your note names the specific failure and what a user would observe when it happens.

Key Terms

TermWhat people sayWhat it actually means
exit 2"an error"A blocking decision. Cancels a pending action on blocking events.
exit 1"a failure"Correct. A non-blocking error. The action continues.
non-blocking error"it broke"Any non-0, non-2 exit, plus a process that can't start, plus a timeout
fail open"it's broken"A broken guardrail that permits. The dangerous default.
fail closed"it's strict"A broken guardrail that stops. Safer, and it can lock you out of your own session.
onFailure: "block""strict mode"Converts failures, timeouts, and invalid output into blocks. Recent feature; check your version.
blocking reason"the output"The first line of stderr on exit 2. Not stdout.

What this lesson skipped

The JSON decision fields per event. Exit 2 and structured JSON are two different doors into the same decision. Lesson 57 covers the three you'll write by hand.

Async hooks and their exit codes. A background hook's exit code arrives after the harness stopped waiting — it can't retroactively block. asyncRewake is the exception: it wakes Claude on exit 2. Lesson 60.

Timeouts as failures. A timed-out PreToolUse normally lets the call through. Combined with onFailure: "block", it stops. This is a debugging story more than a design one, so it's in Lesson 60.

Version specifics. onFailure requires v2.1.295+. Exit codes 0/1/2 are far older and stable. Check the hooks page for the current floor before you depend on the newer field.

Blocking-event membership was verified against the hooks page on 2026-10-15. Re-check https://code.claude.com/docs/llms.txt — events get added, and a new event's blocking behaviour is exactly the thing you'd get wrong by trusting this list.

Check yourself

4 questions. Answer before you reveal — recognising the right option is not the same as being able to produce it.

  1. Your PreToolUse guardrail reads rm -rf, decides to block, writes its reason with echo "Blocked: destructive" (no redirect) and exits 1. The agent runs the command anyway. Why?

    1. Exit 1 is a non-blocking error — the harness treats it as a crash and carries on, and the reason on stdout is ignored
    2. Exit 1 blocks only when stderr is empty
    3. The command ran because echo flushed stdout before the exit code was read
    4. Exit 1 blocks, but Bash is an event where exit codes don't apply
    Show answer

    A. Exit 1 is a non-blocking error — the harness treats it as a crash and carries on, and the reason on stdout is ignored

    To the harness, exit 1 means "this hook broke" — a non-blocking error — so the pending action continues. The reason is doubly lost: it went to stdout, and only the first line of stderr is read as a blocking reason, on exit 2. Option B invents a condition; stream choice and exit code are independent, and exit 1 never blocks. Option C mistakes ordering for semantics: the decision is the exit code, not the timing of the write. Option D is simply false — PreToolUse is a blocking event, and a guardrail can be attached to any tool via its matcher.

  2. The same guardrail script is moved to PostToolUse on Edit|Write and still exits 2 when the path is under dist/. You edit a file there. The edit lands, and on a later turn the model references your reason. Is the hook working?

    1. Yes — PostToolUse fires after the write, so exit 2 can't undo it; there it delivers stderr into the model's context
    2. No — exit 2 always blocks, so the file should have been removed
    3. No — the matcher must be wrong, since a correct matcher would have fired before the write
    4. Yes — but only because the file happened to be under dist/
    Show answer

    A. Yes — PostToolUse fires after the write, so exit 2 can't undo it; there it delivers stderr into the model's context

    PostToolUse is a non-blocking event: the write already happened, so no exit code can take it back. Exit 2's useful role there is to hand the first line of stderr to the model as feedback — which is exactly what you observed. If you wanted the write refused, the seam is PreToolUse. Option B assumes exit 2 blocks everywhere, which is the trap this lesson is named for. Option C blames the matcher although the handler demonstrably ran. Option D attaches significance to dist/ that isn't there; the event's position on the loop is the whole story.

  3. A hook exits 3 and prints exactly one valid JSON object on stdout. What does the harness do with the decision?

    1. Treats the JSON as the decision and ignores the exit code — a valid structured decision wins
    2. Treats exit 3 as the decision and ignores the JSON
    3. Fails the hook, because exit 3 is out of range
    4. Skips the hook and runs the next handler in the group
    Show answer

    A. Treats the JSON as the decision and ignores the exit code — a valid structured decision wins

    Valid JSON on stdout is a successful structured decision, and when one is present the exit code is not consulted. This is convenient and is exactly how a leftover echo that happens to print JSON turns into a hook that 'succeeds' while blocking nothing. Option B reverses the precedence. Option C assumes an allowed range that doesn't exist — any exit other than 0 and 2 is just a generic failure. Option D invents handler-skipping; the JSON is the answer.

  4. You want a broken guardrail — a crash, a timeout, or schema-invalid JSON — to stop the action instead of letting it through. What do you add, and what does it not cover?

    1. "onFailure": "block" in the handler — it converts failures, timeouts, and invalid output into blocks, but plain-text stdout is not a failure
    2. "exitOnFailure": true — it blocks on any non-zero exit, including exit 1
    3. set -e at the top of the script — any error becomes a block
    4. "onFailure": "block" — it also blocks whenever stdout isn't JSON, so plain text is covered
    Show answer

    A. "onFailure": "block" in the handler — it converts failures, timeouts, and invalid output into blocks, but plain-text stdout is not a failure

    onFailure: "block" is the documented switch: it turns crashes, timeouts, connection failures, and schema-invalid output into blocks, and it needs a recent Claude Code (v2.1.295 or later). What it does not cover is plain text on stdout — that is not a failure, so a hook printing prose still doesn't block. Option B names a field that doesn't exist. Option C is a shell feature that makes the script exit non-zero, which fails open, the opposite of what you want. Option D is the tempting over-read and wrong precisely because of the plain-text clause.
